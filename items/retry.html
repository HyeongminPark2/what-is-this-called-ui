재시도

Retry · backoff

재시도는 실패한 요청을 다시 보내는 것입니다. 멈춘 서버에 요청을 쉬지 않고 계속 보내면 부하가 쌓여 서버가 복구되기 더 어려워지므로, 다시 보내는 간격을 두 배씩 늘리는 것이 기본입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

서버가 잠깐 멈췄다가 돌아오는 상황이라고 가정해 보겠습니다. 실패하자마자 바로바로 다시 보내면 짧은 시간에 요청이 수십 번 나가는데, 데모는 보낸 횟수와 마지막 간격을 재서 적습니다.
지수 백오프는 간격을 1 · 2 · 4 · 8초로 늘립니다. 그러면 같은 시간 동안 보내는 횟수가 크게 줄면서도, 서버가 돌아오면 금세 성공합니다. 재시도하는 동안에는 언제 다시 시도하는지, 지금 몇 번째 시도인지를 사용자에게도 보여 줘야 합니다.

2 이름같은 것을 부르는 여러 이름

한국어재시도, 다시 시도, 백오프
영어retry, exponential backoff, jitter
같이 쓰는 말재시도 간격을 두 배씩 늘리는 것은 지수 백오프, 그 간격에 무작위 값을 섞어 여러 기기가 같은 순간에 몰리지 않게 하는 것은 지터(jitter)라고 합니다. 같은 요청을 두 번 받아도 한 번만 처리되는 성질은 멱등(idempotent)이라고 하고, 실패가 계속될 때 요청 자체를 끊는 장치는 서킷 브레이커라고 부릅니다.
자주 잘못 부르는 이름새로 고침 — 새로 고침은 사용자가 직접 화면 전체를 다시 불러오는 것이고, 재시도는 실패한 요청 하나를 다시 보내는 것입니다.
폴링 — 폴링은 실패와 상관없이 일정한 주기로 서버에 묻는 것입니다.
오프라인 큐 — 오프라인 큐는 연결이 없을 때 요청을 쌓아 두는 것이고, 재시도는 연결된 상태에서 실패한 요청을 다시 보내는 것입니다.

3 상태간격에 따라 달라지는 결과

4 해부도부분마다 붙은 이름

간격을 1 · 2 · 4 · 8초로 두 배씩 늘림
흔들기(jitter)로 요청이 몰리지 않게 함
다섯 번쯤 실패하면 자동 재시도를 멈춤
다시 보내도 되는 요청인지 먼저 확인함
몇 번째 시도인지, 언제 다시 보내는지 보여 줌
끝내 실패하면 다시 시도 버튼을 줌
  1. 간격 두 배씩 늘림1 · 2 · 4 · 8초로 간격을 늘립니다
  2. 흔들기 무작위 섞기간격에 무작위 값을 섞어 여러 기기의 요청이 한꺼번에 몰리지 않게 합니다
  3. 최대 횟수 다섯 번쯤다섯 번쯤 실패하면 자동 재시도를 멈추고 사용자에게 넘깁니다
  4. 다시 보내도 되는지 확인 보내기 전에 확인다시 보내도 되는 요청인지 먼저 확인합니다. 결제는 멱등 키 없이 다시 보내면 안 됩니다
  5. 진행 상황 표시 몇 번째 시도인지와 다음 시각몇 번째 시도인지, 언제 다시 보내는지 보여 줍니다
  6. 자동 재시도 중단 다시 시도 버튼다시 시도할지는 사용자가 정하게 합니다

다시 보내기 전에 이 요청을 두 번 보내도 되는지 꼭 확인해야 합니다. 조회(GET)는 두 번 보내도 괜찮지만, 결제나 전송은 두 번 처리되면 사고로 이어집니다. 그래서 결제나 전송 요청에는 멱등 키를 붙여, 서버가 같은 키를 두 번 받으면 한 번만 처리하게 해 둡니다.
흔들기가 없는 백오프도 문제를 일으킵니다. 수천 대의 기기가 동시에 끊겼다면 모두 정확히 1초 뒤에 다시 보내게 되고, 그 순간 몰린 요청 때문에 서버가 또 멈춥니다. 간격에 무작위 값을 조금 섞으면 요청이 보내지는 시점이 흩어집니다.

5 쓸 때 / 안 쓸 때

재시도를 구현할 때 지킬 것

  • 재시도를 구현할 때. 지수 백오프에 흔들기를 더한 방식을 기본으로 씁니다
  • 요청을 다시 보내기 전. 다시 보내도 되는 요청인지 먼저 확인합니다
  • 재시도하는 동안. 지금 몇 번째 시도인지 보여 줍니다

재시도에서 피할 것

  • 쉬지 않고 다시 보낼 때. 서버 부하를 더 키웁니다
  • 결제나 전송 요청을 멱등 키 없이 다시 보낼 때
  • 끝없이 다시 보낼 때. 다섯 번쯤에서 멈춥니다
  • 사용자에게 알리지 않고 재시도할 때. 사용자는 화면이 멈춘 줄 압니다

함께 보면 좋은 항목 — 연결이 아예 없을 때의 처리는 오프라인 항목에서, 실패 화면은 에러 상태 항목에서 다룹니다. 기다리는 동안 보여 줄 표시는 스피너에, 실패를 알리는 문구는 오류 문구에 정리되어 있습니다.

7 최소 코드와 규칙구현할 때 지킬 최소 규칙

간격을 두 배씩 늘리고 무작위 값을 조금 섞습니다. 최대 횟수는 다섯 번이면 충분합니다.

async function withRetry(fn, { max = 5 } = {}) {
  for (let n = 0; ; n++) {
    try { return await fn(); }
    catch (e) {
      if (n >= max || !canRetry(e)) throw e;
      const base = Math.min(8000, 1000 * 2 ** n);
      const jitter = base * (0.5 + Math.random() * 0.5);  // 흔들기
      show(`${n + 2}번째 시도 — ${Math.round(jitter / 1000)}초 뒤`);
      await sleep(jitter);
    }
  }
}

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

Retry-After 헤더로 간격 알려 주기서버가 이 헤더로 언제 다시 보내라고 알려 주면 화면에서 간격을 짐작할 필요가 없습니다.
멱등 키로 중복 처리 막기서버는 같은 키가 붙은 요청을 두 번 받으면 다시 처리하지 않고 처음 결과를 그대로 돌려줍니다.
오류 종류에 따라 다르게 대응하기429(요청이 너무 잦음)는 기다렸다가 다시 보내면 되지만 400(잘못된 요청)은 다시 보내도 실패하므로, 두 오류는 전혀 다르게 대응해야 합니다.
서킷 브레이커로 요청 잠시 끊기실패가 연달아 쌓이면 잠시 요청 자체를 끊어서 서버가 복구될 시간을 줍니다.

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

재시도의 원리는 플랫폼마다 같고, 쓰는 라이브러리만 다릅니다.

웹직접 또는 라이브러리
fetch 자체에는 재시도 기능이 없지만, 데이터를 불러오는 쿼리 라이브러리들은 재시도를 기본으로 넣어 둡니다.
iOSURLSession · 직접
waitsForConnectivity를 켜면 요청이 연결될 때까지 기다렸다가 나가게 할 수 있습니다.
안드로이드WorkManager
백오프까지 OS가 맡아서, 앱이 꺼져 있어도 나중에 다시 보냅니다.

플랫폼 차이 때문에 자주 생기는 문제 — 안드로이드의 WorkManager는 앱이 꺼진 뒤에도 재시도를 이어 가는 장치로, 웹에는 이런 장치가 없습니다. 웹에서 가장 비슷한 기능은 서비스 워커의 백그라운드 동기화인데, 아직 브라우저마다 지원 여부가 다릅니다. 그래서 웹에서는 탭이 열려 있는 동안에만 재시도가 돈다고 보는 편이 안전합니다. 중요한 요청은 오프라인 항목처럼 쌓아 두었다가 다음에 앱을 열었을 때 보내도록 설계합니다.
