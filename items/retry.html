재시도

Retry · backoff

죽은 서버에 쉬지 않고 몰아치면 더 못 일어납니다. 간격을 두 배씩 늘리는 것이 기본입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

서버가 잠깐 죽었다 돌아온다고 칩시다. 바로바로 다시 보내면 짧은 시간에 요청이 수십 번 나갑니다 — 데모가 보낸 횟수와 마지막 간격을 재서 적습니다.
지수 백오프는 1 · 2 · 4 · 8초로 간격을 늘립니다. 같은 시간에 보내는 횟수가 확 줄고, 서버가 돌아오면 금세 성공합니다. 그리고 재시도가 도는 동안 사람에게도 보여 줘야 합니다 — 언제 다시 시도하는지, 지금 몇 번째인지.

2 이름부르는 말이 여러 개다

한국어재시도, 다시 시도, 백오프
영어retry, exponential backoff, jitter
같이 쓰는 말간격을 두 배씩 늘리는 것이 지수 백오프, 거기에 무작위를 섞어 여러 기기가 같은 순간에 몰리지 않게 하는 것이 지터(jitter)입니다. 같은 요청을 두 번 받아도 한 번만 처리되게 하는 성질을 멱등(idempotent)이라 하고, 계속 실패할 때 아예 요청을 끊는 장치를 서킷 브레이커라 부릅니다.
자주 잘못 부름새로 고침 — 새로 고침은 사람이 화면 전체를 다시 부르는 것입니다.
폴링 — 폴링은 실패와 상관없이 주기적으로 묻는 것입니다.
오프라인 큐 — 오프라인은 연결이 없을 때 쌓아 두는 쪽입니다.

5 해부도부분 이름이 제일 안 알려진 지식

간격을 두 배씩 — 1 · 2 · 4 · 8초
흔들기(jitter) — 다 같이 몰리지 않게
최대 횟수 — 다섯 번쯤에서 멈춘다
다시 보내도 되는 요청인지 먼저 본다
사람에게 보여 준다 — 몇 번째, 언제 다시
끝내 실패하면 다시 시도 단추를 준다
  1. 간격 두 배씩1 · 2 · 4 · 8초
  2. 흔들기 무작위 섞기여러 기기가 같이 몰리지 않게
  3. 최대 횟수 다섯 번쯤그 뒤엔 사람에게
  4. 다시 보내도 되나 먼저 확인결제는 안 된다
  5. 보여 주기 몇 번째 · 언제말없이 돌리지 않는다
  6. 포기 단추사람이 정하게

다시 보내기 전에 꼭 물어볼 것이 있습니다 — 이 요청을 두 번 보내도 되나입니다. 조회(GET)는 괜찮지만 결제나 전송은 두 번 가면 사고입니다. 그래서 그런 요청에는 멱등 키를 붙여, 서버가 같은 키를 두 번 받으면 한 번만 처리하게 해 둡니다.
흔들기가 없는 백오프도 문제가 됩니다 — 수천 대가 동시에 끊겼다면 모두 정확히 1초 뒤에 다시 보내고, 그 순간 서버가 또 넘어집니다. 간격에 무작위를 조금 섞으면 그 몰림이 흩어집니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 지수 백오프 + 흔들기를 기본으로
  • 다시 보내도 되는 요청인지 먼저 보기
  • 도는 동안 몇 번째인지 보여 주기

이럴 때는 안 쓴다

  • 쉬지 않고 다시 보내기 — 서버를 더 눕힌다
  • 결제·전송을 멱등 키 없이 다시 보내기
  • 끝없이 다시 보내기 — 다섯 번쯤에서 멈춘다
  • 말없이 돌리기 — 사용자는 멈춘 줄 안다

대신 이걸 — 연결이 아예 없으면 오프라인, 실패 화면은 에러 상태, 기다림 표시는 스피너, 문구는 오류 문구.

8 최소 코드와 규칙이 재시도의 계약서

간격을 두 배씩 늘리고 무작위를 조금 섞습니다. 다섯 번이면 충분합니다.

async function withRetry(fn, { max = 5 } = {}) {
  for (let n = 0; ; n++) {
    try { return await fn(); }
    catch (e) {
      if (n >= max || !canRetry(e)) throw e;
      const base = Math.min(8000, 1000 * 2 ** n);
      const jitter = base * (0.5 + Math.random() * 0.5);  // 흔들기
      show(`${n + 2}번째 시도 — ${Math.round(jitter / 1000)}초 뒤`);
      await sleep(jitter);
    }
  }
}

9 서버 쪽으로 치면백엔드 감각으로 번역

Retry-After서버가 언제 다시 오라고 알려 주면 화면이 추측할 필요가 없습니다.
멱등 키같은 키의 요청을 두 번 받으면 처음 결과를 그대로 돌려줍니다.
어떤 오류인지429(너무 잦음)와 400(잘못된 요청)은 전혀 다른 대응이 필요합니다.
서킷 브레이커연속 실패가 쌓이면 잠시 요청 자체를 끊어 서버가 일어날 틈을 줍니다.
