설정 화면

Settings

설정 화면은 사용자가 값을 바꾸는 화면입니다. 바꾼 값을 바로 적용할지, 저장 버튼을 누르게 할지를 먼저 정해야 부품 선택과 나머지 설계를 그에 맞춰 정할 수 있습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

스위치는 바로 적용, 체크박스는 저장 버튼으로 짝을 짓는 약속은 셋 모두 같습니다. 위 체크로 두 방식을 바꿔 보세요.
저장 버튼 방식에서는 바꾼 줄에 '바뀜'이 붙고, 저장을 누르기 전에는 적용되지 않습니다. 반면 바로 적용 방식에는 저장 버튼이 아예 없어야 합니다. 저장 버튼이 있는데 누르지 않아도 적용된다면 사용자는 무엇이 저장됐는지 알 수 없기 때문입니다.

2 이름같은 것을 부르는 여러 이름

한국어설정, 환경설정, 기본 설정, 계정 설정
영어settings, preferences, options, account settings
같이 쓰는 말맥·iOS에서는 Preferences·Settings를, 윈도에서는 Options를 많이 씁니다. 되돌릴 수 없는 항목을 따로 모아 둔 자리를 위험 구역(danger zone)이라 하고, 값을 바꾼 뒤 아직 저장하지 않은 상태를 더티(dirty)라고 합니다.
자주 잘못 부르는 이름프로필 — 프로필은 남에게 보이는 정보이고, 설정은 내 쪽에서 앱이 동작하는 방식을 바꿉니다. 둘을 섞어 두면 지금 바꾸는 값이 어느 쪽인지 헷갈립니다.
관리자 설정 — 조직 전체 설정과 개인 설정은 서로 다른 화면입니다. 같은 자리에 두면 권한이 없는 사람이 조직 설정을 건드리는 사고가 납니다.
폼 — 폼은 한 번 보내면 끝나지만, 설정 화면에는 사용자가 값을 계속 고치러 돌아옵니다.

설정 화면을 한 줄로 정리하면 — 저장 버튼이 있으면 체크박스를, 없으면 스위치를 씁니다. 부품과 저장 방식이 어긋나면 사용자는 값이 저장됐는지 끝내 확신할 수 없습니다.

5 해부도부분마다 붙은 이름

스위치 = 바로 적용 · 체크박스 = 저장 버튼
설정
새 정산 알림정산이 들어오면
묶음 이름 — 알림 · 화면 · 계정
줄마다 한 줄 설명 — 켜면 무슨 일이 나는가
스무 줄이 넘으면 검색이 묶음보다 빠르다
위험 구역은 맨 아래 따로 — 빨간 테두리로 가둔다
  1. 약속 스위치 ↔ 체크박스바로 적용할지, 저장 버튼을 쓸지를 가장 먼저 정합니다
  2. 줄 이름 + 한 줄 설명켰을 때 무슨 일이 일어나는지 적습니다
  3. 묶음 알림 · 화면 · 계정성격이 같은 것끼리 모아 이름을 붙입니다
  4. 설명 작게, 늘 보이게작은 글씨로 늘 보이게 둡니다. 툴팁에 숨기면 폰에서 볼 수 없습니다
  5. 검색 스무 줄 넘으면설정이 스무 줄을 넘으면 묶음을 잘 짜 두어도 검색으로 찾는 편이 더 빠릅니다
  6. 위험 구역 맨 아래, 따로되돌릴 수 없는 항목만 모으고, 누르면 위험한 동작의 확인 흐름으로 이어집니다

가장 흔한 사고는 두 방식을 섞는 것입니다. 예를 들어 스위치를 늘어놓고 아래에 저장 버튼을 두면, 사용자는 스위치를 넘긴 뒤 이미 저장됐다고 믿은 채 화면을 나가지만 실제로는 아무것도 바뀌지 않습니다. 반대로 바로 적용 방식인데 저장 버튼이 있으면, 버튼을 눌러도 아무 일이 일어나지 않아 버튼이 고장 난 것처럼 보입니다. 그러니 둘 중 하나를 정하고 화면 전체가 그 방식 하나를 따르게 하면 됩니다.

6 쓸 때 / 안 쓸 때

설정 화면을 쓰는 경우

  • 사용자가 값을 계속 고치러 돌아오는 화면일 때
  • 켜고 끄는 항목이 많을 때. 성격별로 묶고 줄마다 설명을 답니다
  • 되돌릴 수 없는 항목이 있을 때. 그 항목은 위험 구역에 따로 모읍니다

설정 화면을 쓰지 않는 경우

  • 스위치와 저장 버튼을 함께 둘 때. 가장 흔한 사고입니다
  • 설명 없이 이름만 적을 때. '고급 모드'처럼 이름만으로는 무엇이 바뀌는지 알 수 없습니다
  • 기본값 없이 비워 둘 때. 기본값을 정해 무엇이 보통인지 알려 줍니다
  • 계정 삭제를 다른 항목들 사이에 끼워 둘 때

설정 화면 대신 다른 것을 써야 하는 경우 — 한 번 보내고 끝이면 폼 설계, 켜고 끄는 부품 자체는 스위치·체크박스, 지우는 흐름은 위험한 동작.

8 최소 마크업과 키보드구현할 때 지킬 최소 규칙

묶음은 <fieldset>으로, 바로 적용되는 항목은 role="switch"로 적습니다.

<fieldset>
  <legend>알림</legend>

  <!-- 바로 적용 -->
  <div class="row">
    <span id="n1">새 정산 알림</span>
    <p id="n1d">정산이 들어오면 알려 줍니다</p>
    <button role="switch" aria-checked="true"
            aria-labelledby="n1" aria-describedby="n1d"></button>
  </div>
</fieldset>

<p role="status">저장했습니다</p>

// 저장 버튼 방식이면 나가기 전에 물어본다
window.addEventListener('beforeunload', e => { if (dirty) e.preventDefault(); });
키와 동작그때 일어나야 하는 일
role="switch" + aria-checked스크린 리더가 '켜짐/꺼짐'으로 읽습니다. 체크박스는 '선택됨'으로 읽히므로 전달되는 뜻이 다릅니다
aria-describedby줄 밑의 설명을 항목과 연결합니다. 연결하지 않으면 이름만 읽힙니다
<fieldset><legend>'알림 묶음, 새 정산 알림 스위치'처럼 묶음 이름이 함께 읽힙니다
role="status"바로 적용 방식이면 저장됐다는 알림이 필요합니다. 색만 바뀌면 화면을 보지 않는 사람은 알 수 없습니다
저장 전 이탈beforeunload로 묻습니다. 다만 뒤로가기에는 통하지 않을 수 있어서 직접 확인 창을 띄웁니다
위험 구역Tab으로 쉽게 닿는 자리에 두지 않고 맨 아래에 둡니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

바로 적용은 요청이 잦다스위치를 넘길 때마다 요청이 가므로, 요청을 묶어 보내거나 짧게 디바운스합니다.
실패했을 때 되돌린다요청이 실패했는데 스위치가 켜진 채로 남으면 화면이 실제와 다른 상태를 보여 주게 됩니다. 그래서 낙관적 UI처럼 실패하면 원래대로 되돌리는 처리가 필요합니다.
기본값은 서버가 쥔다'아직 안 고른 것'과 '꺼 둔 것'은 다릅니다. null과 false로 둘을 구별해 두면 나중에 기본값을 바꿀 때 사용자가 직접 끈 값은 건드리지 않을 수 있습니다.
설정이 늘어난다설정이 늘 때마다 테이블에 칸을 하나씩 더하면 저장 구조가 금방 넓어집니다. 그래서 키-값 형태로 저장하는 편이 오래 버팁니다.
기기별 설정다크 모드처럼 기기마다 달라야 하는 설정은 계정이 아니라 기기에 저장합니다.
