낙관적 UI

Optimistic UI

서버 응답을 기다리지 않고 먼저 화면을 바꾸는 방식. 거의 성공할 일에 쓰고, 실패하면 되돌립니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

'서버를 느리게'를 켜고 별을 눌러 보세요. 느낌이 똑같습니다 — 기다림이 사용자 쪽에서 사라졌기 때문입니다. 세 번째 줄(권한 없음)은 서버가 거절해서 별이 원래대로 되돌아가고 이유를 알려 줍니다. 이 되돌림을 감당할 수 있는 일에만 쓸 수 있습니다.

2 이름부르는 말이 여러 개다

한국어낙관적 UI, 낙관적 업데이트, 선반영
영어optimistic UI, optimistic update
같이 쓰는 말먼저 바꾼 화면을 낙관적 상태, 서버가 거절해 되돌리는 것을 롤백이라 합니다. 반대말은 비관적(pessimistic) — 응답을 받고 나서 바꾸는 쪽입니다.
자주 잘못 부름캐싱 — 캐시는 읽기를 빠르게 하고, 낙관적 UI는 쓰기를 빠르게 보이게 합니다.
즉시 반영 — 통하기는 하지만 되돌림이 핵심이라는 점이 빠집니다.
로컬 상태 — 그냥 화면 상태를 바꾸는 것과 달리, 낙관적 UI는 서버에 보낸 뒤 결과를 맞춰야 합니다.

3 가르는 기준형제들과 비교하는 네 축

겹쳐 뜨는 부품들은 모양으로는 구별이 안 됩니다. 이 네 가지만 물어보면 갈립니다.

끝나는 때를 아나들어올 자리를 잡나사용자가 기다리나화면이 덜컥거리나
스피너모른다안 잡는다기다린다덜컥거린다
스켈레톤모른다잡는다기다린다안 덜컥거린다
프로그레스 바안다잡기도 한다기다린다안 덜컥거린다
낙관적 UI해당 없음잡는다안 기다린다안 덜컥거린다

한 줄로 — 낙관적 UI는 기다림을 없애는 쪽입니다. 그래서 '어떻게 보여 줄까'가 아니라 '실패하면 어떻게 되돌릴까'가 설계의 전부입니다.

4 상태그림 한 장으로는 못 배운다

5 해부도부분 이름이 제일 안 알려진 지식

누른 직후 ★ 보냄
서버가 거절 ★ 되돌림
권한이 없어 되돌렸습니다 다시 시도
  1. 먼저 바뀐 화면 optimistic state서버는 아직 모른다. 사용자만 결과를 보고 있다
  2. 보류 표시 pending아주 약하게. 눈에 띄면 결국 기다리게 되어 쓰는 뜻이 없어진다
  3. 되돌아간 값 rollback누르기 전 값을 기억해 뒀다가 그대로 되돌린다
  4. 되돌림 신호 rollback cue조용히 바꾸면 사용자는 자기가 잘못 본 줄 안다. 짧게 흔들거나 색으로 알린다
  5. 이유 알림 reason왜 안 됐는지와 다시 할 길을 같이 준다. 보통 토스트로

그림에 안 보이는 가장 중요한 것이 기억해 둔 원래 값입니다. 이게 없으면 되돌릴 수 없고, 되돌릴 수 없으면 낙관적 UI를 쓸 수 없습니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 거의 항상 성공하는 일 — 좋아요, 즐겨찾기, 체크, 순서 바꾸기
  • 되돌리는 비용이 싼 일 — 값 하나만 되돌리면 되는 것
  • 자주 반복하는 일 — 누를 때마다 기다리면 금세 지칩니다

이럴 때는 안 쓴다

  • 실패가 잦은 일 — 되돌림이 자주 보이면 화면을 못 믿게 됩니다
  • 돈이 오가는 일 — 결제·이체는 서버가 확정한 뒤 보여 줍니다
  • 되돌리기 어려운 일 — 메일 발송, 파일 삭제처럼 바깥에 영향이 남는 것
  • 결과가 다른 화면에도 퍼지는 일 — 되돌릴 곳이 여러 군데면 금세 엉킵니다

대신 이걸 — 확정을 기다려야 하면 스피너나 프로그레스 바, 되돌릴 틈을 주려면 되돌리기 토스트, 실패를 알릴 때는 에러 상태.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 키보드이 부품의 계약서

순서가 전부입니다 — 먼저 바꾸고, 보내고, 거절당하면 되돌린다. 되돌릴 값을 먼저 챙기는 것이 첫 줄입니다.

const before = state.starred;       // 1) 되돌릴 값을 챙긴다
setStarred(!before);                  // 2) 화면을 먼저 바꾼다

try {
  await api.star(id, !before);       // 3) 서버에 보낸다
} catch (e) {
  setStarred(before);                 // 4) 거절당하면 되돌린다
  toast('권한이 없어 되돌렸습니다', { retry });   // 5) 이유를 알린다
}

// 빠르게 여러 번 누르면 응답이 뒤섞인다 — 마지막 것만 반영한다
const seq = ++latest;
if (seq !== latest) return;
키일어나야 하는 일
누름바로 바뀐다. 포커스는 누른 자리에 그대로 둔다
스크린 리더바뀐 상태를 aria-pressed로 알린다. 되돌릴 때는 라이브 리전으로 이유를 읽어 준다
되돌릴 때소리 없이 되돌리지 않는다. 눈을 떼고 있던 사용자는 바뀐 줄도 모른다
빠른 연타마지막 눌림만 반영한다. 응답이 뒤섞이면 화면과 서버가 어긋난다
오프라인보류함에 쌓아 두고, 연결되면 보낸다. 쌓인 것이 있다는 표시를 남긴다

9 서버 쪽으로 치면백엔드 감각으로 번역

낙관적 UI = 낙관적 잠금과 같은 생각먼저 진행하고 충돌하면 되돌립니다. DB 의 optimistic locking 과 이름도 생각도 같습니다. 충돌이 드물 때만 이득이라는 조건도 같습니다.
되돌림 = 보상 트랜잭션이미 보여 준 것을 물리는 일입니다. 사가(saga) 패턴의 보상 단계와 같아서, 보상할 수 없는 일에는 쓸 수 없습니다.
연타 = 순서 뒤섞임요청 두 개의 응답이 거꾸로 올 수 있습니다. 일련번호를 붙여 마지막 것만 반영합니다. 분산 시스템의 last-write-wins 와 같은 문제입니다.
멱등성같은 요청이 두 번 가도 결과가 같아야 재시도를 마음 놓고 합니다. 멱등 키를 붙이면 되돌림도 단순해집니다.
오프라인 = 아웃박스보내지 못한 변경을 쌓아 두는 큐입니다. 큐가 길어질수록 되돌림이 어려워지니 상한을 둡니다.
