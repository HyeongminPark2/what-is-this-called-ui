권한 요청

Permission request

OS 권한 창은 한 번만 띄울 수 있습니다. 사용자가 거절하면 앱이 그 창을 다시 띄울 방법이 없습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

앞선 설명 띄우기를 켜면 OS 창을 띄우기 전에 우리 화면에서 먼저 묻습니다. 여기서 '나중에'를 고르면 OS 창은 아직 쓰지 않은 채로 남기 때문에, 다음에 다시 물어볼 수 있습니다.
반대로 앞선 설명을 끄고 OS 창에서 거절한 뒤 다시 눌러 보면 아무 일도 일어나지 않습니다. 권한 요청 화면은 결국 이 한 번의 OS 창을 언제 쓸지 정하는 일입니다.

2 이름같은 것을 부르는 여러 이름

한국어권한 요청, 접근 허용, 퍼미션
영어permission request, permission prompt, pre-permission
같이 쓰는 말OS 창을 띄우기 전에 우리 화면에서 먼저 묻는 것을 프리프롬프트(pre-prompt)·프라이밍(priming)이라고 합니다. 웹에서는 navigator.permissions.query()로 지금 권한 상태를 확인할 수 있고, 돌아오는 값은 granted·denied·prompt 세 가지입니다. 클릭 같은 사용자 동작 없이는 권한 창을 띄우지 못하게 막는 규칙을 사용자 제스처 요구라고 합니다.
자주 잘못 부르는 이름약관 동의 — 약관 동의는 법적인 동의이고, 권한은 OS가 관리하는 기기 기능을 쓰도록 허락받는 것이라 전혀 다릅니다.
로그인 — 누구인지 확인하는 일과 기기 기능을 쓰는 일은 서로 다릅니다.
설정 — 앱의 설정에서 기능을 끌 수는 있지만, 한 번 거절한 권한을 다시 켜는 일은 OS 설정 앱에서만 됩니다.

권한 요청을 한 줄로 정리하면 — 권한은 사용자가 그 기능을 쓰려는 순간에, 왜 필요한지 먼저 말한 뒤 묻습니다. 첫 화면에서 권한 다섯 개를 한꺼번에 묻는 것이 가장 나쁜 방식입니다.

4 권한을 묻는 흐름한 번뿐인 OS 창을 언제 쓰는가

5 해부도부분마다 붙은 이름

첫 화면이 아니라 기능을 쓰려는 순간에 물음
알림을 보내도 될까요?정산이 들어온 순간에만 보냅니다
앞선 설명에서 거절하면 OS 창은 아껴 둠
OS 창은 한 번만 뜸
거절당하면 설정으로 가는 길을 둠
권한 없이도 앱을 쓸 수 있어야 함
  1. 묻는 시점 쓰려는 순간첫 화면이 아니라 사용자가 그 기능을 누를 때 묻습니다
  2. 앞선 설명 우리 화면권한이 왜 필요한지 우리 화면에서 우리 말로 적습니다
  3. 나중에 버튼 OS 창을 아껴 둠여기서 거절하면 OS 창을 쓰지 않고 아껴 둡니다
  4. OS 창 한 번뿐문구도 모양도 바꿀 수 없고, 한 번 거절되면 다시 띄울 수 없습니다
  5. 거절된 뒤 안내 설정 앱으로OS 창을 다시 띄울 수 없으니 설정으로 가는 길만 알려 줄 수 있습니다
  6. 권한이 없을 때 그래도 쓸 수 있게권한이 없어도 그 기능만 빠지고 앱은 쓸 수 있게 만듭니다

앞선 설명은 사용자에게 한 번 더 묻는 일이라 번거로워 보이지만, 실제로는 권한을 받을 기회를 늘립니다. OS 창은 한 번만 띄울 수 있어서, 사용자가 그 창에서 거절하면 그 기능을 다시 요청할 기회가 사라집니다. 반면 앞선 설명에서 '나중에'를 고른 사람에게는 OS 창을 아직 띄우지 않았으므로, 그 기능이 정말 필요해진 순간에 다시 물어볼 수 있습니다. OS 창을 바로 띄웠다가 거절당하면 나중에 사용자가 마음을 바꿔도 앱이 할 수 있는 일이 없고, 설정 앱으로 가는 길을 알려 주는 것밖에 남지 않습니다.

6 쓸 때 / 안 쓸 때

권한을 물어도 되는 때

  • 사용자가 그 기능을 쓰려는 순간일 때
  • 묻기 전에 왜 필요한지 한 줄로 설명할 수 있을 때
  • 거절당해도 나머지 기능은 쓸 수 있게 만들 수 있을 때

권한을 이렇게 물으면 안 되는 경우

  • 첫 화면에서 권한을 몰아서 물을 때. 대부분 거절당합니다
  • 앞선 설명 없이 바로 OS 창을 띄울 때. 한 번뿐인 기회를 잃습니다
  • 거절한 사람에게 계속 다시 요청할 때
  • 권한이 없으면 앱을 아예 못 쓰게 막을 때

상황에 따라 함께 볼 항목 — 처음 설정하는 흐름에서 묻는다면 온보딩 안에 앞선 설명을 넣습니다. 권한이 꺼져 있다고 알릴 때는 빈 상태를, 권한 없이 설명만 하면 될 때는 팝오버를 씁니다.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 코드와 규칙구현할 때 지킬 최소 규칙

먼저 지금 권한 상태를 확인하고, 앞선 설명을 거친 뒤에만 OS 창을 띄웁니다.

// 사용자가 이미 결정했을 수 있으니 지금 상태부터 확인한다
const st = (await navigator.permissions.query({ name: 'notifications' })).state;

if (st === 'denied') {
  showSettingsHint();          // OS 창은 다시 못 띄우니 설정으로 가는 길만 알려 준다
} else if (st === 'granted') {
  subscribe();
} else {
  const wants = await showPrePrompt();   // 우리 화면에서 먼저
  if (!wants) return;                    // OS 창은 아직 안 썼다
  const res = await Notification.requestPermission();
  if (res === 'granted') subscribe();
  else showSettingsHint();
}
지킬 규칙지키는 방법
사용자 동작 안에서만 부르기클릭 핸들러 밖에서 부르면 브라우저가 막습니다. 그래서 페이지를 불러오자마자 띄울 수는 없습니다
permissions.querygranted·denied·prompt 가운데 어느 상태인지 묻기 전에 확인합니다
앞선 설명은 다이얼로그로 만들기초점을 다이얼로그 안에 가두고 Esc로 닫히게 합니다. 기본 선택은 '나중에'로 둡니다
OS 창은 꾸밀 수 없음문구·버튼·순서를 모두 OS가 정합니다. 앱이 손댈 수 있는 것은 앞선 설명뿐입니다
거절된 뒤 설정 경로 안내하기'설정 › 알림'처럼 찾아갈 경로를 적어 줍니다. 브라우저는 권한 설정 화면을 자동으로 열어 주지 못합니다
role="status"권한 상태가 바뀌면 알립니다. 아이콘만 바뀌면 화면을 보지 않는 사람은 알 수 없습니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

서버는 권한 상태를 알 수 없음허용 여부는 기기에만 기록됩니다. 서버는 구독 정보가 들어왔는지를 보고 짐작할 수 있을 뿐입니다.
끊긴 구독 지우기사용자가 나중에 기기 설정에서 알림을 끄면 서버에는 아무 신호도 오지 않고 발송만 조용히 실패합니다. 그래서 발송 실패 응답을 보고 그 구독을 지워야 합니다.
알림 대신 쓸 전달 수단 두기알림을 받지 않는 사람에게는 메일이나 화면 안 표시로 같은 정보를 전합니다.
앞선 설명의 허용률 기록하기앞선 설명을 거친 사용자와 거치지 않은 사용자의 허용률 차이를 재 보면, 앞선 설명이 실제로 효과가 있는지 확인할 수 있습니다.

플랫폼 차이 때문에 자주 생기는 문제 — "첫 화면에서 권한을 다 받아 놓죠"라는 결정은 나중에 가장 큰 손실로 돌아옵니다. 첫 화면에서 한꺼번에 물으면 다섯 개 가운데 네 개는 거절당하고, 나중에 그 기능이 필요해져도 되돌릴 방법이 없습니다. 권한을 쓰려는 순간에 하나씩 묻도록 바꾸기만 해도 허용률이 크게 달라지고, 그 차이는 직접 재서 보여 줄 수 있습니다.
