권한 요청

Permission request

OS 권한 창은 한 번뿐입니다. 거절당하면 앱은 다시 띄울 수 없습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

앞선 설명 띄우기를 켜면 우리 화면에서 먼저 묻습니다. 여기서 '나중에'를 고르면 OS 창은 아직 쓰지 않은 채로 남아, 다음에 다시 물어볼 수 있습니다.
끄고 거절해 본 뒤 다시 눌러 보세요 — 아무 일도 일어나지 않습니다. 그 한 번을 아끼는 것이 이 화면의 전부입니다.

2 이름부르는 말이 여러 개다

한국어권한 요청, 접근 허용, 퍼미션
영어permission request, permission prompt, pre-permission
같이 쓰는 말OS 창을 띄우기 전에 우리 화면에서 먼저 묻는 것을 프리프롬프트(pre-prompt)·프라이밍(priming)이라 합니다. 웹에서는 navigator.permissions.query()로 지금 상태를 물어볼 수 있고, 값은 granted·denied·prompt 셋입니다. 사용자의 동작 없이 띄우지 못하게 막는 것을 사용자 제스처 요구라 합니다.
자주 잘못 부름약관 동의 — 법적 동의이고, 권한은 OS 가 쥔 기능입니다. 전혀 다릅니다.
로그인 — 누구인지 확인하는 것과 기기 기능을 쓰는 것은 다릅니다.
설정 — 설정에서 끌 수는 있지만, 켜는 건 OS 설정 앱에서만 됩니다.

4 흐름한 번뿐인 기회를 어떻게 쓰나

5 해부도부분 이름이 제일 안 알려진 지식

쓰려는 바로 그 순간에 — 첫 화면에서가 아니라
알림을 보내도 될까요?정산이 들어온 순간에만 보냅니다
앞선 설명 — 여기서 거절해도 OS 창은 안 쓴다
OS 창 — 한 번뿐이다
거절당하면 설정으로 가는 길을 둔다
권한 없이도 쓸 수 있는 길이 있어야 한다
  1. 묻는 때 쓰려는 순간첫 화면이 아니라 그 기능을 누를 때
  2. 앞선 설명 우리 화면왜 필요한지를 우리 말로 적는다
  3. 아낀 기회 나중에여기서 거절해도 OS 창은 안 쓴다
  4. OS 창 한 번뿐문구도 모양도 못 바꾼다. 이게 전부다
  5. 거절 뒤 설정으로다시 못 띄운다. 길만 알려 줄 수 있다
  6. 없을 때 쓸 수 있게권한이 없어도 그 기능만 빠지게 만든다

앞선 설명이 더 묻는 일이라 나빠 보이지만 반대입니다. OS 창은 한 번뿐이라 '지금 쓸지 말지'를 판돈으로 겁니다. 앞선 설명에서 '나중에'를 고른 사람은 OS 창을 아직 안 쓴 사람이라, 그 기능이 정말 필요해진 순간에 다시 물어볼 수 있습니다. 반대로 바로 띄웠다 거절당하면, 나중에 그 사람이 마음을 바꿔도 우리는 아무것도 할 수 없습니다 — 설정 앱으로 가는 길을 알려 주는 것이 전부입니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 그 기능을 쓰려는 순간에 묻기
  • 묻기 전에 왜 필요한지 한 줄
  • 거절당해도 나머지는 쓰이게 만들기

이럴 때는 안 쓴다

  • 첫 화면에서 몰아 묻기 — 다 거절당한다
  • 앞선 설명 없이 바로 OS 창 — 한 번뿐인 기회를 버린다
  • 거절한 사람에게 계속 조르기
  • 권한이 없으면 앱을 못 쓰게 막기

대신 이걸 — 첫 설정 흐름이면 온보딩 안에서, 꺼져 있다고 알릴 때는 빈 상태, 설명만이면 팝오버.

8 최소 코드와 규칙이 요청의 계약서

먼저 상태를 물어보고, 앞선 설명을 거친 뒤에만 OS 창을 씁니다.

// 지금 상태부터 물어본다 — 이미 결정났을 수 있다
const st = (await navigator.permissions.query({ name: 'notifications' })).state;

if (st === 'denied') {
  showSettingsHint();          // 다시 못 띄운다. 길만 알려 준다
} else if (st === 'granted') {
  subscribe();
} else {
  const wants = await showPrePrompt();   // 우리 화면에서 먼저
  if (!wants) return;                    // OS 창은 아직 안 썼다
  const res = await Notification.requestPermission();
  if (res === 'granted') subscribe();
  else showSettingsHint();
}
키일어나야 하는 일
사용자 동작 안에서만클릭 핸들러 밖에서 부르면 브라우저가 막는다. 페이지 로드 직후는 안 된다
permissions.querygranted·denied·prompt. 묻기 전에 확인한다
앞선 설명은 다이얼로그초점을 가두고 Esc로 닫히게. '나중에'가 기본
OS 창은 못 꾸민다문구·버튼·순서 전부 OS 것이다. 우리가 할 수 있는 건 앞선 설명뿐
거절 뒤 안내'설정 › 알림'처럼 경로를 적어 준다. 브라우저는 자동으로 못 열어 준다

9 서버 쪽으로 치면백엔드 감각으로 번역

서버는 권한을 모른다허용 여부는 기기에만 있습니다. 서버는 구독 정보가 들어왔는지로만 짐작합니다.
구독은 끊길 수 있다사용자가 나중에 설정에서 끄면 조용히 실패합니다. 발송 실패를 보고 구독을 지워야 합니다.
대체 길을 둔다알림을 못 보내는 사람에게는 메일이나 화면 안 표시로 같은 정보를 줍니다.
허용률을 기록한다앞선 설명을 거친 쪽과 아닌 쪽의 허용률 차이를 재 보면 이 설계가 값을 하는지 알 수 있습니다.
