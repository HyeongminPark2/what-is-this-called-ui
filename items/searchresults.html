검색 결과 화면

Search results page

검색은 찾는 일이고 결과 화면은 고르는 일입니다. 들어갔다 돌아오는 왕복이 설계의 전부입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

결과에서 한 건을 눌러 들어갔다가 ← 뒤로를 눌러 보세요.
둘 다 켜 두면 질의 · 필터 · 굴린 자리가 그대로 살아납니다. 끄면 빈 검색 화면으로 돌아가고 처음부터 다시 찾아야 합니다 — 목록 화면에서 가장 자주 나오는 민원입니다.

2 이름부르는 말이 여러 개다

한국어검색 결과, 결과 목록, 목록 화면
영어search results page, SERP, results listing
같이 쓰는 말검색 엔진 쪽에서는 SERP(search engine results page)라 부릅니다. 결과에서 하나를 눌러 들어갔다 돌아오는 것을 왕복(pogo-sticking), 돌아왔을 때 상태를 되살리는 것을 상태 복원(scroll restoration·state restoration)이라 합니다. 맞은 글자를 굵게 보여 주는 것은 하이라이팅·스니펫입니다.
자주 잘못 부름검색 — 검색은 입력칸과 응답 처리, 이쪽은 결과 화면 전체입니다.
필터 — 필터는 이 화면의 한 부분입니다.
목록 — 그냥 목록은 질의가 없습니다. 결과 화면은 무엇으로 찾았는지를 늘 지고 있습니다.

4 상태왕복이 되는가

5 해부도부분 이름이 제일 안 알려진 지식

🔍모란
‘모란’ · 승인됨 · 6건 — 무엇으로 찾았는지 다시 적는다
?q=모란&f=승인됨&page=2 — 주소에 담는다
굴린 자리를 기억했다 돌아올 때 되살린다
0건이면 조건을 지울 길과 다른 질의를 준다
돌아왔더니 빈 화면 — 가장 흔한 민원
  1. 질의 상자 친 글자 그대로결과 화면에도 남아 있어야 고쳐 찾는다
  2. 요약 줄 ‘모란’ · 승인됨 · 6건무엇으로 몇 건인지. 0건일 때 특히 중요하다
  3. 주소 ?q=&f=&page=공유 · 새로고침 · 뒤로가기가 한꺼번에 해결된다
  4. 굴린 자리 복원돌아왔을 때 보던 줄에서 이어 본다
  5. 0건의 길 넓히기 · 지우기막다른 길을 만들지 않는다
  6. 안 담았을 때 빈 화면처음부터 다시. 가장 흔한 민원

굴린 자리 복원은 생각보다 까다롭습니다. 돌아왔을 때 목록이 아직 안 받아졌으면 복원할 자리가 없고, 그때 억지로 굴려 놓으면 데이터가 들어오면서 다시 튑니다. 그래서 받고 그린 다음에 복원해야 하고, 무한 스크롤이면 몇 쪽까지 받았는지도 함께 기억해야 합니다. 이것이 무한 스크롤보다 페이지네이션이 편한 이유 가운데 하나입니다 — 쪽 번호 하나면 자리가 정해집니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 찾은 뒤 골라 들어가는 화면 — 목록·상품·문서
  • 조건이 여럿 붙는 목록 — 주소에 담아 공유되게
  • 건수가 많아 쪽을 넘기는 화면

이럴 때는 안 쓴다

  • 질의를 주소에 안 담기 — 공유도 새로고침도 안 된다
  • 0건에서 막다른 길 만들기
  • 돌아왔을 때 맨 위로 보내기
  • 친 글자를 결과 화면에서 지우기 — 고쳐 찾을 수가 없다

대신 이걸 — 입력칸과 응답 처리는 검색, 조건 고르기는 필터와 패싯, 줄이 아주 많으면 가상 스크롤.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 키보드이 화면의 계약서

상태를 주소에 담고, 돌아올 때 그린 뒤에 자리를 되살립니다.

<form role="search" action="/search">
  <label for="q" class="sr-only">가맹점 검색</label>
  <input id="q" name="q" type="search" value="모란">
</form>

<p role="status">‘모란’ 검색 결과 6건</p>
<ol>…</ol>

// 조건이 바뀌면 쌓지 말고 갈아끼운다
history.replaceState(null, '', `?q=${q}&f=${f}`);

// 상세로 갈 때 굴린 자리를 적어 둔다
sessionStorage.setItem('pos', String(list.scrollTop));

// 돌아와서는 "그린 뒤에" 되살린다
await renderResults();
list.scrollTop = +sessionStorage.getItem('pos') || 0;
키일어나야 하는 일
role="search"검색 영역을 구역으로 알린다. 스크린 리더가 바로 건너뛴다
role="status"'6건'. 결과만 바뀌면 눈으로 안 보는 사람은 모른다
<ol>로 적는다순서가 뜻을 지닌다. '6개 중 2번째'로 읽힌다
replaceState와 pushState조건이 바뀔 뿐이면 갈아끼운다 — 시스템 백
scrollRestoration브라우저 기본 복원과 직접 복원이 싸울 수 있다. 하나만 쓴다
초점상세에서 돌아오면 눌렀던 줄로 초점을 되돌린다. 안 그러면 처음부터 Tab 한다

9 서버 쪽으로 치면백엔드 감각으로 번역

조건을 주소에서 읽는다서버가 ?q=·?page=를 그대로 받아 그리면 공유한 링크가 같은 화면이 됩니다.
허용 목록으로sort·f 값을 그대로 질의에 넣지 않습니다 — 데이터 테이블과 같은 주입 문제입니다.
같은 값의 순서순서가 요청마다 흔들리면 쪽을 넘길 때 같은 줄이 두 번 나옵니다. ID 를 2차 정렬로 붙입니다.
건수는 비싸다COUNT(*)가 큰 표에서는 느립니다. '100+ 건'으로 적거나 커서 방식으로 바꿉니다.
빈 질의?q=가 비었을 때 전체를 돌려줄지 아무것도 안 줄지 정해 둡니다. 안 정하면 전체 조회가 터집니다.
