스켈레톤

Skeleton · Placeholder

들어올 내용의 모양대로 미리 자리를 잡아 두는 회색 뼈대. 기다림이 짧게 느껴지고, 내용이 들어올 때 화면이 덜컥거리지 않습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

두 버튼을 번갈아 눌러 보세요. 아래에 화면이 몇 px 흔들렸는지 적힙니다. 스켈레톤은 0px, 스피너는 수십 px입니다. 이 흔들림을 레이아웃 시프트라 부르고, 스켈레톤이 존재하는 이유가 바로 이걸 없애는 것입니다.

2 이름부르는 말이 여러 개다

한국어스켈레톤, 스켈레톤 화면, 뼈대 화면
영어skeleton, skeleton screen, placeholder, ghost element
같이 쓰는 말지나가는 빛을 시머(shimmer), 회색 덩어리 하나하나를 플레이스홀더라 합니다. 모양이 거의 똑같으면 고스트라고도 합니다.
자주 잘못 부름로딩 — 스피너와 뭉뚱그려 부르면 '자리를 잡느냐'라는 결정적 차이가 사라집니다.
와이어프레임 — 와이어프레임은 설계 단계의 그림이고, 스켈레톤은 실제로 돌아가는 화면의 한 상태입니다.
더미 데이터 — 가짜 글자를 넣는 것과는 다릅니다. 스켈레톤에는 글자를 넣지 않습니다.

3 가르는 기준형제들과 비교하는 네 축

기다리는 화면은 모양이 다 비슷합니다. 이 네 가지만 물어보면 갈립니다.

끝나는 때를 아나들어올 자리를 잡나사용자가 기다리나화면이 덜컥거리나
스피너모른다안 잡는다기다린다덜컥거린다
스켈레톤모른다잡는다기다린다안 덜컥거린다
프로그레스 바안다잡기도 한다기다린다안 덜컥거린다
낙관적 UI해당 없음잡는다안 기다린다안 덜컥거린다

한 줄로 — 스켈레톤은 들어올 모양을 알 때만 쓸 수 있습니다. 모양을 모르면서 아무 뼈대나 깔면 내용이 들어올 때 결국 덜컥거립니다.

4 상태그림 한 장으로는 못 배운다

5 해부도부분 이름이 제일 안 알려진 지식

  1. 줄 틀 row · container실제 줄과 높이가 같아야 한다. 여기가 어긋나면 스켈레톤을 쓴 보람이 없다
  2. 동그란 자리 avatar placeholder아바타가 들어올 자리. 크기와 모양까지 맞춘다
  3. 긴 글줄 자리 line placeholder제목이 들어올 자리. 길이를 조금씩 다르게 해야 진짜처럼 보인다
  4. 짧은 글줄 자리 secondary line보조 설명 자리. 모든 줄을 같은 길이로 깔면 표처럼 보인다
  5. 끝 열 자리 trailing placeholder금액·시각처럼 오른쪽에 붙는 것. 빠뜨리기 쉬운 칸이다

회색 덩어리 위로 지나가는 빛이 시머(shimmer)입니다. 테두리가 없어 번호를 못 붙였습니다. 움직임을 줄여 달라는 설정이 켜져 있으면 시머를 꺼야 합니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 목록·카드·표처럼 모양이 정해진 것을 불러올 때
  • 첫 화면 — 자리를 잡아 두면 체감 속도가 눈에 띄게 빨라집니다
  • 내용이 들어오며 화면이 밀리는 곳 (레이아웃 시프트를 없앱니다)

이럴 때는 안 쓴다

  • 들어올 모양을 모를 때 — 안 맞는 뼈대는 스피너보다 나쁩니다
  • 0.3초 안에 끝나는 일 — 깜빡임만 남습니다
  • 버튼 하나처럼 자리가 작을 때 → 스피너
  • 가짜 글자를 넣기 — 진짜 내용으로 오해합니다. 글자는 넣지 않습니다

대신 이걸 — 모양을 모르면 스피너, 끝나는 때를 알면 프로그레스 바, 기다림을 없앨 수 있으면 낙관적 UI, 불러올 것이 아예 없으면 빈 상태.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 키보드이 부품의 계약서

어려운 건 반짝이는 회색 상자가 아니라 실제 줄과 높이를 맞추는 일입니다. 줄 높이를 고정해 두면 거의 저절로 맞습니다.

<!-- 글자를 넣지 않는다. 읽을 것이 없다고 알린다 -->
<div class="row" aria-hidden="true">
  <span class="skl skl--circle"></span>
  <span class="skl" style="height:12px;width:58%"></span>
</div>

/* 줄 높이를 고정해야 뼈대와 실제 줄이 딱 맞는다 */
.row { height: 72px; }

/* 움직임을 줄여 달라면 반짝임을 끈다 */
@media (prefers-reduced-motion: reduce) {
  .skl::after { animation: none; }
}
키일어나야 하는 일
스크린 리더뼈대는 읽을 것이 없다. aria-hidden="true"로 숨기고, 바깥 영역에 aria-busy="true"를 건다
포커스뼈대에는 누를 것이 없으니 포커스가 가지 않는다
내용이 들어올 때aria-busy를 지운다. 포커스가 사라진 요소에 머물지 않게 한다
움직임 줄이기시머를 끈다. 회색 자리만 남겨도 제 일은 다 한다
실패뼈대를 치우고 다시 시도할 길을 보여 준다

9 서버 쪽으로 치면백엔드 감각으로 번역

스켈레톤 = 스키마를 미리 아는 것응답을 받기 전에 모양을 알고 있다는 뜻입니다. 타입이 정해진 응답과 같습니다. 모양을 모르면 뼈대를 그릴 수 없습니다.
레이아웃 시프트 = 재할당크기를 모르고 담았다가 내용이 들어오며 늘어나는 것은, 용량을 안 잡고 배열에 넣다가 다시 할당하는 것과 같습니다. 미리 크기를 잡아 두면 둘 다 안 흔들립니다.
일부만 뼈대 = 부분 응답캐시에 있는 것은 바로 그리고 없는 칸만 뼈대로 둡니다. stale-while-revalidate 와 같은 모양입니다.
체감 지연실제로 빨라지지는 않습니다. 기다리는 느낌만 줄어듭니다. 그래도 그게 사용자에게는 진짜입니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

스켈레톤은 웹에서 나온 기법이라 모바일 지침에는 이름이 또렷하지 않습니다.

웹표준 지침 없음
스켈레톤 · 가장 널리 쓰이고 이름도 여기서 굳었습니다. 시머를 넣는 것이 관례입니다.
iOSApple HIG
이름이 따로 없습니다. 지침은 '자리 표시 내용(placeholder content)을 보여 주라'고만 합니다. 시머를 쓰는 앱도 안 쓰는 앱도 많습니다.
안드로이드Material 3
플레이스홀더(Placeholder) · 역시 별도 부품이 아니라 '로딩 중 자리 표시' 패턴으로 다룹니다.

자주 생기는 사고 — "스켈레톤 넣어 주세요"는 웹에서는 바로 통하지만, 네이티브 앱 쪽에는 그 이름의 표준 부품이 없습니다. 어떤 모양으로 몇 줄을 깔지를 같이 정해 줘야 합니다 — 그걸 안 정하면 뼈대가 실제 줄과 안 맞아 결국 덜컥거립니다.
