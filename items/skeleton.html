스켈레톤

Skeleton · Placeholder

스켈레톤은 들어올 내용의 모양대로 미리 자리를 잡아 두는 회색 뼈대입니다. 기다림이 짧게 느껴지고, 내용이 이미 잡아 둔 자리에 들어오기 때문에 화면이 덜컥거리지 않습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

두 버튼을 번갈아 눌러 보세요. 누를 때마다 화면이 몇 px 흔들렸는지 아래에 적힙니다. 스켈레톤은 0px이고 스피너는 수십 px입니다. 내용이 들어오면서 화면이 이렇게 흔들리는 것을 레이아웃 시프트라고 부르는데, 스켈레톤은 레이아웃 시프트를 없애려고 씁니다.

2 이름같은 것을 부르는 여러 이름

한국어스켈레톤, 스켈레톤 화면, 뼈대 화면
영어skeleton, skeleton screen, placeholder, ghost element
같이 쓰는 말뼈대 위로 지나가는 빛은 시머(shimmer), 회색 덩어리 하나하나는 플레이스홀더라고 부릅니다. 실제 내용과 모양이 거의 똑같은 뼈대는 고스트라고도 합니다.
자주 잘못 부르는 이름로딩 — 스피너와 한데 묶어 부르면 '들어올 자리를 미리 잡느냐'라는 중요한 차이가 드러나지 않습니다.
와이어프레임 — 와이어프레임은 설계 단계에서 그리는 그림이고, 스켈레톤은 실제로 돌아가는 화면의 한 상태입니다.
더미 데이터 — 자리에 가짜 글자를 채워 넣는 더미 데이터와 달리, 스켈레톤에는 글자를 넣지 않습니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

겹쳐 뜨는 부품들은 모양만 보고는 구별하기 어렵지만, 아래 네 가지를 따져 보면 어느 부품인지 가려낼 수 있습니다.

끝나는 때를 아나들어올 자리를 잡나사용자가 기다리나화면이 덜컥거리나
스피너모른다안 잡는다기다린다덜컥거린다
스켈레톤모른다잡는다기다린다안 덜컥거린다
프로그레스 바안다잡기도 한다기다린다안 덜컥거린다
낙관적 UI해당 없음잡는다안 기다린다안 덜컥거린다

스켈레톤을 한 줄로 정리하면 — 스켈레톤은 들어올 내용의 모양을 알 때만 쓸 수 있습니다. 모양을 모르는 채로 아무 뼈대나 깔아 두면 실제 내용과 크기가 맞지 않아, 내용이 들어올 때 결국 화면이 덜컥거립니다.

4 상태상태마다 달라지는 모습

5 해부도부분마다 붙은 이름

  1. 줄 틀 row · container실제 줄과 높이가 같아야 합니다. 높이가 어긋나면 내용이 들어올 때 화면이 밀리므로 스켈레톤을 쓴 효과가 없어집니다
  2. 동그란 자리 avatar placeholder아바타가 들어올 자리입니다. 크기와 모양까지 실제 아바타에 맞춥니다
  3. 긴 글줄 자리 line placeholder제목이 들어올 자리입니다. 줄마다 길이를 조금씩 다르게 해야 실제 목록처럼 보입니다
  4. 짧은 글줄 자리 secondary line보조 설명이 들어올 자리입니다. 모든 줄을 같은 길이로 깔면 목록이 아니라 표처럼 보입니다
  5. 끝 열 자리 trailing placeholder금액이나 시각처럼 줄 오른쪽 끝에 붙는 값의 자리입니다. 뼈대를 그릴 때 빠뜨리기 쉽습니다

회색 덩어리 위로 지나가는 빛을 시머(shimmer)라고 부르는데, 테두리가 없는 효과라서 그림에 번호를 붙이지 못했습니다. 사용자가 움직임을 줄여 달라는 설정을 켜 두었다면 시머를 꺼야 합니다.

6 쓸 때 / 안 쓸 때

스켈레톤을 쓰는 경우

  • 목록·카드·표처럼 모양이 정해진 것을 불러올 때
  • 첫 화면을 불러올 때. 자리를 잡아 두면 사용자가 느끼는 속도가 눈에 띄게 빨라집니다
  • 내용이 들어오면서 화면이 밀리는 곳을 고칠 때. 레이아웃 시프트를 없앱니다

스켈레톤을 쓰지 않는 경우

  • 들어올 모양을 모를 때. 실제 내용과 맞지 않는 뼈대는 스피너보다 나쁩니다
  • 0.3초 안에 끝나는 일을 기다릴 때. 뼈대가 깜빡이기만 하고 사라집니다
  • 버튼 하나처럼 자리가 작을 때. 스피너를 씁니다
  • 뼈대에 가짜 글자를 넣을 때. 사용자가 진짜 내용으로 오해하므로 글자는 넣지 않습니다

스켈레톤 대신 다른 것을 써야 하는 경우 — 모양을 모르면 스피너, 끝나는 때를 알면 프로그레스 바, 기다림을 없앨 수 있으면 낙관적 UI, 불러올 것이 아예 없으면 빈 상태.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 마크업과 키보드구현할 때 지킬 최소 규칙

반짝이는 회색 상자는 쉽게 만들 수 있고, 손이 많이 가는 부분은 뼈대를 실제 줄과 같은 높이로 맞추는 일입니다. 줄 높이를 고정해 두면 뼈대와 실제 줄의 높이가 거의 저절로 맞습니다.

<!-- 글자를 넣지 않는다. 읽을 것이 없다고 알린다 -->
<div class="row" aria-hidden="true">
  <span class="skl skl--circle"></span>
  <span class="skl" style="height:12px;width:58%"></span>
</div>

/* 줄 높이를 고정해야 뼈대와 실제 줄이 딱 맞는다 */
.row { height: 72px; }

/* 움직임을 줄여 달라면 반짝임을 끈다 */
@media (prefers-reduced-motion: reduce) {
  .skl::after { animation: none; }
}
키와 동작그때 일어나야 하는 일
스크린 리더뼈대에는 읽을 내용이 없으므로 aria-hidden="true"로 숨기고, 바깥 영역에 aria-busy="true"를 겁니다
포커스뼈대에는 누를 것이 없으니 포커스가 가지 않습니다
내용이 들어올 때aria-busy를 지웁니다. 뼈대가 사라질 때 포커스가 사라진 요소에 남아 있지 않게 합니다
움직임 줄이기시머를 끕니다. 회색 자리만 남겨도 내용이 들어올 자리를 잡아 두는 역할은 그대로 합니다
실패뼈대를 치우고 다시 시도할 수 있는 버튼을 보여 줍니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

스켈레톤 = 스키마를 미리 아는 것스켈레톤을 그린다는 것은 응답을 받기 전에 그 응답의 모양을 알고 있다는 뜻이고, 타입이 정해진 응답과 같은 상황입니다. 응답의 모양을 모르면 뼈대를 그릴 수 없습니다.
레이아웃 시프트 = 재할당크기를 모르는 채로 자리를 잡았다가 내용이 들어오면서 늘어나는 것은, 용량을 정하지 않은 배열에 값을 넣다가 공간이 모자라 다시 할당하는 것과 같습니다. 두 경우 모두 미리 크기를 잡아 두면 다시 할당하거나 화면이 흔들리는 일이 없습니다.
일부만 뼈대 = 부분 응답캐시에 있는 것은 바로 그리고, 캐시에 없는 칸만 뼈대로 둡니다. 캐시 값을 먼저 쓰고 뒤에서 새 값을 받아 오는 stale-while-revalidate와 같은 구조입니다.
체감 지연스켈레톤을 쓴다고 실제 응답이 빨라지지는 않고, 사용자가 기다린다고 느끼는 시간만 줄어듭니다. 그래도 사용자는 느끼는 시간으로 속도를 판단하기 때문에 쓸 가치가 있습니다.

10 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

스켈레톤은 웹에서 나온 기법이라서 모바일 디자인 지침에는 따로 정해진 이름이 없습니다.

웹표준 지침 없음
스켈레톤 · 웹에서 가장 널리 쓰이고, 스켈레톤이라는 이름도 웹에서 자리 잡았습니다. 시머를 넣는 것이 관례입니다.
iOSApple HIG
이름이 따로 없습니다. 지침에는 '자리 표시 내용(placeholder content)을 보여 주라'는 말만 있고, 시머를 쓰는 앱과 쓰지 않는 앱이 모두 많습니다.
안드로이드Material 3
플레이스홀더(Placeholder) · iOS와 마찬가지로 따로 정한 부품은 없고, '로딩 중 자리 표시' 패턴으로 다룹니다.

플랫폼 차이 때문에 자주 생기는 문제 — "스켈레톤 넣어 주세요"라는 요청은 웹 개발자에게는 바로 통하지만, 네이티브 앱에는 그런 이름의 표준 부품이 없습니다. 그래서 어떤 모양으로 몇 줄을 깔지도 함께 정해 주어야 합니다. 이 부분을 정하지 않으면 뼈대가 실제 줄과 맞지 않아 내용이 들어올 때 결국 덜컥거립니다.
