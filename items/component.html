컴포넌트와 인스턴스

Component & instance

원본 하나와 복제본들. 원본을 고치면 복제본이 전부 따라오는 것이 요점입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

맨 왼쪽이 마스터(원본), 나머지가 인스턴스(복제본)입니다. 마스터의 글자나 모서리를 바꿔 보세요 — 전부 따라옵니다.
인스턴스에서 떼어내기를 누르면 그 하나만 연결이 끊깁니다. 나중에 마스터를 고칠 때 떼어낸 것만 옛 모습으로 남습니다.

2 이름부르는 말이 여러 개다

한국어컴포넌트, 마스터, 인스턴스, 복제본, 떼어내기
영어component, main component, instance, override, detach
같이 쓰는 말원본을 마스터 컴포넌트·메인 컴포넌트라 하고, 복제본이 인스턴스입니다. 인스턴스에서 글자나 아이콘만 바꾸는 것이 오버라이드(덮어쓰기), 연결을 끊는 것이 디태치(떼어내기)입니다. 여러 마스터를 모아 하나로 만든 것은 컴포넌트 세트이고, 그 안의 칸들이 배리언트입니다.
자주 잘못 부름컴포넌트 — 개발 쪽의 리액트 컴포넌트와 같은 생각이지만 같은 것은 아닙니다. 시안의 것은 그림입니다.
심볼 — 다른 도구의 옛 이름입니다. 뜻은 같습니다.
복사·붙여넣기 — 그냥 복사한 것은 연결이 없습니다. 인스턴스가 아닙니다.

3 가르는 기준형제들과 비교하는 네 축

현장 용어는 말이 아니라 일하는 단계를 가리킵니다. 이 네 가지만 물어보면 갈립니다.

무엇을 가리키나언제 나오나개발 쪽 대응물잘못 알아들으면
와이어프레임과 목업과 시안얼마나 진짜 같은 그림인가기획 ~ 디자인마크업 구조 ~ 완성 화면엉뚱한 리뷰가 돌아온다
디자인 시스템규칙 + 부품 + 문서프로젝트 내내토큰 + 컴포넌트 라이브러리스타일 가이드와 섞인다
컴포넌트와 인스턴스원본과 복제본시안 작업컴포넌트 정의와 사용원본을 고쳐 전체가 바뀐다
배리언트와 프롭같은 부품의 정해진 변형시안 작업props상태와 섞인다
오토 레이아웃자동 배치시안 작업flexbox‘여백이 자동’을 못 알아듣는다
프로토타입눌리는 시안리뷰 · 사용자 시험아직 코드가 아니다다 된 줄 안다
핸드오프넘기는 일개발 시작 전스펙 읽기그림만 받고 규칙은 못 받는다
에셋 내보내기그림 파일 넘기기개발 중srcset · SVG1배만 받아 뭉갠다
디자인 리뷰고칠 거리를 만드는 말단계마다코드 리뷰너무 이르거나 너무 늦다
버전 관리어느 것이 지금 것인가프로젝트 내내커밋 메시지final 사슬이 생긴다

한 줄로 — 떼어낸 것은 흔적이 안 남습니다. 그래서 급할 때 떼어낸 하나가 몇 달 뒤 혼자 옛 모습으로 남습니다.

4 연결 상태마스터를 따라오나

5 해부도부분 이름이 제일 안 알려진 지식

마스터 — 원본 하나. 여기만 고친다
인스턴스 — 복제본. 마스터를 따라간다
덮어쓰기 — 글자·아이콘만 바꾼다. 연결은 남는다
떼어내기(디태치) — 연결이 끊긴다. 되돌리기 어렵다
코드로는 컴포넌트 정의와 사용
떼어낸 것은 눈으로 찾아야 한다
  1. 마스터 원본 하나여기만 고친다. 화면에 안 쓰기도 한다
  2. 인스턴스 복제본마스터를 따라간다
  3. 덮어쓰기 글자 · 아이콘연결은 남는다. 이게 정상적인 쓰임
  4. 떼어내기 연결 끊기급할 때 쓰지만 흔적이 안 남는다
  5. 코드로는 정의와 사용function Button()과 <Button />
  6. 찾기 눈으로떼어낸 것을 목록으로 뽑기 어렵다

떼어내야 할 것 같으면 대개 마스터가 부족한 것입니다. '이 버튼만 아이콘을 넣고 싶은데 마스터에 자리가 없다' 같은 순간에 떼어내게 되는데, 그때 필요한 것은 떼어내기가 아니라 마스터에 아이콘 자리를 추가하는 일입니다. 코드에서도 같습니다 — 컴포넌트를 복사해 조금 고친 버전을 만드는 대신 props 를 하나 추가하는 쪽이 거의 늘 낫습니다. 그 판단이 쌓인 결과가 배리언트 설계입니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 같은 모양이 여러 번 나올 때
  • 나중에 한꺼번에 고칠 일이 있을 때
  • 덮어쓰기로 되는 범위까지만 바꾸기

이럴 때는 안 쓴다

  • 급하다고 떼어내기 — 흔적이 안 남는다
  • 복사·붙여넣기로 늘리기 — 연결이 없다
  • 한 번만 쓰는 것을 컴포넌트로 — 과하다
  • 마스터를 화면 안에 그대로 쓰기 — 실수로 고쳐진다

대신 이걸 — 변형이 여럿이면 배리언트, 값이 흩어지면 디자인 시스템의 토큰, 배치는 오토 레이아웃.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 코드와 맞춰 보기이 부품의 계약서

시안의 마스터·인스턴스는 코드의 정의와 사용입니다.

// 마스터 = 컴포넌트 정의 — 한 곳에만 있다
function Button({ label, tone = 'primary', size = 'md' }) {
  return <button className={`btn btn--${tone} btn--${size}`}>{label}</button>;
}

// 인스턴스 = 쓰는 곳 — 덮어쓰기는 props 로
<Button label="내보내기" />
<Button label="삭제" tone="danger" />

// ✕ 떼어내기에 해당하는 코드 — 복사해서 조금 고친 것
function ButtonWithIcon({ label }) {     // 마스터와 멀어진다
  return <button className="btn btn--primary">◆ {label}</button>;
}
키일어나야 하는 일
마스터는 한 곳에화면 안에 두면 실수로 고쳐진다. 따로 모아 둔다
덮어쓰기는 props글자·아이콘·상태. 모양 자체를 바꾸려면 마스터를 고친다
접근성도 마스터에role·aria-*·키보드를 넣어 두면 쓰는 쪽이 공짜로 얻는다
떼어내면 그것도 끊긴다접근성 속성까지 과거 모습으로 굳는다
이름을 쓰임으로Button/Primary보다 Button/주동작처럼 언제 쓰는지가 드러나게
찾기코드에서는 검색으로 쓰인 곳을 다 찾을 수 있다. 시안에서는 어렵다

9 서버 쪽으로 치면백엔드 감각으로 번역

부품 묶음에 버전마스터를 고치면 쓰는 쪽이 전부 바뀝니다. 무엇이 바뀌는지를 적어 배포합니다.
쓰인 곳 세기코드에서는 검색으로 셀 수 있습니다. 안 쓰이는 부품은 지웁니다.
복사된 부품 찾기비슷한 클래스 이름(btn-primary-2)을 찾아보면 떼어낸 자리가 드러납니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

이름만 다르고 생각은 같습니다.

웹컴포넌트
저장정의 / 사용
function Button()과 <Button />. 시안의 마스터·인스턴스와 그대로 짝입니다.
iOSSwiftUI View

View 하나가 컴포넌트입니다. 쓰는 쪽은 값만 넘깁니다.
안드로이드Composable

@Composable 함수가 같은 자리입니다.

자주 생기는 사고 — 시안에서 떼어낸 부품은 코드에서 복사해 고친 컴포넌트와 같은 문제를 만듭니다 — 둘 다 그 순간에는 가장 빠른 길이고, 몇 달 뒤 고칠 때 혼자 남습니다. "이거 떼어낸 건가요"와 "이거 복사한 건가요"는 같은 질문이고, 둘 다 원본에 자리를 하나 더 만들면 안 해도 되는 일입니다.
