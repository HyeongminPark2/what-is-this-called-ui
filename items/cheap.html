무엇을 움직이나

Cheap vs expensive properties

같은 움직임도 어떤 속성을 바꾸느냐에 따라 값이 다릅니다. 버벅임의 거의 전부가 여기서 납니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

네 가지 방법으로 같은 거리를 움직이고 한 프레임을 만드는 데 걸린 시간을 잽니다.
상자 수를 올리면 차이가 벌어집니다 — transform·opacity는 거의 그대로인데 left·width는 함께 올라갑니다. 그 차이가 그대로 버벅임입니다.

2 이름부르는 말이 여러 개다

한국어리플로우, 리페인트, 합성, 레이어
영어reflow / layout, repaint, compositing, GPU acceleration
같이 쓰는 말배치를 다시 재는 것이 리플로우(reflow)·레이아웃, 다시 칠하는 것이 리페인트(repaint)·페인트, 이미 그린 조각을 옮겨 겹치는 것이 컴포지팅(compositing)입니다. 읽기와 쓰기가 번갈아 일어나 배치가 되풀이되는 것을 레이아웃 스래싱이라 합니다.
자주 잘못 부름GPU 가속 — transform이 빠른 것은 가속 때문만이 아니라 배치를 건너뛰기 때문입니다.
FPS — 초당 프레임 수는 결과이고, 원인은 프레임 하나에 든 시간입니다.
최적화 — 이건 최적화가 아니라 처음부터 맞게 쓰는 문제입니다.

3 가르는 기준형제들과 비교하는 네 축

움직임은 장식이 아니라 말입니다. 이 네 가지만 물어보면 갈립니다.

무엇을 정하나사람이 읽는 뜻과하면모션 줄이기에서
이징 곡선속도를 나눠 쓰는 방식무게와 재질끈적해 보인다그대로 둔다
지속 시간얼마나 걸리나거리와 크기기다리게 된다짧게 하거나 0
진입과 퇴장들고 나는 방식어디서 왔나닫는 데 붙잡힌다퇴장은 거의 0
무엇을 움직이나어떤 속성을 바꾸나매끄러움 그 자체버벅인다해당 없음
스프링지나쳤다 돌아오는 정도손으로 민 느낌어지럽다튕김을 0으로
차례로 들어오기줄 사이 지연순서와 묶음마지막이 늦는다한꺼번에 띄운다
제스처손가락을 따라가는 규칙내가 조작한다실수로 닫힌다그대로 둔다
모션 줄이기무엇을 끄나배려받고 있다다 꺼서 변화를 못 읽는다이게 그 기준이다
공유 요소 전환두 화면의 같은 것어디서 왔나자리가 어긋나면 더 헷갈린다자리 이동 없이
스크롤 연동굴림에 맞춰 움직이기내가 어디쯤인가멀미를 부른다연출만 끈다

한 줄로 — 움직일 때는 transform, 사라질 때는 opacity. 이 둘로 안 되는 움직임은 대개 설계를 다시 보는 게 빠릅니다.

4 속성별 비용어느 단계부터 다시 하나

5 해부도부분 이름이 제일 안 알려진 지식

스타일배치칠하기합치기
transform · opacity — 배치도 칠하기도 건너뛴다
color · box-shadow — 다시 칠한다
left · width · margin — 배치부터 다시
한 프레임에 쓸 수 있는 시간 = 16.7ms
쓰고 바로 읽으면 그 자리에서 배치가 돈다
  1. 네 단계 스타일 → 배치 → 칠하기 → 합치기뒤로 갈수록 싸다. 어디서 끼어드느냐가 비용이다
  2. 가장 싼 둘 transform · opacity스타일만 바꾸고 합치기로 건너뛴다
  3. 중간 색 · 그림자자리는 그대로지만 다시 칠해야 한다
  4. 가장 비싼 것 left · width · margin그 줄 전체, 때로는 문서 전체를 다시 잰다
  5. 예산 16.7ms60fps 기준 한 프레임. 여기서 브라우저 몫도 빼야 한다
  6. 쓰고 바로 읽기 layout thrashingel.style.width=…; el.offsetWidth — 그 줄에서 배치가 즉시 돈다

읽기와 쓰기를 섞지 않는 것이 두 번째 규칙입니다. 반복문 안에서 style.left를 쓰고 바로 offsetLeft를 읽으면, 브라우저는 정확한 값을 주려고 그 자리에서 배치를 다시 합니다 — 100개면 배치가 100번 돕니다. 읽을 것을 먼저 다 읽고, 쓸 것을 나중에 다 쓰면 한 번으로 끝납니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 자리 옮김은 transform: translate()
  • 크기 변화는 scale()로 대신할 수 있는지 먼저 보기
  • 나타남·사라짐은 opacity
  • 읽기를 먼저 몰아 하고 쓰기를 나중에

이럴 때는 안 쓴다

  • left·top으로 애니메이션 — 같은 결과를 더 비싸게 낸다
  • width를 매 프레임 — 형제들 자리까지 흔든다
  • 반복문 안에서 쓰고 바로 읽기
  • will-change를 아무 데나 — 레이어가 늘면 메모리를 먹는다

대신 이걸 — 긴 목록이 무거우면 가상 스크롤, 그림이 무거우면 크기를 줄이기, 애니메이션이 많으면 모션 줄이기부터 챙기기.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 코드와 규칙이 성능의 계약서

움직임은 transform·opacity로 적고, 읽기와 쓰기를 가릅니다.

/* 싼 쪽 */
.card { transition: transform 220ms var(--ease-out), opacity 160ms linear; }
.card.out { transform: translateY(8px); opacity: 0; }

/* 펼치기 — height: auto 는 전환이 안 된다 */
.acc { display: grid; grid-template-rows: 0fr; transition: grid-template-rows 220ms; }
.acc[open] { grid-template-rows: 1fr; }
.acc > div { overflow: hidden; }

// 읽기를 먼저, 쓰기를 나중에
const tops = items.map(el => el.getBoundingClientRect().top);   // 읽기
items.forEach((el, i) => { el.style.transform = `translateY(${tops[i]}px)`; });  // 쓰기
키일어나야 하는 일
will-change는 미리, 그리고 치운다움직이기 직전에 켜고 끝나면 지운다. 늘 켜 두면 레이어가 쌓인다
transform은 새 기준을 만든다자식의 position:fixed가 화면이 아니라 이 상자를 따르게 된다
opacity도 쌓임 맥락을 만든다z-index가 안 먹는 흔한 이유다
content-visibility: auto화면 밖 덩어리를 안 그린다. 긴 문서에 효과가 크다
@media (prefers-reduced-motion)비싼 애니메이션일수록 줄이기에서 먼저 끈다
재는 법개발자 도구의 성능 탭에서 보라색(배치)·초록색(칠하기) 띠를 본다

9 서버 쪽으로 치면백엔드 감각으로 번역

느린 쪽이 어디인지'화면이 버벅인다'의 원인은 서버일 수도 그리기일 수도 있습니다. 응답 시간과 프레임 시간을 따로 재야 갈립니다.
한 번에 밀어 넣는 양서버가 2,000건을 한 번에 주면 그리는 쪽이 멎습니다. 쪽을 나누거나 가상 스크롤로 받습니다.
이미지 크기원본 2000px 이미지를 100px 자리에 넣으면 칠하기가 비쌉니다. 서버에서 줄여 보냅니다.
실사용자 측정개발 기기는 빠릅니다. INP 같은 실사용자 지표를 모아 보면 느린 기기의 사정이 드러납니다.
