무엇을 움직이나

Cheap vs expensive properties

같은 움직임이라도 어떤 속성을 바꾸느냐에 따라 브라우저가 치르는 비용이 다릅니다. 움직임이 버벅이는 원인은 대부분 여기에 있습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

네 가지 방법으로 같은 거리를 움직이면서 한 프레임을 만드는 데 걸린 시간을 잽니다.
상자 수를 늘리면 차이가 벌어지는데, transform과 opacity는 시간이 거의 그대로인 반면 left와 width는 상자 수와 함께 늘어납니다. 이렇게 늘어난 시간이 화면에서는 버벅임으로 나타납니다.

2 이름같은 것을 부르는 여러 이름

한국어리플로우, 리페인트, 합성, 레이어
영어reflow / layout, repaint, compositing, GPU acceleration
같이 쓰는 말요소의 자리와 크기를 다시 계산하는 것을 리플로우(reflow) 또는 레이아웃, 픽셀을 다시 칠하는 것을 리페인트(repaint) 또는 페인트, 이미 그린 조각을 옮겨 겹치는 것을 컴포지팅(compositing)이라고 합니다. 값을 읽고 쓰는 일이 번갈아 일어나 배치 계산이 되풀이되는 현상은 레이아웃 스래싱이라고 부릅니다.
자주 잘못 부르는 이름GPU 가속 — transform이 빠른 것은 GPU 가속 때문만이 아니라 배치 계산을 건너뛰기 때문입니다.
FPS — 초당 프레임 수는 결과로 나타나는 숫자이고, 그 원인은 프레임 하나를 만드는 데 든 시간입니다.
최적화 — 속성을 고르는 일은 나중에 하는 최적화가 아니라 처음부터 맞게 써야 하는 기본입니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

움직임은 화면에서 무엇이 바뀌었는지 사용자에게 알려 주는 역할을 합니다. 아래 네 가지를 따져 보면 움직임을 다루는 항목들을 서로 구별할 수 있습니다.

이 항목이 정하는 것사용자가 움직임에서 읽어 내는 것지나치게 쓰면 생기는 일모션 줄이기를 켰을 때
이징 곡선속도를 나눠 쓰는 방식무게와 재질끈적해 보임그대로 둠
지속 시간얼마나 걸리는지거리와 크기사용자를 기다리게 함짧게 줄이거나 0으로
진입과 퇴장들고 나는 방식어디서 왔는지닫힐 때까지 붙잡혀 기다림퇴장 시간을 거의 0으로
무엇을 움직이나어떤 속성을 바꾸는지움직임이 매끄러운지화면이 버벅임해당 없음
스프링지나쳤다 돌아오는 정도손으로 민 듯한 느낌어지러움튕김을 0으로
차례로 들어오기줄과 줄 사이의 지연순서와 묶음마지막 줄이 늦게 나타남한꺼번에 띄움
제스처손가락을 따라가는 규칙내가 조작하고 있다는 느낌실수로 닫히기 쉬움그대로 둠
모션 줄이기무엇을 끄는지배려받고 있다는 느낌다 꺼 버려 무엇이 바뀌었는지 알 수 없음이 항목이 그 기준
공유 요소 전환두 화면에 함께 있는 같은 요소어디서 왔는지자리가 어긋나면 오히려 헷갈림자리 이동 없이 전환
스크롤 연동스크롤에 맞춰 움직이는 방식지금 어디쯤 읽고 있는지멀미를 일으킴연출만 끔

무엇을 움직이나를 한 줄로 정리하면 — 자리를 옮길 때는 transform, 나타나거나 사라질 때는 opacity를 씁니다. 이 두 속성으로 만들 수 없는 움직임이라면 대개 움직임 설계를 다시 보는 편이 빠릅니다.

5 해부도부분마다 붙은 이름

스타일배치칠하기합치기
transform과 opacity는 배치와 칠하기를 건너뜀
color와 box-shadow는 다시 칠함
left·width·margin은 배치부터 다시 함
한 프레임에 쓸 수 있는 시간은 16.7ms
쓰고 바로 읽으면 그 자리에서 배치를 계산함
  1. 네 단계 스타일 → 배치 → 칠하기 → 합치기뒤 단계일수록 비용이 적습니다. 속성을 바꿨을 때 어느 단계부터 다시 하느냐가 비용을 정합니다
  2. 비용이 가장 적은 두 속성 transform · opacity스타일만 바꾸고 배치와 칠하기를 건너뛰어 바로 합치기로 갑니다
  3. 비용이 중간인 속성 색 · 그림자자리는 그대로지만 다시 칠해야 합니다
  4. 비용이 가장 큰 속성 left · width · margin그 줄 전체, 때로는 문서 전체의 자리를 다시 계산합니다
  5. 한 프레임 예산 16.7ms60fps 기준으로 한 프레임에 쓸 수 있는 시간입니다. 여기서 브라우저가 쓰는 시간도 빼야 합니다
  6. 쓰고 바로 읽기 layout thrashingel.style.width=…; el.offsetWidth처럼 쓰고 바로 읽으면 그 줄에서 배치 계산이 즉시 일어납니다

두 번째 규칙은 읽기와 쓰기를 섞지 않는 것입니다. 반복문 안에서 style.left를 쓰고 바로 offsetLeft를 읽으면, 브라우저는 정확한 값을 돌려주려고 그 자리에서 배치를 다시 계산합니다. 그래서 요소가 100개면 배치 계산도 100번 일어납니다. 반면 읽을 값을 먼저 다 읽고 쓸 값을 나중에 다 쓰면 배치 계산은 한 번으로 끝납니다.

6 쓸 때 / 안 쓸 때

비용이 적은 속성으로 움직이는 방법

  • 자리를 옮길 때. transform: translate()를 씁니다
  • 크기를 바꿀 때. scale()로 대신할 수 있는지 먼저 봅니다
  • 나타나거나 사라질 때. opacity를 씁니다
  • 값을 여러 개 읽고 쓸 때. 읽기를 먼저 몰아서 하고 쓰기는 나중에 합니다

움직임을 만들 때 피할 속성과 습관

  • left·top으로 애니메이션할 때. transform과 같은 결과를 더 큰 비용으로 냅니다
  • width를 매 프레임 바꿀 때. 옆에 있는 요소들의 자리까지 다시 계산됩니다
  • 반복문 안에서 값을 쓰고 바로 읽을 때
  • will-change를 아무 데나 걸 때. 레이어가 늘어나면 그만큼 메모리를 씁니다

속성을 바꿔도 화면이 무거울 때 살펴볼 것 — 긴 목록 때문에 무거우면 가상 스크롤을 쓰고, 그림이 무거우면 그림 크기를 줄입니다. 애니메이션이 많아서 무겁다면 모션 줄이기부터 살펴봅니다.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 코드와 규칙구현할 때 지킬 최소 규칙

움직임은 transform과 opacity로 적고, 값을 읽는 코드와 쓰는 코드를 나눕니다.

/* 싼 쪽 */
.card { transition: transform 220ms var(--ease-out), opacity 160ms linear; }
.card.out { transform: translateY(8px); opacity: 0; }

/* 펼치기 — height: auto 는 전환이 안 된다 */
.acc { display: grid; grid-template-rows: 0fr; transition: grid-template-rows 220ms; }
.acc[open] { grid-template-rows: 1fr; }
.acc > div { overflow: hidden; }

// 읽기를 먼저, 쓰기를 나중에
const tops = items.map(el => el.getBoundingClientRect().top);   // 읽기
items.forEach((el, i) => { el.style.transform = `translateY(${tops[i]}px)`; });  // 쓰기
알아 둘 규칙자세한 내용
will-change는 미리 켜고 끝나면 지우기움직이기 직전에 켜고 움직임이 끝나면 지웁니다. 늘 켜 두면 레이어가 계속 쌓입니다
transform이 만드는 새 기준자식 요소의 position:fixed가 화면이 아니라 이 상자를 기준으로 자리를 잡습니다
opacity가 만드는 쌓임 맥락z-index가 듣지 않을 때 흔히 이것이 원인입니다
content-visibility: auto화면 밖에 있는 덩어리는 그리지 않습니다. 긴 문서에서 효과가 큽니다
@media (prefers-reduced-motion)비용이 큰 애니메이션일수록 모션 줄이기 설정에서 먼저 끕니다
비용을 재는 방법개발자 도구의 성능 탭에서 보라색(배치)·초록색(칠하기) 띠가 얼마나 긴지 봅니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

느린 쪽이 서버인지 화면인지 가리기화면이 버벅일 때 원인은 서버일 수도 있고 화면을 그리는 쪽일 수도 있습니다. 응답 시간과 프레임 시간을 따로 재야 어느 쪽인지 가릴 수 있습니다.
한 번에 보내는 데이터 양서버가 2,000건을 한 번에 보내면 화면을 그리는 동안 브라우저가 멈춥니다. 그래서 페이지를 나눠 받거나 가상 스크롤을 씁니다.
이미지를 서버에서 줄여 보내기원본 2000px 이미지를 100px 자리에 넣으면 칠하는 비용이 커집니다. 이미지는 서버에서 줄여 보냅니다.
실제 사용자 기기에서 재기개발자가 쓰는 기기는 대개 빠릅니다. INP 같은 실사용자 지표를 모아 보면 느린 기기에서 실제로 얼마나 걸리는지 알 수 있습니다.

플랫폼이 달라도 자리를 다시 계산하게 하지 않는다는 규칙은 같습니다.

플랫폼 차이 때문에 자주 생기는 문제 — "애니메이션이 끊겨요"라는 신고를 받으면 애니메이션이 어떤 속성을 바꾸고 있는지부터 봅니다. left나 width를 매 프레임 바꾸고 있다면 기기 성능 문제가 아니고, transform으로 바꾸는 것만으로 해결되는 경우가 많습니다. 애니메이션 라이브러리를 바꾸는 것보다 속성 두 개를 바꾸는 편이 대부분 더 빨리 해결됩니다.
