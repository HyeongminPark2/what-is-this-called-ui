세이프 에어리어

Safe area · safe area insets

세이프 에어리어는 화면에서 무엇을 놓아도 안전한 영역입니다. 그 바깥은 노치와 홈 막대가 차지하고 있어서, 글자나 버튼을 두면 가려지거나 눌리지 않습니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

빨간 띠는 내용을 놓으면 안 되는 자리입니다. 체크를 켜면 상단 바 글자가 노치 아래로 내려오고, 탭바가 홈 인디케이터 위로 올라옵니다.
웹에서는 env(safe-area-inset-top) 같은 값으로 인셋을 읽는데, viewport-fit=cover를 적지 않으면 이 값이 항상 0입니다. "env가 안 먹어요"라는 문제는 대부분 이 때문에 생깁니다.

2 이름같은 것을 부르는 여러 이름

한국어세이프 에어리어, 안전 영역
영어safe area, safe area insets, notch, display cutout
같이 쓰는 말위쪽 카메라 자리는 노치(notch) 또는 다이내믹 아일랜드, 구멍 모양은 펀치홀(punch hole · display cutout), 아래 막대는 홈 인디케이터(home indicator)입니다. 안전 영역의 두께는 인셋(inset)이라고 하고, 화면 끝까지 그리는 것은 엣지 투 엣지(edge-to-edge)라고 부릅니다.
자주 잘못 부르는 이름상태 바 — 시계와 배터리가 있는 띠는 상태 바이고, 세이프 에어리어는 상태 바까지 포함한 '쓰면 안 되는 범위'입니다.
패딩 — padding-top: 44px처럼 숫자로 고정하면 기기마다 어긋나기 때문에 OS에 값을 물어봐야 합니다.
뷰포트 — 화면 크기와 안전 영역은 다릅니다. 안전 영역은 화면 전체보다 안쪽에 있습니다.

3 화면 모양에 따라 챙길 자리기기와 화면 방향마다 달라지는 인셋

4 해부도부분마다 붙은 이름

모란상회 홈정산
위는 노치가 차지하는 두께
아래는 홈 막대가 차지하는 두께
env(safe-area-inset-top)
env(safe-area-inset-bottom)
viewport-fit=cover 없으면 값이 늘 0
  1. 화면 전체 viewport기기의 물리적 화면입니다. 여기까지 그릴 수는 있습니다
  2. 위 인셋 safe-area-inset-top노치와 상태 바가 차지하는 두께로, 기기마다 다릅니다
  3. 아래 인셋 safe-area-inset-bottom홈 인디케이터 자리입니다. 여기에 버튼을 두면 눌리지 않습니다
  4. 위 값 읽기 env(safe-area-inset-top)숫자를 고정하지 않고 OS에 값을 물어봅니다
  5. 아래 값 읽기 env(safe-area-inset-bottom)홈 막대가 없는 기기에서는 0이 오기 때문에 max()와 함께 씁니다
  6. viewport-fit=cover meta viewport이 설정이 없으면 env 값이 항상 0입니다. 'env가 안 먹어요'라는 문제는 대개 이것이 원인입니다

노치가 없는 기기나 데스크톱 브라우저에서는 인셋 값이 0일 수도 있습니다. 그래서 padding-bottom: env(safe-area-inset-bottom)만 적으면 그런 기기에서 패딩이 아예 사라집니다. max(16px, env(…))처럼 적어서 최소 여백을 함께 정해 두는 것이 정석입니다.

5 쓸 때 / 안 쓸 때

세이프 에어리어를 챙겨야 하는 경우

  • 화면 끝까지 그리는 앱이나 웹앱(엣지 투 엣지)을 만들 때
  • 화면 아래 붙박이 버튼이나 탭바가 있을 때
  • 노치 쪽까지 사진이나 배경을 채울 때. 배경은 끝까지 채우고 글자는 안쪽에 둡니다
  • 가로 화면을 지원할 때. 좌우 인셋도 챙깁니다

세이프 에어리어를 다룰 때 피할 것

  • 인셋을 숫자로 고정할 때. padding-top: 44px은 다른 기기에서 맞지 않습니다
  • env()만 쓰고 최소값을 주지 않을 때. 노치 없는 기기에서 여백이 0이 됩니다
  • 바의 배경까지 안쪽으로 밀 때. 화면 가장자리에 흰 띠가 남습니다
  • viewport-fit=cover 없이 env() 값을 쓰려 할 때

세이프 에어리어와 함께 보면 좋은 항목 — 화면 아래에 붙는 탭바 자체는 바텀 탭바에서, 위쪽 바는 앱바에서 다룹니다. 스크롤하는 동안 요소를 한자리에 붙여 두는 방법은 스티키에서 봅니다.

6 자주 보는 모습구조만 따라 그린 재현 그림

7 최소 코드와 규칙메타 태그 한 줄과 패딩 한 줄

<meta> 한 줄과 padding 한 줄이면 되는데, 메타 태그를 먼저 적어야 합니다.

<!-- 이 줄이 없으면 env( )가 항상 0이다 -->
<meta name="viewport"
      content="width=device-width, initial-scale=1, viewport-fit=cover">

/* 바 배경은 끝까지, 내용만 안쪽으로 */
.bottom-nav {
  padding-bottom: max(12px, env(safe-area-inset-bottom));
}                   /* ↑ 노치 없는 기기에서도 최소 12px */

.app-bar {
  padding-top: max(12px, env(safe-area-inset-top));
}

/* 가로 화면에서는 좌우도 챙긴다 */
.page {
  padding-inline: max(16px, env(safe-area-inset-left));
}
지킬 규칙지키는 방법
viewport-fit=cover부터 적기이 한 줄이 없으면 env()가 모두 0이 됩니다. env가 작동하지 않는 가장 흔한 원인입니다
max()로 최소 여백 함께 주기노치 없는 기기에서 0이 와도 최소 여백이 남게 합니다
바 배경은 화면 끝까지 두기바의 배경은 화면 끝까지 두고 안의 내용만 밉니다. 배경까지 밀면 가장자리에 띠가 생깁니다
가로 화면의 좌우 인셋도 챙기기가로로 돌리면 left·right에 값이 생깁니다
인셋을 숫자로 고정하지 않기44px·34px 같은 값은 특정 기기에서만 맞습니다
실기기에서 눌러 보며 확인하기눈으로는 가려지지 않은 것 같아도 눌리지 않는 경우가 있으므로 실기기로 눌러 봅니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

화면에서만 처리하는 일세이프 에어리어는 화면에서만 처리하는 일입니다. 다만 웹앱을 홈 화면에 설치해 쓰는 경우라면 매니페스트의 display: standalone과 함께 생각해야 합니다.
테스트할 기기 조합노치 있는 기기, 노치 없는 기기, 가로 화면 세 가지가 최소한의 테스트 조합입니다. 브라우저 개발자 도구의 기기 에뮬레이션으로도 문제를 상당 부분 잡을 수 있습니다.
키보드가 올라올 때입력칸에 포커스가 가면 키보드가 올라와 화면이 줄어듭니다. 그래서 아래 붙박이 버튼은 키보드 위로 올라오게 따로 처리해야 합니다.
스크린샷으로 자동 검사하기글자 상자가 인셋 영역과 겹치는지는 좌표로 잴 수 있기 때문에, 실기기 없이도 회귀를 막을 수 있습니다.

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

OS가 인셋 값을 알려 준다는 점은 같고, 이름과 기본값이 다릅니다.

WindowInsets로 읽습니다. 최신 안드로이드는 엣지 투 엣지가 기본이라서 인셋을 챙기지 않으면 바로 겹칩니다.

플랫폼 차이 때문에 자주 생기는 문제 — 플랫폼마다 기본값이 정반대입니다. iOS는 안전 영역 안쪽에 그리는 것이 기본이라서 따로 챙기지 않아도 안전하지만, 웹과 최신 안드로이드는 화면 끝까지 그리는 것이 기본이라서 챙기지 않으면 겹칩니다. 같은 시안을 세 플랫폼에 넘길 때 "화면 끝까지 그릴지"를 먼저 정해 두면 플랫폼마다 다른 버그가 생기는 일을 막을 수 있습니다.
