보이는 순서와 읽는 순서

Visual order vs DOM order

CSS로는 보이는 자리만 바꿀 수 있습니다. Tab으로 옮겨 가는 차례와 스크린 리더가 읽어 주는 차례는 CSS와 상관없이 마크업 순서를 따릅니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

보이는 차례를 바꾸는 방법을 고른 뒤 Tab으로 차례대로 옮겨 보기를 누르면 초점이 옮겨 간 차례가 적힙니다.
row-reverse나 order로 뒤집으면 눈에는 취소가 먼저 보이지만 Tab은 저장부터 갑니다. 마우스를 쓰는 사람은 이 차이를 알아챌 일이 없지만, 키보드를 쓰는 사람은 보이는 차례와 다르게 움직이는 초점을 따라가야 합니다.
마크업 순서를 바꾸면 두 차례가 같아지며, 이것이 유일하게 맞는 방법입니다.

2 이름같은 것을 부르는 여러 이름

한국어보이는 순서와 읽는 순서, 시각 순서와 DOM 순서, 초점 순서
영어visual order, DOM order, focus order, reading order
같이 쓰는 말Tab이 따라가는 차례는 초점 순서(focus order), 스크린 리더가 읽어 가는 차례는 읽는 순서(reading order)라고 합니다. 두 순서는 거의 항상 같고, 모두 마크업 순서를 따릅니다. 눈에 보이는 차례는 따로 시각 순서(visual order)라고 부릅니다.
자주 잘못 부르는 이름z-index — 겹침 순서는 요소가 위아래로 쌓이는 순서이고, 이 항목은 앞뒤로 이어지는 차례를 다룹니다.
order 속성 — order는 이 문제를 일으키는 속성이지 해결하는 속성이 아닙니다.
tabindex — 요소가 초점을 받게 할 뿐이고, 차례를 고치는 도구는 아닙니다.

3 두 차례가 어긋나는 경우보이는 차례와 Tab 차례가 같은지 비교

4 해부도부분마다 붙은 이름

마크업 순서 Tab과 읽어 주는 차례의 유일한 근거
order·row-reverse 보이는 자리만 바꿈
position으로 옮겨도 보이는 자리만 바뀜
tabindex="0" 원래 못 받는 요소에 초점을 줌
tabindex="3" 같은 양수 차례를 뒤엎음
두 차례를 맞추려면 마크업을 고침
  1. 마크업 순서 유일한 근거Tab과 스크린 리더가 읽어 주는 차례는 마크업 순서만 따릅니다
  2. order·row-reverse 보이는 자리만 바꿈보이는 자리만 바뀝니다
  3. position 보이는 자리만 바꿈자리를 옮겨도 차례는 그대로입니다
  4. tabindex="0" 초점을 줌초점을 받는 차례는 마크업의 제자리에서 정해집니다
  5. 양수 tabindex 쓰지 않음페이지 전체의 차례를 뒤엎습니다
  6. 두 차례를 맞추는 방법 마크업 수정차례를 맞추는 하나뿐인 방법입니다

두 차례가 어긋나도 마우스로 쓸 때는 전혀 드러나지 않기 때문에, 몇 달이 지나서야 '키보드로 쓰면 버튼 차례가 이상하다'는 제보로 발견되곤 합니다. 확인하는 방법은 간단합니다. Tab을 눌러 초점이 가는 차례와 눈에 보이는 차례가 같은지 보면 됩니다. 특히 반응형 화면에서 단 순서를 뒤집은 자리를 의심하세요. 좁은 화면에서는 맞는데 넓은 화면에서만 어긋나는 일이 흔합니다.

5 쓸 때 / 안 쓸 때

두 차례를 맞추기 위해 할 일

  • 요소의 자리를 바꿀 때. CSS가 아니라 마크업을 바꿉니다
  • 화면을 다 만든 뒤. Tab만 눌러 한 바퀴 돌려 봅니다
  • 반응형에서 단 순서를 바꿨을 때. 좁은 폭과 넓은 폭 모두 확인합니다

두 차례를 어긋나게 만드는 경우

  • order로 버튼 자리를 바꿀 때. Tab 차례는 원래대로 남습니다
  • row-reverse로 오른쪽 정렬을 흉내 낼 때. margin-left:auto로 충분합니다
  • 양수 tabindex로 차례를 고칠 때. 페이지 전체의 차례가 망가집니다
  • position:absolute로 요소를 멀리 옮겨 놓고 마크업은 그대로 둘 때

함께 보면 좋은 항목 — 초점이 무엇인지는 초점에서, 창 안에 초점을 가두는 방법은 초점 갇힘에서, 키보드로 조작하는 방법은 키보드 조작에서 다룹니다. 요소가 위아래로 쌓이는 순서는 겹침 순서에서 봅니다.

6 자주 보는 모습구조만 따라 그린 재현 그림

7 최소 코드와 규칙순서를 다룰 때 지킬 것

보이는 차례와 마크업 차례를 같게 두면 지킬 규칙이 하나로 줄어듭니다.

<!-- 마크업 순서가 Tab 순서다. 보이고 싶은 차례대로 적는다 -->
<div class="row">
  <button class="ghost">취소</button>
  <button>저장</button>
</div>

/* 오른쪽으로 붙인다. 차례는 바뀌지 않는다 */
.row { display: flex; gap: 8px; }
.row .ghost { margin-right: auto; }

/* ✕ 보이는 자리만 뒤집혀서 Tab은 저장부터 간다 */
.row { flex-direction: row-reverse; }
.save { order: -1; }

/* ✕ 페이지 전체 차례를 뒤엎는다 */
<button tabindex="3">
키와 속성초점이 움직이는 방식
Tab마크업 순서로만 이동하고, CSS는 영향을 주지 않습니다
Shift + Tab마크업의 역순으로 이동하며, 눈에 보이는 역순과 다를 수 있습니다
tabindex="0"마크업 자리에서 초점을 받습니다. 권장하는 값입니다
tabindex="-1"Tab으로는 갈 수 없고 focus()로만 초점을 옮길 수 있습니다
양수 tabindex0인 요소들보다 먼저 모두 돌기 때문에 쓰지 않습니다
확인하는 방법주소창에서 Tab을 계속 누르며 초점 테두리를 눈으로 따라갑니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

정렬된 배열로 보내 주기목록 API가 정렬된 배열을 주면 그대로 그려도 차례가 맞습니다. 반면 객체(dict)로 주면 순서가 보장되지 않아 어긋날 수 있습니다.
정렬 기준도 함께 보내기?sort=amount.desc처럼 무엇으로 정렬했는지를 응답에도 담아 주면 화면에서 임의로 다시 정렬하는 일이 없습니다.
실시간으로 줄이 추가될 때실시간으로 새 줄이 끼어들면 초점이 엉뚱한 줄로 옮겨지기 때문에, 줄을 끼워 넣기 전에 초점 위치를 기억해 둡니다.

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

보이는 자리와 초점 차례가 따로 정해진다는 것은 어느 플랫폼에서나 같은 규칙입니다.

웹DOM order
저장1취소2
order·row-reverse·position은 모두 보이는 자리만 바꿉니다.
iOSaccessibilityElements
뷰 계층이 차례를 정합니다. 필요하면 accessibilityElements로 따로 지정합니다.
안드로이드traversalBefore
traversalBefore·traversalAfter로 두 뷰 사이 차례를 국소적으로 바꿉니다.

플랫폼 차이 때문에 자주 생기는 문제 — 앱에는 차례를 따로 지정하는 방법이 있지만 웹에는 사실상 없습니다. 양수 tabindex는 페이지 전체 차례를 바꿔 버려서 쓰지 않기 때문입니다. 그래서 웹에서는 마크업을 올바른 차례로 적는 것이 유일한 방법이고, 달리 보면 지킬 규칙이 하나뿐이라 간단합니다.
