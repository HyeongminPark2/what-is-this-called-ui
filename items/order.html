보이는 순서와 읽는 순서

Visual order vs DOM order

CSS 는 보이는 자리만 바꿉니다. Tab 과 읽어 주는 차례는 끝까지 마크업 순서를 따라갑니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

뒤집는 법을 골라 보고 Tab 으로 훑어보기를 누르세요 — 초점이 간 차례가 적힙니다.
row-reverse나 order로 뒤집으면 눈에는 취소가 먼저인데 Tab 은 저장부터 갑니다. 마우스로 쓰는 사람은 영영 모르고, 키보드로 쓰는 사람에게는 화면이 거짓말을 합니다.
마크업 순서를 바꾸면 둘이 같아집니다 — 유일하게 맞는 방법입니다.

2 이름부르는 말이 여러 개다

한국어보이는 순서와 읽는 순서, 시각 순서와 DOM 순서, 초점 순서
영어visual order, DOM order, focus order, reading order
같이 쓰는 말Tab 이 따라가는 차례가 초점 순서(focus order), 스크린 리더가 읽어 가는 차례가 읽는 순서(reading order)입니다. 둘은 거의 늘 같고, 둘 다 마크업 순서를 따릅니다. 눈에 보이는 차례만 시각 순서(visual order)라고 따로 부릅니다.
자주 잘못 부름z-index — 겹침 순서는 위아래이고, 이건 앞뒤입니다.
order 속성 — order는 이 문제를 만드는 쪽이지 해결하는 쪽이 아닙니다.
tabindex — 초점을 받게 할 뿐, 차례를 고치는 도구가 아닙니다.

한 줄로 — 자리를 바꾸고 싶으면 마크업을 바꾸세요. order와 row-reverse는 눈만 속입니다.

4 어긋나는 꼴눈과 Tab 이 같은가

5 해부도부분 이름이 제일 안 알려진 지식

마크업 순서 — Tab · 읽어 주는 차례의 유일한 근거
order · row-reverse — 보이기만 바꾼다
position 으로 자리 옮기기 — 역시 보이기만
tabindex="0" — 원래 못 받는 것에 초점을 준다
tabindex="3" 같은 양수 — 차례를 뒤엎는다
둘을 맞추는 법 — 마크업을 고친다
  1. 마크업 순서 유일한 근거Tab 과 읽어 주는 차례가 이것만 본다
  2. order·row-reverse 보이기만눈만 바뀐다
  3. position 보이기만자리를 옮겨도 차례는 그대로
  4. tabindex="0" 초점을 준다차례는 제자리에서 생긴다
  5. 양수 tabindex 쓰지 않는다페이지 전체 차례를 뒤엎는다
  6. 맞추는 법 마크업 수정하나뿐인 방법

어긋나도 마우스로는 전혀 드러나지 않습니다. 그래서 몇 달 지나 '키보드로 쓰면 버튼 차례가 이상하다'는 제보로 발견됩니다. 확인은 간단합니다 — Tab 을 눌러 보고 적힌 차례와 눈에 보이는 차례가 같은지 보면 됩니다. 특히 반응형에서 단 순서를 뒤집은 자리를 의심하세요. 좁은 화면에서는 맞는데 넓은 화면에서만 어긋나는 일이 흔합니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 자리를 바꾸려면 마크업을 바꾸기
  • 다 만든 뒤 Tab 만 눌러 한 바퀴 돌려 보기
  • 단 순서를 바꾼 자리는 두 폭 모두 확인하기

이럴 때는 안 쓴다

  • order로 버튼 자리 바꾸기 — Tab 차례가 남는다
  • row-reverse로 '오른쪽 정렬' 흉내 내기 — margin-left:auto면 된다
  • 양수 tabindex로 차례 고치기 — 페이지 전체가 망가진다
  • position:absolute로 멀리 옮겨 놓고 마크업은 그대로 두기

대신 이걸 — 초점 자체는 초점, 갇힘은 초점 갇힘, 키보드 조작은 키보드 조작, 겹침 순서는 겹침 순서.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 코드와 규칙이 순서의 계약서

보이기와 차례를 같이 두면 규칙이 하나로 줄어듭니다.

<!-- 마크업 순서가 Tab 순서다. 보이고 싶은 차례대로 적는다 -->
<div class="row">
  <button class="ghost">취소</button>
  <button>저장</button>
</div>

/* 오른쪽으로 붙이기 — 차례를 안 건드린다 */
.row { display: flex; gap: 8px; }
.row .ghost { margin-right: auto; }

/* ✕ 눈만 뒤집힌다 — Tab 은 저장부터 간다 */
.row { flex-direction: row-reverse; }
.save { order: -1; }

/* ✕ 페이지 전체 차례를 뒤엎는다 */
<button tabindex="3">
키일어나야 하는 일
Tab마크업 순서로만 간다. CSS 는 영향이 없다
Shift + Tab그 역순. 눈으로 보는 역순과 다를 수 있다
tabindex="0"제자리에서 초점을 받는다 — 권장
tabindex="-1"Tab 으로는 못 가고 focus()로만 간다
양수 tabindex0 인 것들보다 먼저 전부 돈다 — 쓰지 않는다
확인하는 법주소창에서 Tab 을 계속 누르며 초점 테두리를 눈으로 따라간다

9 서버 쪽으로 치면백엔드 감각으로 번역

순서대로 보내 준다목록 API 가 정렬된 배열을 주면 그대로 그려도 차례가 맞습니다. 객체(dict)로 주면 순서 보장이 없어 어긋날 수 있습니다.
sort 기준을 같이?sort=amount.desc처럼 무엇으로 정렬했는지를 응답에도 담으면 화면이 임의로 다시 섞지 않습니다.
추가되는 줄실시간으로 줄이 끼어들면 초점이 엉뚱한 줄로 옮겨집니다 — 끼워 넣기 전에 초점 위치를 기억해 둡니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

어디서나 같은 규칙입니다 — 보이기와 차례는 따로 간다.

웹DOM order
저장1취소2
order·row-reverse·position이 전부 보이기만 바꿉니다.
iOSaccessibilityElements
뷰 계층이 차례를 정합니다. 필요하면 accessibilityElements로 따로 지정합니다.
안드로이드traversalBefore
traversalBefore·traversalAfter로 두 뷰 사이 차례를 국소적으로 바꿉니다.

자주 생기는 사고 — 앱 쪽에는 차례를 고쳐 지정하는 길이 있고 웹에는 사실상 없습니다 — 양수 tabindex는 너무 거칠어서 쓰지 않습니다. 그래서 웹에서는 마크업을 옳게 적는 것이 유일한 방법이 되고, 거꾸로 보면 지켜야 할 규칙이 하나뿐이라 간단합니다.
