위험한 동작

Destructive action

삭제처럼 되돌리기 어려운 일을 할 때는, 누르기 전에 되묻는 것보다 누른 뒤에 무를 수 있게 하는 편이 거의 언제나 낫습니다.

① 실물② 이름③ 상태④ 해부도⑤ 쓸 때⑥ 사례⑦ 마크업⑧ 백엔드 메모⑨ 플랫폼

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

네 가지 방식을 바꿔 가며 삭제를 눌러 보세요.
바로 지우기는 손가락이 잘못 닿기만 해도 되돌릴 수 없고, 한 번 되묻기는 세 번째쯤부터 사용자가 문구를 읽지 않고 누릅니다. 이름을 직접 치게 하기는 확실하지만 번거롭습니다.
대개는 되돌릴 틈을 주는 방식이 가장 낫습니다. 묻지 않으니 빠르고, 실수로 지워도 되살릴 수 있기 때문입니다.

2 이름같은 것을 부르는 여러 이름

한국어위험한 동작, 파괴적 동작, 삭제 확인
영어destructive action, confirmation dialog, type-to-confirm
같이 쓰는 말되묻는 창을 확인 다이얼로그라 하고, 지울 대상의 이름을 그대로 치게 하는 방식을 타이프 투 컨펌(type-to-confirm)이라고 합니다. 지운 것을 바로 없애지 않고 잠시 두는 곳은 휴지통·소프트 삭제(soft delete)라 하고, 지운 뒤 되돌릴 틈을 주는 줄은 언두 스낵바라고 부릅니다. 위험한 동작을 설정 맨 아래에 모아 두는 자리는 위험 구역(danger zone)이라고 합니다.
자주 잘못 부르는 이름경고 — 경고는 상황을 알리는 것이고, 위험한 동작의 확인은 실수를 막는 장치입니다.
모달 — 모달은 화면에 띄우는 방식이고, 확인은 그 안에 담는 내용입니다.
되돌리기 — 되돌리기는 확인의 반대말이 아니라 대안입니다. 그래서 둘을 함께 쓰면 지나칩니다.

4 해부도부분마다 붙은 이름

‘정산 내역 128건이 함께’처럼 사라질 것을 적음
되돌릴 수 있는지 없는지 그대로 적음
취소삭제
버튼 이름은 ‘확인’ 대신 ‘삭제’처럼 동사로
되돌리기가 있으면 묻지 않아도 됨
세 번째부터는 읽지 않고 누름
  1. 사라지는 대상 숫자로 적기'정산 내역 128건이 함께'처럼 숫자로 적습니다. 막연하게 적으면 사용자가 읽지 않습니다
  2. 되돌릴 수 있는지 안내 있는 그대로 적기되돌릴 수 있으면 그렇다고 적고, 없으면 없다고 적습니다
  3. 버튼 두 개 취소 · 삭제취소를 기본 버튼으로 두되, 눈에 덜 띄게 만듭니다
  4. 버튼 이름 동사로'확인'이 아니라 '삭제'처럼 버튼을 누르면 무엇을 하는지 적습니다
  5. 되돌리기 묻기의 대안되돌리기가 있으면 묻지 않아도 됩니다. 둘을 함께 쓰면 지나칩니다
  6. 습관적으로 누르기 세 번째부터확인 창을 자주 볼수록 사용자는 읽지 않고 누릅니다

확인 창은 자주 띄울수록 효과가 떨어집니다. 세 번쯤 보고 나면 문구를 읽지 않고 오른쪽 버튼을 누르는 손버릇이 생기고, 그때부터는 확인 창이 있어도 사고가 납니다. 그래서 되돌릴 수 있는 일에는 묻지 말고 되돌리기를 주고, 확인 창은 정말 되돌릴 수 없는 것에만 남겨 두는 편이 좋습니다. 드물게 뜨는 창이어야 사용자가 문구를 읽기 때문입니다.

5 쓸 때 / 안 쓸 때

위험한 동작 앞에서 할 일

  • 되돌릴 수 있는 일일 때. 묻지 말고 되돌리기를 줍니다
  • 되돌릴 수 없는 일일 때. 한 번 묻습니다
  • 큰 것을 지울 때. 이름 치기나 메일 확인을 한 단계 더 둡니다

위험한 동작을 이렇게 다루면 안 되는 경우

  • 모든 동작에 확인 창을 띄울 때. 사용자가 읽지 않고 누르게 됩니다
  • 버튼을 '확인 / 취소'로 적을 때. 무엇을 확인하는지 알 수 없습니다
  • 삭제를 기본 버튼으로 둘 때. 엔터만 눌러도 지워집니다
  • 되돌리기와 확인 창을 둘 다 쓸 때. 번거롭기만 합니다

함께 보면 좋은 항목 — 실수를 막을 필요 없이 상황을 알리기만 하면 되는 경우는 오류 메시지에서, 지운 결과와 되돌리기 줄은 토스트에서 다룹니다. 여러 건을 한꺼번에 지울 때는 일괄 선택의 범위 확인을 함께 봅니다.

6 자주 보는 모습구조만 따라 그린 재현 그림

7 최소 마크업과 키보드구현할 때 지킬 최소 규칙

확인 창은 <dialog>로 만들고 취소를 기본 버튼으로 둡니다.

<dialog id="confirm" aria-labelledby="t" aria-describedby="d">
  <h2 id="t">‘모란상회’를 지울까요?</h2>
  <p id="d">정산 내역 128건이 함께 지워집니다. 되돌릴 수 없습니다.</p>

  <form method="dialog">
    <button value="cancel" autofocus>취소</button>
    <button value="delete" class="danger">삭제</button>
  </form>
</dialog>

// 되돌릴 수 있으면 묻지 말고, 5초 뒤에 진짜로 보낸다
function removeWithUndo(id) {
  hideFromList(id);
  const t = setTimeout(() => api.remove(id), 5000);
  showUndoBar(() => { clearTimeout(t); restore(id); });
}
키와 마크업처리하는 방법
autofocus는 취소 버튼에 두기창이 열리자마자 엔터를 쳐도 지워지지 않습니다
Esc를 누르면 취소<dialog>는 이 동작을 기본으로 제공합니다. 위험한 쪽이 기본 동작이 되면 안 됩니다
aria-describedby무엇이 사라지는지까지 읽히게 합니다. 제목만 읽히면 무엇이 함께 지워지는지 알 수 없습니다
버튼 이름은 동사로 적기'확인'이라고만 적으면 무엇을 확인하는지 알 수 없습니다
되돌리기 줄에 role="status" 달기토스트와 같은 방식으로, 초점을 가져가지 않고 알립니다
되돌리기 버튼까지 갈 시간5초는 키보드·스크린 리더 사용자에게 짧습니다. 그래서 초점이나 마우스가 머무르는 동안에는 시간이 멈추게 합니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

되돌리기는 요청을 늦게 보내는 방식으로화면에서 먼저 지우고 5초 뒤에 서버로 보내면, 되돌리기는 타이머를 취소하는 것만으로 끝납니다. 구현 방법 가운데 가장 간단합니다.
소프트 삭제삭제 요청을 미룰 수 없다면 deleted_at에 시각을 기록해 두고 나중에 실제로 지웁니다. 대신 모든 질의가 그 칸을 확인해야 합니다.
함께 지워지는 데이터가맹점을 지우면 거기에 딸린 정산과 사용자도 같이 지워집니다. 그래서 무엇이 함께 지워지는지 화면 문구에도 적습니다.
삭제 권한을 서버에서 다시 확인하기삭제 권한은 서버에서 다시 확인합니다. 화면에서 버튼을 숨기는 것만으로는 요청을 직접 보내는 사람을 막을 수 없습니다.
삭제 기록 남기기누가 언제 무엇을 지웠는지 기록해 두면 나중에 들어오는 복구 요청에 답할 수 있습니다.
되돌릴 수 없는 삭제에 유예 기간 두기계정이나 조직을 지울 때는 유예 기간(30일)을 두는 편이 민원이 적습니다.

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

플랫폼마다 확인 창의 버튼 순서와 색이 다릅니다. 자세한 차이는 HIG와 Material에서 다룹니다.

웹<dialog>
지울까요?
취소삭제
버튼을 오른쪽 아래에 두고 확인 버튼을 바깥쪽에 놓습니다. 위험한 동작의 버튼은 빨간색으로 칠합니다.
iOSAlert · Action Sheet
지울까요?
취소삭제
버튼 자리를 반반으로 나누고 위험한 쪽을 빨간색으로 표시합니다. 목록에서는 쓸어넘기기로도 지울 수 있습니다.
안드로이드Dialog · 스낵바
1건 삭제됨실행취소
스낵바와 실행취소 조합이 규격에 들어 있고, 되묻기보다 나중에 무르게 하는 방식을 권합니다.

플랫폼 차이 때문에 자주 생기는 문제 — "삭제할 때 한 번 물어봐 주세요"는 가장 쉬운 해결책이지만 효과는 가장 약합니다. 그런 요청을 받으면 그 삭제를 되돌릴 수 있는지부터 따져 보고, 되돌릴 수 있다면 묻지 말고 되돌리기를 주는 쪽으로 바꾸세요. 그러면 화면도 빨라지고 사고도 줄어듭니다. 되돌리기는 나중에 붙이기 가장 어려운 기능이라서, 처음 설계할 때 정해 두는 편이 훨씬 수월합니다.
