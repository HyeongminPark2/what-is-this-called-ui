오프라인

Offline handling

끊긴 동안 쓴 것이 사라지면 그게 가장 큰 사고입니다. 쌓아 뒀다가 연결되면 보냅니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

'연결됨'을 꺼 보세요. 끊긴 동안 저장을 누르면 셋 중 하나가 일어납니다 — 쌓아 두거나, 못 누르게 막거나, 그때마다 실패하거나. 데모가 쌓인 작업 수와 헛되이 실패한 횟수를 세서 적습니다.
다시 연결하면 쌓아 둔 것이 저절로 나갑니다. '그때마다 실패'는 가장 흔하면서 가장 나쁜 쪽입니다 — 쓴 글이 사라지니까요. 읽기는 끊겨도 되게 두는 편이 낫습니다.

2 이름부르는 말이 여러 개다

한국어오프라인, 연결 끊김, 오프라인 지원
영어offline, offline-first, outbox, background sync
같이 쓰는 말보내지 못한 작업을 모아 두는 곳을 아웃박스(outbox)나 큐라 하고, 연결되면 저절로 보내는 것을 백그라운드 동기화라 합니다. 끊겨도 쓸 수 있게 만드는 설계를 오프라인 퍼스트(offline-first)라 부르고, 웹에서 그걸 맡는 장치가 서비스 워커입니다.
자주 잘못 부름재시도 — 재시도는 연결은 있는데 실패했을 때입니다.
캐시 — 캐시는 빠르게 하려고 두는 것이고, 오프라인은 없을 때를 대비하는 것입니다.
에러 상태 — 에러 상태는 더 넓은 말입니다.

3 가르는 기준형제들과 비교하는 네 축

연결이 끊겼을 때 다루는 방법들입니다. 이 네 가지만 물어보면 갈립니다.

쓴 것이 남나읽기는 되나언제 나가나사용자가 아나
쌓아 두기남는다받아 둔 것은 된다연결되면 저절로띠로 알린다
못 누르게 막기해당 없음된다다시 눌러야단추가 꺼져 있다
그때마다 실패사라진다된다다시 써야오류만 뜬다
아무 대비 없음사라진다안 된다—화면이 빈다

한 줄로 — 쓴 것은 절대로 잃지 마세요. 보내는 것은 나중에 해도 됩니다.

4 상태쓴 것이 남는지가 갈린다

5 해부도부분 이름이 제일 안 알려진 지식

끊김 띠 — 화면 꼭대기에 한 줄
쓴 것은 쌓아 둔다 — 사라지지 않게
쌓인 것이 몇 건인지 보인다
읽기는 되게 — 받아 둔 것은 보여 준다
연결되면 저절로 나가고 알린다
그때마다 실패하면 쓴 글이 사라진다
  1. 끊김 띠 꼭대기 한 줄왜 안 되는지를 알린다
  2. 쌓아 두기 쓴 것사라지지 않게
  3. 몇 건인지 보이기기다리는 것이 있다는 신호
  4. 읽기 되게 두기받아 둔 것은 보여 준다
  5. 다시 연결 저절로나갔다고 알린다
  6. 그때마다 실패 가장 나쁨쓴 글이 사라진다

연결이 있다 없다는 생각보다 흐릿합니다 — navigator.onLine 은 '랜선이 꽂혀 있다' 정도만 알려 주고, 인터넷이 실제로 되는지는 모릅니다. 지하철에서 안테나는 떠 있는데 아무것도 안 되는 상태가 그것입니다. 그래서 요청이 실패한 것을 신호로 삼는 편이 더 정확합니다.
쌓아 둔 것을 보낼 때는 차례가 중요합니다 — '만들기' 뒤에 '고치기'가 있었다면 그 순서대로 나가야 하고, 중간에 하나가 실패하면 뒤엣것을 보내면 안 됩니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 쓴 것을 쌓아 두고 연결되면 보내기
  • 읽기는 되게 두기 — 받아 둔 것은 보여 준다
  • 쌓인 것이 몇 건인지 보여 주기

이럴 때는 안 쓴다

  • 끊긴 동안 쓴 글을 버리기
  • navigator.onLine 만 믿기 — 떠 있어도 안 될 수 있다
  • 끊겼다고 읽기까지 막기
  • 쌓인 것을 차례 없이 한꺼번에 보내기

대신 이걸 — 연결은 되는데 실패하면 재시도, 실패 화면은 에러 상태, 기다리는 표시는 스피너, 문구는 오류 문구.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 코드와 규칙이 대비의 계약서

실패를 신호로 삼아 쌓아 두고, 연결되면 차례대로 보냅니다.

<!-- 끊김 띠는 화면 꼭대기에 한 줄 -->
<p role="status" class="offline-bar">
  연결이 끊겼습니다 — 쓴 것은 쌓아 뒀다가 보냅니다 (2건)
</p>

async function send(job) {
  try { await api.post(job); }
  catch (e) {
    outbox.push(job);              // 실패를 신호로 삼는다
    render();
  }
}

window.addEventListener('online', async () => {
  while (outbox.length) {
    await api.post(outbox[0]);   // 차례대로
    outbox.shift();
  }
  announce('쌓아 둔 2건을 보냈습니다');
});
키일어나야 하는 일
role="status"끊김과 복구를 소리로도 알린다
단추 잠금막을 거라면 왜 꺼졌는지를 같이 적는다
online·offline브라우저가 주는 신호. 정확하지는 않다
navigator.onLine'랜선이 꽂혔다'만 안다 — 인터넷은 모른다
서비스 워커탭이 닫혀도 나중에 보낼 수 있는 길
확인하는 법개발자 도구에서 Offline 으로 바꾸고 써 본다

9 서버 쪽으로 치면백엔드 감각으로 번역

멱등 키쌓아 둔 것을 보낼 때 두 번 가는 일이 생깁니다 — 키가 있으면 한 번만 처리됩니다.
차례created_at 이나 순번이 있어야 만든 뒤 고친 차례가 지켜집니다.
충돌끊긴 동안 남이 같은 것을 고쳤으면 어느 쪽을 남길지를 정해야 합니다.
읽기 캐시목록에 ETag 가 있으면 바뀐 것만 받아 옵니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

앱 쪽이 훨씬 잘 되어 있습니다.

웹서비스 워커
● 연결이 끊겼습니다⏳ 메모 1
탭이 열려 있어야 하는 것이 한계입니다. 백그라운드 동기화는 브라우저마다 다릅니다.
iOS로컬 저장 + 동기화
앱이 자기 저장소를 가져 끊겨도 그대로 씁니다. 동기화는 직접 만듭니다.
안드로이드Room + WorkManager
앱이 꺼져 있어도 연결되면 OS 가 대신 보냅니다 — 웹에는 없는 장치입니다.

자주 생기는 사고 — 앱은 자기 저장소를 들고 시작하니 '끊기면 못 쓴다'는 말 자체가 드뭅니다. 웹은 반대로 연결이 기본이라, 끊김 대비를 하려면 품이 많이 듭니다. 그래서 웹에서는 쓴 것만은 잃지 않게 하는 선까지를 현실적인 목표로 잡는 편이 낫습니다 — 그것만 해도 사용자가 겪는 가장 큰 고통이 사라집니다.
