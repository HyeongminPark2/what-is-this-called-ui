오프라인

Offline handling

오프라인 처리는 네트워크 연결이 끊긴 동안 화면이 어떻게 동작할지 정하는 일입니다. 끊긴 동안 사용자가 쓴 내용이 사라지는 것이 가장 큰 사고이므로, 쓴 내용은 쌓아 두었다가 연결되면 보냅니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

'연결됨'을 꺼 보세요. 끊긴 동안 저장을 누르면 방식에 따라 쌓아 두거나, 버튼을 못 누르게 막거나, 누를 때마다 실패하는 세 가지 가운데 하나가 일어납니다. 데모는 쌓인 작업 수와 헛되이 실패한 횟수를 세서 적습니다.
다시 연결하면 쌓아 둔 작업이 저절로 나갑니다. '그때마다 실패'는 가장 흔하면서도 가장 나쁜 방식인데, 사용자가 쓴 글이 사라지기 때문입니다. 그리고 연결이 끊겨도 읽기는 되게 두는 편이 낫습니다.

2 이름같은 것을 부르는 여러 이름

한국어오프라인, 연결 끊김, 오프라인 지원
영어offline, offline-first, outbox, background sync
같이 쓰는 말보내지 못한 작업을 모아 두는 곳은 아웃박스(outbox)나 큐라고 하고, 연결되면 쌓인 작업을 저절로 보내는 것은 백그라운드 동기화라고 합니다. 연결이 끊겨도 쓸 수 있게 만드는 설계는 오프라인 퍼스트(offline-first)라고 부르며, 웹에서 이 일을 맡는 장치가 서비스 워커입니다.
자주 잘못 부르는 이름재시도 — 재시도는 연결은 되어 있는데 요청이 실패했을 때 다시 보내는 것입니다.
캐시 — 캐시는 빠르게 읽으려고 데이터를 두는 것이고, 오프라인 처리는 연결이 없을 때를 대비하는 것입니다.
에러 상태 — 에러 상태는 연결 끊김을 포함해 여러 실패를 아우르는 더 넓은 말입니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

연결이 끊겼을 때 다루는 방법들을 모았습니다. 아래 네 가지를 물어보면 방법마다 차이가 드러납니다.

쓴 것이 남나읽기는 되나언제 나가나사용자가 아나
쌓아 두기남는다받아 둔 것은 된다연결되면 저절로띠로 알린다
못 누르게 막기해당 없음된다다시 눌러야단추가 꺼져 있다
그때마다 실패사라진다된다다시 써야오류만 뜬다
아무 대비 없음사라진다안 된다—화면이 빈다

오프라인을 한 줄로 정리하면 — 오프라인 처리에서는 사용자가 쓴 내용을 절대로 잃지 않게 하는 것이 먼저입니다. 서버로 보내는 일은 연결된 뒤에 해도 됩니다.

4 상태방식마다 다른, 쓴 내용이 남는지 여부

5 해부도부분마다 붙은 이름

끊김 띠 — 화면 꼭대기에 한 줄
쓴 것은 쌓아 둔다 — 사라지지 않게
쌓인 것이 몇 건인지 보인다
읽기는 되게 — 받아 둔 것은 보여 준다
연결되면 저절로 나가고 알린다
그때마다 실패하면 쓴 글이 사라진다
  1. 끊김 띠 꼭대기 한 줄보내기가 왜 안 되는지 알립니다
  2. 쌓아 두기 쓴 것쓴 내용이 사라지지 않게 쌓아 둡니다
  3. 몇 건인지 보이기보내기를 기다리는 작업이 있다는 것을 알립니다
  4. 읽기 되게 두기이미 받아 둔 내용은 보여 줍니다
  5. 다시 연결 저절로쌓인 작업을 보낸 뒤 보냈다고 알립니다
  6. 그때마다 실패 가장 나쁨누를 때마다 실패하면 쓴 글이 사라집니다

연결이 있는지 없는지는 생각보다 판단하기 어렵습니다. navigator.onLine은 '랜선이 꽂혀 있다' 정도만 알려 줄 뿐 인터넷이 실제로 되는지는 알지 못합니다. 예를 들어 지하철에서 안테나는 떠 있는데 아무것도 열리지 않는 상태가 있습니다. 그래서 요청이 실패했다는 사실을 끊김의 신호로 삼는 편이 더 정확합니다.
쌓아 둔 작업을 보낼 때는 순서가 중요합니다. '만들기' 뒤에 '고치기'가 있었다면 그 순서대로 보내야 하고, 중간에 하나가 실패하면 그 뒤의 작업은 보내면 안 됩니다.

6 쓸 때 / 안 쓸 때

오프라인을 쓰는 경우

  • 끊긴 동안 쓴 내용을 쌓아 두었다가 연결되면 보낼 때
  • 끊긴 동안에도 읽기는 되게 둘 때. 이미 받아 둔 내용은 보여 줍니다
  • 쌓인 작업이 몇 건인지 보여 줄 때

오프라인을 쓰지 않는 경우

  • 끊긴 동안 쓴 글을 버릴 때
  • navigator.onLine만 믿을 때. 연결된 것으로 나와도 실제로는 안 될 수 있습니다
  • 연결이 끊겼다고 읽기까지 막을 때
  • 쌓인 작업을 순서 없이 한꺼번에 보낼 때

오프라인 대신 다른 것을 써야 하는 경우 — 연결은 되는데 실패하면 재시도, 실패 화면은 에러 상태, 기다리는 표시는 스피너, 문구는 오류 문구.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 코드와 규칙구현할 때 지킬 최소 규칙

요청이 실패하면 그것을 신호로 삼아 작업을 쌓아 두고, 연결되면 순서대로 보냅니다.

<!-- 끊김 띠는 화면 꼭대기에 한 줄 -->
<p role="status" class="offline-bar">
  연결이 끊겼습니다 — 쓴 것은 쌓아 뒀다가 보냅니다 (2건)
</p>

async function send(job) {
  try { await api.post(job); }
  catch (e) {
    outbox.push(job);              // 실패를 신호로 삼는다
    render();
  }
}

window.addEventListener('online', async () => {
  while (outbox.length) {
    await api.post(outbox[0]);   // 차례대로
    outbox.shift();
  }
  announce('쌓아 둔 2건을 보냈습니다');
});
키와 동작그때 일어나야 하는 일
role="status"연결 끊김과 복구를 스크린 리더로도 알립니다
단추 잠금버튼을 막는다면 왜 꺼졌는지도 함께 적습니다
online·offline브라우저가 보내 주는 신호지만 정확하지는 않습니다
navigator.onLine'랜선이 꽂혔다'는 것만 알 뿐 인터넷이 실제로 되는지는 모릅니다
서비스 워커탭이 닫혀도 쌓인 작업을 나중에 보낼 수 있게 해 줍니다
확인하는 법개발자 도구에서 네트워크를 Offline으로 바꾸고 직접 써 봅니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

멱등 키쌓아 둔 작업을 보내다 보면 같은 요청이 두 번 가는 일이 생기는데, 멱등 키가 있으면 서버가 한 번만 처리합니다.
차례작업에 created_at이나 순번이 있어야 만든 뒤 고친 순서가 지켜집니다.
충돌끊긴 동안 다른 사람이 같은 항목을 고쳤다면 어느 쪽 변경을 남길지 정해야 합니다.
읽기 캐시목록 응답에 ETag가 있으면 바뀐 것만 받아 올 수 있습니다.

10 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

오프라인 대비는 웹보다 네이티브 앱 쪽이 훨씬 잘 갖춰져 있습니다.

웹서비스 워커
● 연결이 끊겼습니다⏳ 메모 1
탭이 열려 있어야 동작한다는 한계가 있고, 백그라운드 동기화 지원은 브라우저마다 다릅니다.
iOS로컬 저장 + 동기화
앱에 자체 저장소가 있어서 연결이 끊겨도 그대로 쓸 수 있습니다. 서버와의 동기화는 직접 만듭니다.
안드로이드Room + WorkManager
앱이 꺼져 있어도 연결되면 OS가 대신 보내 주는데, 웹에는 이런 장치가 없습니다.

플랫폼 차이 때문에 자주 생기는 문제 — 네이티브 앱은 처음부터 자체 저장소를 갖추고 시작하기 때문에 '끊기면 못 쓴다'는 일이 드뭅니다. 반대로 웹은 연결되어 있는 것이 기본이라서 끊김에 대비하려면 품이 많이 듭니다. 그래서 웹에서는 쓴 내용만은 잃지 않게 하는 데까지를 현실적인 목표로 잡는 편이 낫습니다. 그것만 해도 연결이 끊겼을 때 사용자가 겪는 가장 큰 문제인, 쓴 내용을 잃는 일은 막을 수 있습니다.
