비밀번호 칸

Password field

비밀번호 칸을 만들 때는 무엇을 막지 않을지가 핵심입니다. 예를 들어 보안을 위해 붙여넣기를 막으면 사용자가 더 약한 비밀번호를 쓰게 되어 오히려 보안이 약해집니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

붙여넣기를 막으면 비밀번호 관리자를 쓸 수 없어서 사용자가 오히려 약한 비밀번호를 고르게 됩니다. 체크를 끄고 붙여넣어 보면 데모가 막힌 횟수를 세어 줍니다.
대문자·숫자·기호를 모두 넣게 하는 갈래 강제는 Passw0rd! 같은 짧고 뻔한 비밀번호는 통과시키면서 길고 센 한국어 문장은 막습니다. 데모가 같은 비밀번호를 두 규칙으로 각각 판정해 보여 줍니다.
보기 단추는 사용자가 친 비밀번호를 눈으로 확인할 수 있는 유일한 방법입니다.

2 이름같은 것을 부르는 여러 이름

한국어비밀번호 칸, 암호 입력, 패스워드 필드
영어password field, password input, masked input
같이 쓰는 말글자를 점으로 가리는 것은 마스킹, 단추를 눌러 가린 글자를 드러내는 것은 보기 토글(reveal)이라고 부릅니다. 비밀번호 세기를 막대로 보여 주는 것은 스트렝스 미터, 여러 낱말을 이어 만든 긴 비밀번호는 패스프레이즈라고 합니다.
자주 잘못 부르는 이름텍스트 필드 — 텍스트 필드와 같은 태그를 쓰지만 type이 다릅니다.
PIN — 네 자리 숫자 비밀번호는 비밀번호 칸이 아닌 다른 부품으로 만드는 편이 낫습니다.
OTP — 일회용 번호를 받는 칸에는 autocomplete="one-time-code"를 씁니다.

비밀번호 칸을 한 줄로 정리하면 — 비밀번호의 세기는 길이로 판단하세요. 대문자·숫자·기호 같은 갈래를 강제하면 규칙만 겨우 맞춘 짧고 뻔한 비밀번호가 늘어납니다.

4 상태상태마다 달라지는 모습

5 해부도부분마다 붙은 이름

보기 단추는 눈으로 확인할 유일한 방법
세기 막대는 규칙이 아니라 안내
붙여넣기를 막으면 관리자를 못 쓰게 됨
autocomplete로 관리자가 알아보게 함
갈래 강제는 짧고 뻔한 것을 통과시킴
규칙은 치기 전에 적어 둠
  1. 보기 단추 눈으로 확인하기친 비밀번호를 눈으로 확인할 수 있는 유일한 방법입니다
  2. 세기 막대 규칙이 아닌 안내세기를 알려 주는 안내이고, 통과 여부를 정하는 규칙이 아닙니다
  3. 붙여넣기 막지 않기붙여넣기를 열어 두어야 비밀번호 관리자를 쓸 수 있습니다
  4. autocomplete 관리자가 알아봄new-password를 적어 두면 관리자가 새 비밀번호 칸으로 알아봅니다
  5. 갈래 강제 오히려 약해짐짧고 뻔한 비밀번호가 오히려 통과합니다
  6. 규칙 미리 적기규칙은 사용자가 치기 전에 보여 주고, 틀린 뒤에 처음 알리지 않습니다

대문자·숫자·기호를 꼭 넣으라는 규칙은 오래 쓰였지만 지금은 권하지 않습니다. 사람들이 Password1!이나 Qwer1234!처럼 규칙을 최소한으로만 맞춘 비밀번호를 만들기 때문입니다. 그보다는 길이를 기준으로 삼고, 이미 유출된 비밀번호 목록과 대조하는 편이 실제로 비밀번호를 세게 만듭니다.
붙여넣기를 막는 것도 보안을 위한 조치처럼 보이지만, 관리자가 만들어 주는 20자짜리 무작위 비밀번호를 쓸 수 없게 되기 때문에 사용자는 결국 외우기 쉬운 약한 비밀번호를 고르게 됩니다.

6 쓸 때 / 안 쓸 때

비밀번호 칸을 쓰는 경우

  • 비밀번호 세기를 길이로 판단하기
  • 보기 단추를 두고 aria-pressed로 눌린 상태 알리기
  • autocomplete="new-password"를 적어 관리자가 알아보게 하기

비밀번호 칸을 쓰지 않는 경우

  • 붙여넣기 막기. 비밀번호 관리자를 쓸 수 없게 됩니다
  • 대문자·숫자·기호 갈래를 강제하기. 규칙만 맞춘 짧고 뻔한 비밀번호가 늘어납니다
  • 규칙을 사용자가 틀린 뒤에 처음 알리기
  • 최대 길이를 짧게 두기. 20자짜리 비밀번호도 못 넣는 칸이 많습니다

비밀번호 칸 대신 다른 것을 써야 하는 경우 — 글자를 가릴 필요가 없는 한 줄 글이면 텍스트 필드를 씁니다. 비밀번호 규칙을 어떻게 검사할지는 입력 검증에서, 로그인 화면 전체를 어떻게 짤지는 로그인에서, 틀렸을 때 보여 줄 문구는 오류 문구에서 다룹니다.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 마크업과 키보드구현할 때 지킬 최소 규칙

autocomplete를 알맞게 적는 것만으로 비밀번호 관리자가 칸을 알아보고 채워 주기 때문에, 코드에서 가장 큰 차이를 만드는 부분입니다.

<label for="pw">새 비밀번호</label>
<input id="pw" type="password"
       autocomplete="new-password"      <!-- 로그인이면 current-password -->
       minlength="12" aria-describedby="pw-rule">
<button type="button" aria-pressed="false"
        aria-label="비밀번호 보기">보기</button>
<p id="pw-rule">12자 이상이면 되고, 길수록 셉니다</p>

// ✕ 붙여넣기를 이렇게 막지 않는다
input.addEventListener('paste', e => e.preventDefault());
키와 마크업그때 일어나야 하는 일
autocomplete새 비밀번호 칸에는 new-password, 로그인 칸에는 current-password를 구분해 적습니다
aria-pressed보기 단추가 눌린 상태인지 알립니다
aria-describedby비밀번호 규칙 안내를 칸과 연결해 둡니다
Caps LockCaps Lock이 켜져 있으면 알려 주는 편이 좋습니다
minlength브라우저가 길이를 검사해 줍니다
확인하는 방법비밀번호 관리자로 채워 보고, 직접 붙여넣어 봅니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

화면과 서버의 규칙 맞추기화면에서 검사하는 규칙과 서버의 규칙이 다르면, 화면에서는 통과했는데 서버에서 거절당하는 일이 생깁니다.
유출된 비밀번호 목록과 대조하기널리 유출된 비밀번호 목록과 대조하는 방법이 갈래 규칙보다 훨씬 효과가 큽니다.
최대 길이를 넉넉하게 두기최대 길이를 짧게 두지 말고 64자 이상을 받는 편이 안전합니다.
로그인에 실패했을 때 알리는 문구로그인에 실패하면 '아이디 또는 비밀번호가 다릅니다'라고 적어 둘 중 어느 쪽이 틀렸는지 숨깁니다. 자세한 내용은 로그인 항목에 있습니다.

Autofill 서비스가 같은 일을 하는데, 칸에 자동 채움 힌트를 적어 두어야 비밀번호 칸으로 알아봅니다.

플랫폼 차이 때문에 자주 생기는 문제 — 세 플랫폼 모두 비밀번호 관리자가 일하기 쉽도록 바뀌어 왔습니다. 사람이 외워서 만든 비밀번호보다 기계가 만든 긴 비밀번호가 훨씬 세기 때문입니다. 그런데 붙여넣기를 막으면 관리자가 만든 비밀번호를 넣을 수 없으니 플랫폼이 가는 방향과 반대로 가게 됩니다. 요즘은 비밀번호 자체를 없애는 패스키로 옮겨 가는 중이라서, 새로 만드는 화면이라면 패스키 로그인을 함께 두는 것도 생각해 볼 만합니다.
