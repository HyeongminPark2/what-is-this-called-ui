z-index

z-index · stacking order

겹친 것들의 앞뒤 순서. 아무 숫자나 쓰는 칸이 아니라, 미리 정해 둔 층의 사다리입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

100·300·500처럼 사이를 띄워 두면 나중에 한 층을 끼워 넣을 자리가 남습니다.
아무 값이나 쓰기를 켜면 토스트가 9999가 됩니다. 당장은 맨 위로 오지만, 다음 사람은 99999를 쓰게 되고 결국 아무도 순서를 설명할 수 없게 됩니다. 여기서는 모달이 가림막에 덮여 글자가 안 읽히는 것으로 보여 줍니다.

2 이름부르는 말이 여러 개다

한국어z-인덱스, 쌓임 순서, 층 순서
영어z-index, stacking order, stacking context, layer
같이 쓰는 말앞뒤 비교가 일어나는 울타리를 쌓임 맥락(stacking context)이라 합니다. 같은 맥락 안에서 번호 없이 늘어선 순서는 그리는 순서(painting order)이고, 미리 정해 둔 층 목록은 보통 레이어 스케일 또는 z 스케일이라 부릅니다.
자주 잘못 부름고도 — 고도는 보이는 높이(그림자), z-index 는 그리는 순서입니다. 그림자가 커도 순서가 밀리면 아래에 깔립니다.
레이어 — 디자인 도구의 레이어 패널과는 다릅니다. 브라우저의 순서는 맥락 안에서만 비교됩니다.
position — position이 static이면 z-index 는 아예 안 먹습니다.

3 가르는 기준형제들과 비교하는 네 축

토큰은 눈에 보이는 부품이 아니라 값의 약속입니다. 이 네 가지만 물어보면 어떤 약속인지 갈립니다.

무엇을 정하나몇 단이 좋나바꾸면 어디가 바뀌나틀렸을 때 증상
색 토큰색의 쓰임쓰임 10여 개브랜드 색 전체같은 파랑이 화면마다 조금씩 다르다
다크 모드두 벌의 값2벌(+고대비)화면 전체의 바탕과 글자흰 상자 하나가 혼자 남아 눈을 찌른다
타입 스케일글자 크기 단계6~8단제목과 본문의 크기뭐가 더 중요한지 안 읽힌다
간격 체계여백의 단위6~8단(4·8의 배수)모든 패딩과 줄 간격뭐라 집어 말하기 어려운데 어수선하다
고도그림자의 세기4~5단떠 있는 부품들무엇이 위에 있는지 안 보인다
z-index쌓이는 순서5~6층겹치는 것들의 앞뒤토스트가 모달에 가려 안 보인다

한 줄로 — z-index 는 숫자 싸움이 아니라 층 이름입니다. 9999가 보이면 그 화면에는 이미 사다리가 없는 것입니다.

4 층숫자가 아니라 이름으로 부른다

5 해부도부분 이름이 제일 안 알려진 지식

부모에 transform이 걸려 있으면 여기서 새 맥락이 시작됩니다
transform: translateZ(0)
자식 · z-index: 9999
형제 · z-index: 1 — 이쪽이 위에 그려집니다
  1. 맥락 밖 outer context여기서는 번호가 같은 울타리 안의 것들끼리만 비교된다
  2. 쌓임 맥락 stacking context이 울타리 안의 자식은 아무리 커도 울타리를 못 넘는다
  3. 맥락을 만드는 속성 transform · opacity · filtertransform, opacity가 1 미만, filter, will-change, position: fixed 등이 새 울타리를 만든다
  4. 갇힌 자식 z-index: 99999999 라도 부모 울타리 안에서만 9999 다
  5. 바깥 형제 z-index: 1울타리 바깥의 1 이 안쪽의 9999 를 이긴다. 이것이 'z-index 가 안 먹어요'의 정답

드롭다운이 카드에 가려 안 보이는 사고의 거의 전부가 이것입니다. 부모 어딘가에 transform이나 opacity: .99가 걸려 있는 것이지요. 숫자를 올려서는 절대 안 고쳐집니다. 해결은 두 가지입니다 — 맥락을 만드는 속성을 없애거나, 그 부품을 <body> 바로 밑으로 옮기는 것입니다(포털 · popover 속성).

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 겹쳐 뜨는 부품이 둘 이상 있을 때 — 모달과 토스트가 함께 있는 화면
  • 붙박이 머리말이 다른 것에 가릴 때
  • 층 목록을 한 파일에 모아 둘 때

이럴 때는 안 쓴다

  • 본문 요소에 번호를 주는 것 — 대부분은 번호 없이 그리는 순서로 충분합니다
  • 급해서 숫자를 올리는 것 — 다음 사람이 더 올립니다. 한 번도 해결된 적이 없습니다
  • 999·9999 같은 값 — 사다리를 못 쓰게 만듭니다
  • 맥락이 다른데 숫자로 맞추려는 것 — 원인이 다른 데 있습니다

대신 이걸 — 떠 있어 보이게 하는 일은 고도가 맡고, 어떤 것이 뒤를 막는지는 모달·토스트에 정리돼 있습니다.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 코드와 규칙이 사다리의 계약서

층을 이름으로 두고 그 이름만 씁니다. 숫자를 직접 적는 곳이 한 군데라도 생기면 사다리가 무너집니다.

:root {
  --z-sticky: 100;
  --z-dropdown: 300;
  --z-scrim: 500;
  --z-modal: 600;
  --z-toast: 800;
}

/* position 이 static 이면 z-index 는 아무 일도 하지 않는다 */
.site-header { position: sticky; z-index: var(--z-sticky); }
.toast-area  { position: fixed;  z-index: var(--z-toast); }

// 맥락에 갇히지 않으려면 body 밑으로 옮긴다(포털)
document.body.appendChild(toastEl);

/* 또는 브라우저에 맡긴다 — 최상위 레이어로 올라간다 */
<dialog>, [popover]
규칙지켜야 하는 것
층을 먼저 정한다다섯~여섯 층이면 충분하다. 사이를 100씩 띄워 끼울 자리를 남긴다
숫자를 직접 안 쓴다var(--z-modal)만 쓴다. 숫자가 보이면 리뷰에서 막는다
position을 함께static에서는 z-index 가 무시된다. 가장 흔한 '안 먹어요'의 두 번째 원인
맥락을 의심한다안 먹으면 숫자를 올리지 말고 부모의 transform · opacity · filter를 찾는다
가림막과 모달은 한 칸 차이500 과 600 처럼 붙여 둔다. 사이에 다른 것이 끼면 반드시 사고가 난다
<dialog>·popover 를 먼저브라우저가 최상위 레이어에 그려 줘서 맥락 문제 자체가 없어진다

9 서버 쪽으로 치면백엔드 감각으로 번역

z 스케일 = 우선순위 상수미들웨어 순서나 이벤트 핸들러 우선순위와 같은 꼴입니다. 비어 있는 값을 남겨 두는 이유도 같습니다 — 나중에 끼워 넣으려고.
왜 9999 가 생기나급할 때 가장 싼 해결이기 때문입니다. 코드 리뷰에서 숫자 리터럴을 막는 규칙 하나가 이 문제의 대부분을 없앱니다.
서드파티 위젯채팅 상담, 결제창 같은 외부 스크립트가 제멋대로 큰 값을 씁니다. 우리 층 사다리의 천장을 그보다 높게 잡거나, 해당 구역을 따로 감쌉니다.
디버깅브라우저 개발자 도구의 Layers 패널에서 맥락을 볼 수 있습니다. 숫자를 바꿔 보기 전에 여기를 먼저 열면 시간이 줄어듭니다.
