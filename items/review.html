디자인 리뷰

Design review

디자인 리뷰는 시안을 두고 의견을 주고받는 자리입니다. 리뷰가 쓸모 있으려면 시안의 단계에 맞는 질문을 하고, 듣는 사람이 바로 고칠 수 있는 말투로 의견을 줘야 합니다.

① 실물② 이름③ 상태④ 해부도⑤ 쓸 때⑥ 사례⑦ 마크업⑧ 백엔드 메모⑨ 플랫폼

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

단계를 바꿔 가며 보세요. 같은 말이라도 어떤 단계에서는 쓸모 있지만, 다른 단계에서는 너무 이르거나 너무 늦습니다.
“이건 아닌 것 같아요”처럼 어느 단계에서 들어도 고칠 수 없는 말도 있는데, 무엇이 걱정인지가 빠져 있기 때문입니다.

2 이름같은 것을 부르는 여러 이름

한국어디자인 리뷰, 시안 리뷰, 크리틱, 피드백
영어design review, design critique, feedback round
같이 쓰는 말여럿이 모여 시안을 함께 보는 자리를 크리틱(critique)이라고 하고, 고쳐야 할 것을 적어 돌려주는 것을 피드백이라고 합니다. 꼭 고쳐야 하는 것과 참고할 의견을 가려 블로커와 논블로커로 나누기도 합니다. 리뷰에서 정한 것을 적어 두는 글은 결정 기록(decision log)이라고 부릅니다.
자주 잘못 부르는 이름승인 — 시안을 통과시키는 절차이고, 리뷰는 고칠 거리를 찾는 자리입니다.
QA — 다 만든 뒤에 기능이 되는지 안 되는지를 확인하는 일이라서 시안을 두고 하는 리뷰와 다릅니다.
보고 — 결과를 보여 주는 자리와 의견을 물어보는 자리는 준비할 것이 다릅니다.

3 말이 맞는 리뷰 단계단계에 따라 달라지는 말의 쓸모

4 해부도부분마다 붙은 이름

무엇을 봐 달라는지 단계부터 밝힘
구조는 와이어프레임에서 · 색은 시안에서
“왜 이렇게 했나요”는 설명을 끌어냄
“이건 아닌 것 같아요”는 방어를 끌어냄
무엇이 걱정인지를 적으면 고칠 거리가 됨
두 번 논의하지 않게 정한 것을 적어 둠
  1. 단계 밝히기 무엇을 봐 주세요단계를 밝히지 않으면 보는 사람은 그림에서 눈에 보이는 것을 말하게 됩니다
  2. 단계에 맞는 질문 구조 / 마감 / 동작단계보다 이르거나 늦은 의견은 반영되지 못하고 버려집니다
  3. 왜 이렇게 했나요 설명을 끌어냄디자인에는 대개 이유가 있으니 먼저 그 이유를 묻습니다
  4. 이건 아닌 것 같아요 방어를 끌어냄이 말에는 무엇이 걱정인지가 빠져 있습니다
  5. 걱정 적기 고칠 거리'글이 길어지면 깨질 것 같다'처럼 걱정을 적으면 고칠 거리가 됩니다
  6. 정한 것 적어 두기 결정 기록정한 것을 적어 두어야 같은 문제를 두 번 논의하지 않습니다

리뷰에서 가장 쓸모 있는 말은 '무엇이 걱정인지'를 밝힌 말입니다. 예를 들어 '이 버튼이 눈에 안 띄어요'보다 '이게 주 동작인데 취소와 같은 무게라 헷갈릴 것 같아요'라고 해야 고칠 거리가 됩니다. 앞의 말은 개인 취향으로도 들리지만, 뒤의 말은 해결해야 할 문제를 짚기 때문입니다. 코드 리뷰에서 '이 코드 이상해요'보다 '여기서 null이 오면 터질 것 같아요'가 나은 것도 같은 이유입니다.

5 쓸 때 / 안 쓸 때

디자인 리뷰에서 지킬 것

  • 리뷰를 요청할 때 단계와 질문을 먼저 밝힙니다
  • 걱정을 구체적으로 적습니다
  • 정한 것을 그 자리에서 적어 둡니다

디자인 리뷰에서 피할 것

  • 단계를 밝히지 않고 그림만 올릴 때
  • 취향으로 말할 때. 대신 그 디자인이 무엇을 해치는지를 적습니다
  • 한 번에 스무 가지를 지적할 때. 너무 많으면 결국 아무것도 고쳐지지 않습니다
  • 정한 것을 적어 두지 않을 때. 같은 이야기가 다음 회의에 또 나옵니다

관련 주제는 다른 항목에서 다룹니다 — 그림의 단계 구분은 와이어프레임과 목업과 시안에서, 시안을 개발 쪽에 넘기는 일은 핸드오프에서, 시안 파일이 바뀌어 온 기록은 버전 관리에서 다룹니다.

7 주고받을 때의 규칙요청할 때와 돌려줄 때 적을 것

리뷰를 요청할 때와 의견을 돌려줄 때 각각 적어야 할 것이 정해져 있습니다.

# 리뷰를 요청할 때
단계   : 시안
봐 주실 것: 주 동작이 눈에 띄는지 · 대비가 충분한지
이미 정한 것: 구조와 정보 순서 (지난주 확정)
기한   : 11월 16일까지

# 의견을 줄 때 — 무엇이 걱정인지를 적는다
○ 주 동작인데 취소와 무게가 같아 보입니다. 잘못 누를 것 같아요.
○ 회색 글씨가 3.1:1 로 보입니다. 4.5:1 을 못 넘깁니다.
✕ 이건 좀 아닌 것 같아요.
✕ 제 취향은 아닌데요.

# 정한 것은 그 자리에서 적는다
11-14 주 동작은 칠한 버튼, 취소는 테두리만. (홍길동·김철수 합의)
지킬 규칙그렇게 하는 이유
단계와 질문 먼저 밝히기'무엇을 봐 주세요'라는 요청이 없으면 보는 사람은 그림에서 눈에 보이는 것을 말하게 됩니다
이미 정한 것 적기이미 정한 것을 적어 두면 그 내용이 다시 논의되지 않습니다
걱정을 구체적으로 적기'눈에 안 띈다'보다 '잘못 누를 것 같다'처럼 생길 문제를 적습니다
대비비처럼 잴 수 있는 것으로 말하기대비비처럼 숫자로 말하면 취향을 두고 다툴 일이 없습니다
지적 개수 줄이기스무 가지를 한꺼번에 주면 아무것도 고쳐지지 않으니 중요한 세 가지만 고릅니다
결정 기록 남기기결정 기록이 없으면 같은 안건으로 회의를 두 번 하게 됩니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

개발 쪽 질문은 일찍 하기'이 값은 서버에 있나요' 같은 질문은 와이어프레임 단계에서 일찍 물을수록 고치는 비용이 적게 듭니다.
빠진 화면 지적하기빈 화면과 로딩, 오류 화면은 시안에 거의 없습니다. 리뷰에서 지적하지 않으면 핸드오프 때 다시 문제가 됩니다.
만들 수 있는지 미리 따지기'이 애니메이션은 매 프레임 배치를 다시 합니다' 같은 지적이 시안 단계에서 나오면, 만들고 나서 고치는 것보다 훨씬 적은 품으로 해결할 수 있습니다(무엇을 움직이나 참고).

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

디자인 리뷰의 요령은 플랫폼과 상관없이 같고, 코드 리뷰의 요령과도 같습니다.

웹코드 리뷰와 같은 요령
○ “여기서 null 이 오면 터질 것 같아요”
같은 말투
'무엇이 걱정인지'를 적는다는 점에서 코드 리뷰의 요령과 같습니다.
iOS웹과 같은 규칙
단계 · 질문 · 기한
OS 관례를 지적할 때 HIG의 어느 대목에 근거하는지 함께 적으면 논쟁이 짧아집니다.
안드로이드웹과 같은 규칙
단계 · 질문 · 기한
Material 규격도 마찬가지로, 규격의 어느 대목인지 근거를 적으면 취향을 두고 다투지 않게 됩니다.

플랫폼 차이 때문에 자주 생기는 문제 — 리뷰가 길어지는 이유는 대개 단계를 밝히지 않아서입니다. 단계를 모르니 구조를 묻는 자리에서 색 이야기가 나오고, 색을 정하는 자리에서 구조 이야기가 나옵니다. 리뷰를 요청할 때 "이번에는 이것만 봐 주세요"라는 한 줄만 적어도 회의 시간이 눈에 띄게 줄어듭니다.
