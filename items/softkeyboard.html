폰 키보드

Software keyboard

폰 키보드는 화면의 절반을 덮습니다. 그 아래 있던 것은 전부 사라집니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

입력칸 누르기로 키보드를 올려 보세요. 한글 키보드는 자동완성 줄까지 더해 화면의 절반을 덮습니다.
기본 상태에서는 저장 버튼이 키보드 뒤에 숨습니다 — 글자는 쳤는데 보낼 수가 없습니다. visualViewport 로 따라 올리기를 켜면 바닥에 붙은 것이 키보드 위로 올라옵니다.

2 이름부르는 말이 여러 개다

한국어폰 키보드, 소프트 키보드, 가상 키보드, 화상 키보드
영어software keyboard, on-screen keyboard, virtual keyboard, IME
같이 쓰는 말브라우저 창 안에서 실제로 보이는 영역이 비주얼 뷰포트(visual viewport)이고 window.visualViewport로 읽습니다. 한글·일본어처럼 글자를 조합해 넣는 장치가 IME(입력기)이고, 조합 중에 오는 이벤트가 compositionstart·compositionend입니다. 엔터 키에 적히는 말을 정하는 것이 enterkeyhint입니다.
자주 잘못 부름뷰포트 — 뷰포트 단위의 dvh로는 키보드가 안 잡힙니다. 다른 문제입니다.
리사이즈 — 키보드가 올라와도 window.resize가 안 오는 기기가 있습니다.
키보드 조작 — 키보드 조작은 PC 의 Tab·Enter 이야기라 완전히 다릅니다.

3 가르는 기준형제들과 비교하는 네 축

PC와 폰은 다른 기계가 아니라 다른 전제입니다. 이 네 가지만 물어보면 갈립니다.

무엇이 다른가폰에서는PC에서는안 챙기면
브레이크포인트폭에 따른 배치한 단여러 단중간 폭에서 깨진다
터치 타깃누를 수 있는 넓이44px 이상24px도 된다옆 것이 눌린다
호버가 없는 세계올려놓기가 되나없다있다영영 못 보는 정보가 생긴다
시스템 백뒤로 가는 길OS가 준다브라우저 버튼모달 대신 앱이 나간다
화면 밀도1px 의 실제 화소 수2~3배1~2배그림이 뭉갠다
뷰포트 단위100vh 가 가리키는 높이주소창 때문에 흔들린다고정바닥 버튼이 잘린다
폰 키보드올라오는 자리화면 절반없다입력칸이 가려진다
HIG와 Material의 차이OS 의 말투각자 다르다웹 관례어느 쪽에서도 어색하다

한 줄로 — 키보드는 창 크기를 바꾸지 않습니다. 그래서 position: fixed로 바닥에 붙인 것은 그대로 키보드 뒤에 깔립니다.

4 키보드가 올라오면무엇이 가려지나

5 해부도부분 이름이 제일 안 알려진 지식

키보드가 화면의 절반을 덮는다 (자동완성 줄 포함)
position: fixed 는 키보드를 모른다 — 뒤에 깔린다
visualViewport.height — 지금 보이는 높이
바닥 버튼을 그만큼 올린다
inputmode · enterkeyhint — 키보드 모양을 정한다
초점이 간 칸은 scrollIntoView 로 끌어 올린다
  1. 덮는 높이 화면의 45~55%한글은 자동완성 줄까지 붙어 더 높다
  2. fixed 는 모른다 position: fixed창 크기가 안 바뀌어서 그대로 깔린다
  3. 지금 보이는 높이 visualViewport.height유일하게 믿을 만한 값
  4. 올려 주기 bottom: 덮인 높이바닥에 붙은 것을 그만큼 올린다
  5. 키보드 모양 inputmode · enterkeyhint숫자 칸에 글자 키보드가 뜨면 짜증 난다
  6. 초점 따라가기 scrollIntoView치고 있는 칸이 안 보이면 아무 소용 없다

기기마다 다르게 움직입니다. 안드로이드 크롬은 기본적으로 창을 줄여 resize를 보내지만, iOS 사파리는 창 크기를 그대로 두고 안쪽만 밀어 올립니다. 그래서 window.innerHeight로 재면 iOS 에서 아무 변화가 없습니다. visualViewport만이 두 곳에서 같은 답을 주고, 이 한 가지가 "내 폰에서는 되는데"라는 말이 나오는 가장 흔한 이유입니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 바닥에 버튼이 붙는 폼 — 가장 자주 당한다
  • 채팅처럼 입력칸이 아래에 있는 화면
  • 긴 폼 — 초점 간 칸을 보이게 끌어 올린다

이럴 때는 안 쓴다

  • 100dvh면 해결된다고 믿기 — 키보드는 다른 문제다
  • window.resize만 듣기 — iOS 에서 안 온다
  • 숫자 칸에 글자 키보드 — inputmode 한 줄이면 된다
  • 키보드를 강제로 내리기 — 치려는 사람을 막는다

대신 이걸 — 화면 높이 자체는 뷰포트 단위, 칸 묶음은 폼 설계, 바닥 고정은 스티키.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 코드와 규칙이 키보드의 계약서

visualViewport로 재서 바닥에 붙은 것을 올립니다.

<input inputmode="numeric" enterkeyhint="next"
       autocomplete="tel" name="phone">

// 키보드가 덮은 높이를 잰다 — 두 OS 에서 같은 답
const vv = window.visualViewport;
function fit() {
  const covered = window.innerHeight - vv.height - vv.offsetTop;
  document.documentElement.style.setProperty('--kbd', Math.max(covered, 0) + 'px');
}
vv.addEventListener('resize', fit);
vv.addEventListener('scroll', fit);
fit();

/* 바닥 막대를 그만큼 올린다 */
.cta-bar { position: fixed; bottom: calc(var(--kbd, 0px) + env(safe-area-inset-bottom)); }
키일어나야 하는 일
inputmodenumeric·tel·email·decimal. 키보드 모양만 바꾼다
type과 다르다type="number"는 값까지 숫자로 다뤄 앞의 0 이 사라진다. 전화번호·계좌는 inputmode만
enterkeyhintnext·done·send. 엔터 키에 적히는 말이 바뀐다
autocomplete이름·전화·주소. 폰에서 효과가 가장 큰 한 줄이다
한글 조합 중compositionstart~compositionend 사이에는 input마다 검사하지 않는다 — 조합 중인 글자가 틀렸다고 뜬다
env(safe-area-inset-bottom)키보드 높이와 함께 더한다. 세이프 에어리어

9 서버 쪽으로 치면백엔드 감각으로 번역

검증 시점한글 조합 중에 서버로 확인 요청을 보내면 미완성 글자가 갑니다. compositionend 뒤에 보냅니다.
자동완성 값브라우저가 채운 값은 input 이벤트 없이 들어오기도 합니다. 제출 시점에 다시 읽습니다.
폰 입력은 짧다키보드가 불편해 사람들이 덜 적습니다. 긴 메모 칸은 폰에서 거의 비어 옵니다 — 필수로 두지 않습니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

덮는 방식이 OS 마다 달라 같은 코드가 다르게 움직입니다.

웹visualViewport
창 크기가 바뀌는지 아닌지가 브라우저마다 다릅니다. visualViewport만 양쪽에서 같습니다.
iOS창을 안 줄인다
창 크기는 그대로 두고 안쪽만 밀어 올립니다. innerHeight로는 아무 변화가 없습니다.
안드로이드창을 줄인다
기본적으로 창을 줄여 resize를 보냅니다. 앱에서는 windowSoftInputMode로 고릅니다.

자주 생기는 사고 — "폰에서 저장 버튼이 안 보여요"는 PC 에서 재현이 안 됩니다. 개발자 도구의 기기 흉내 모드에도 키보드는 안 뜹니다. 입력칸이 있는 화면은 실제 폰에서 한 번 열어 보는 것 말고는 확인할 길이 없고, 그 한 번에 대부분이 걸립니다.
