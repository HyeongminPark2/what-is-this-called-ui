2 이름같은 것을 부르는 여러 이름

한국어결제 흐름, 주문하기, 체크아웃
영어checkout, checkout flow, payment flow
같이 쓰는 말모든 입력을 한 화면에 넣는 방식을 원페이지 체크아웃, 여러 화면으로 나눈 방식을 멀티스텝이라고 합니다. 가입하지 않고 사는 것은 게스트 체크아웃이라 하고, 중간에 떠나서 장바구니만 남는 것은 장바구니 이탈(cart abandonment)이라고 합니다. 같은 요청이 두 번 와도 한 번만 처리되게 하려고 요청마다 붙이는 고유한 값을 멱등 키(idempotency key)라고 부릅니다.
자주 잘못 부르는 이름결제 — 카드 승인만 가리킬 때도 있고 흐름 전체를 가리킬 때도 있으므로, 어디까지를 말하는지 먼저 정하고 씁니다.
장바구니 — 장바구니는 상품을 담아 두는 곳이고, 결제 흐름은 그다음 단계입니다.
폼 — 결제 흐름은 폼 여러 개가 이어진 모양이지만, 돈과 재고가 걸려 있어서 다루는 법이 다릅니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

화면 단위 패턴은 부품 하나가 아니라 사용자가 끝내야 하는 일 하나를 기준으로 나눕니다. 그래서 아래 네 가지를 따져 보면 화면끼리 구별할 수 있습니다.

사용자가 끝내야 하는 일사용자가 자주 막히는 곳중간에 떠나면 생기는 일서버가 맡아 두는 것
로그인내가 누구인지 증명하기비밀번호를 잊음아무 일도 일어나지 않음세션 · 토큰

파일 올리기파일을 건네주기다 올리고 거절당함올리던 파일이 사라짐크기 · 형식 · 보관

결제 흐름을 한 줄로 정리하면 — 비용을 숨기지 말고, 결제 버튼이 두 번 눌리는 일을 막으세요. 숨긴 비용은 이탈로 이어지고, 두 번 눌린 결제는 환불 처리로 이어집니다.

4 결제 흐름의 단계사용자가 어디서 떠나는가

5 해부도부분마다 붙은 이름

✓장바구니2배송3결제4완료
배송비를 포함한 금액이 처음부터 끝까지 보임
이전으로 가도 적은 값이 남음
결제 버튼은 누르는 순간 잠김
같은 주문 키로 두 번 와도 한 건만 만듦
마지막에 드러난 비용이 가장 큰 이탈 이유
  1. 단계 표시 2 / 4남은 단계가 몇 개인지 보여야 사용자가 끝까지 갑니다
  2. 금액 처음부터 끝까지배송비·수수료까지 포함해 보여 줍니다. 이 비용이 마지막에야 드러나면 사용자가 떠납니다
  3. 되돌아가기 적은 값 유지앞 단계를 고치러 갔다 와도 다시 입력하지 않게 합니다
  4. 버튼 잠그기 누르는 순간버튼이 두 번 눌리면 결제가 두 건 생기므로 누르는 순간 잠급니다
  5. 멱등 키 같은 주문은 한 건만화면에서 막지 못한 중복 요청도 서버에서 걸러 냅니다
  6. 뒤늦은 비용 가장 큰 이탈 이유배송비·수수료·필수 가입처럼 마지막에 나타나는 부담이 주된 이탈 이유입니다

중복 결제는 화면만으로는 막을 수 없습니다. 버튼을 잠가도 네트워크가 끊겼다가 재시도되거나, 사용자가 새로고침하거나, 뒤로 갔다가 다시 보내면 요청이 두 번 가기 때문입니다. 그래서 화면은 주문마다 고유한 키를 하나 만들어 요청과 함께 보내고, 서버는 같은 키로 두 번째 요청이 오면 첫 번째 결과를 그대로 돌려줍니다. 이렇게 하면 요청을 몇 번 보내도 주문은 한 건만 생기므로, 결제 흐름에는 이 장치를 반드시 넣어야 합니다.

6 쓸 때 / 안 쓸 때

결제 흐름을 여러 단계로 나누는 경우

  • 돈·재고가 걸린 여러 단계 흐름일 때
  • 입력이 많아 한 화면에 다 들어가지 않을 때
  • 중간에 떠난 사람이 돌아올 수 있어야 할 때

결제 흐름을 잘못 만드는 경우

  • 비용을 마지막에 드러낼 때
  • 사려면 가입부터 하게 할 때. 가입하지 않고도 게스트로 살 수 있게 둡니다
  • 이전 단계로 돌아가면 적은 값이 지워질 때
  • 버튼만 잠그고 서버 쪽 장치를 만들지 않을 때

함께 보면 좋은 항목 — 입력 칸을 묶는 방법은 폼 설계에서, 입력값을 검사하는 방법은 입력 검증에서 다룹니다. 결제 결과를 짧게 알릴 때는 토스트를 씁니다.

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

멱등 키로 중복 요청 걸러 내기같은 키로 요청이 두 번 오면 첫 번째 결과를 그대로 돌려줍니다. 결제 기능에는 반드시 넣어야 합니다.
금액은 서버에서 다시 계산하기화면이 보낸 금액을 그대로 믿으면 사용자가 요청을 조작해 금액을 바꿔 보낼 수 있습니다. 그래서 상품 ID와 수량만 받고 금액은 서버에서 계산합니다.
재고는 결제 직전에 다시 확인하기장바구니에 담을 때 확인한 재고는 결제할 무렵이면 이미 달라져 있을 수 있으므로 결제 시점에 다시 확인합니다.
결제사 응답이 끊겼을 때결제사에서 승인은 됐는데 우리 서버가 응답을 받지 못하는 일이 실제로 일어납니다. 그래서 결제사에 결과를 다시 조회해 주문 상태를 맞추는 절차가 필요합니다.
결제가 끝나면 다른 주소로 보내기POST 응답으로 그린 완료 화면에 머물면 새로고침할 때 재전송 경고가 뜹니다. 그래서 결제가 끝나면 주문 상세 주소로 이동시킵니다.
어느 단계까지 했는지 저장하기사용자가 떠난 장바구니를 나중에 되살리려면 어느 단계까지 진행했는지 서버에 남아 있어야 합니다.

플랫폼 차이 때문에 자주 생기는 문제 — 결제 흐름은 화면을 그리는 일보다 경계 상황을 처리하는 데 품이 더 듭니다. 두 번 눌림, 끊긴 응답, 바뀐 재고, 돌아오지 않은 결제창이 그런 경우입니다. 화면 시안은 하루면 그리지만 이 네 가지를 처리하는 데는 그보다 오래 걸리고, 처리하지 않으면 나중에 환불 업무가 늘어납니다. 그래서 일정을 잡을 때 이 네 가지를 따로 적어 두는 편이 낫습니다.
