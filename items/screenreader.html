스크린 리더가 읽는 것

What screen readers announce

스크린 리더는 화면을 세 가지로 읽습니다 — 역할(무엇인가) · 이름(뭐라고 부르나) · 상태(지금 어떤가).

① 실물② 이름③ 가르는 기준④ 상태⑤ 해부도⑥ 쓸 때⑦ 사례⑧ 마크업⑨ 백엔드 메모⑩ 플랫폼

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

스위치를 켜고 '자세히'를 펼쳐 보세요. 아래 나무에서 상태가 실시간으로 바뀝니다.
role·state 를 빼고 보기를 켜면 이름만 남습니다 — '이메일 알림'이 스위치인지 버튼인지, 켜져 있는지 꺼져 있는지 알 수 없게 됩니다. 눈으로는 전부 보이는 것들입니다.

2 이름부르는 말이 여러 개다

한국어스크린 리더, 화면 낭독기, 접근성 트리
영어screen reader, accessibility tree, role · name · state
같이 쓰는 말브라우저가 만드는 '읽히는 구조'를 접근성 트리(accessibility tree)라 합니다. 대표적인 스크린 리더는 NVDA·JAWS(윈도), VoiceOver(맥·아이폰), TalkBack(안드로이드)입니다. 역할을 적는 속성이 role, 상태를 적는 속성이 aria-* 입니다.
자주 잘못 부름ARIA — aria-*는 태그가 없을 때 메우는 땜질이지 기본 수단이 아닙니다. 맞는 태그가 있으면 그걸 씁니다.
role을 붙이면 동작이 생긴다 — 안 생깁니다. 역할만 바뀌고 키 처리는 직접 짜야 합니다.
읽기 전용 — aria-hidden은 안 읽히게 하는 것이지 숨기는 것이 아닙니다.

3 가르는 기준형제들과 비교하는 네 축

접근성은 '눈으로는 안 보이는 것을 챙기는 일'입니다. 이 네 가지만 물어보면 갈립니다.

무엇을 돕나눈으로 보이나안 하면 누가 막히나어떻게 확인하나
포커스지금 어디인지보여야 한다키보드만 쓰는 사람Tab 을 눌러 본다
포커스 트랩모달 안에 가두기안 보인다키보드·스크린 리더모달에서 Tab 을 돌려 본다
키보드 조작마우스 없이 전부안 보인다마우스를 못 쓰는 사람마우스를 치우고 해 본다
이름 붙이기뭐라고 부르나안 보인다화면을 못 보는 사람접근성 트리를 본다
스크린 리더가 읽는 것역할 · 이름 · 상태안 보인다화면을 못 보는 사람실제로 읽혀 본다
라이브 리전저절로 바뀐 것안 보인다화면을 못 보는 사람바꿔 놓고 들어 본다
대비비글자가 읽히나보인다저시력 · 밝은 곳 · 싼 화면재 본다(숫자로 나온다)
시맨틱 태그화면의 구조안 보인다거의 모두구역 목록을 열어 본다

한 줄로 — 눈으로 보이는 것 중 색과 위치로만 표현한 것은 소리로 전달되지 않습니다. 그래서 상태는 속성으로 적어 둬야 합니다.

4 갈래무엇이 읽히고 무엇이 안 읽히나

5 해부도부분 이름이 제일 안 알려진 지식

이메일 알림
role="switch" — 이게 무엇인가
이름 "이메일 알림" — 뭐라고 부르나
aria-checked="true" — 지금 어떤가
aria-expanded · disabled · aria-selected
색·위치로만 표현한 것은 안 읽힌다
  1. 부품 하나 element눈에는 스위치, 소리에는 세 가지 정보
  2. 역할 role이게 무엇인가 — 버튼·스위치·탭·목록. 태그가 주면 안 적어도 된다
  3. 이름 accessible name뭐라고 부르나 — 이름 붙이기가 정한다
  4. 상태 aria-checked 등지금 어떤가 — 바뀔 때마다 같이 바꿔야 한다
  5. 상태 속성들 expanded · selected · disabled펼침·골라짐·비활성. 눈으로 표현한 것을 말로 옮긴다
  6. 안 읽히는 것 색 · 위치 · 굵기소리로는 전달되지 않는다. 속성으로 따로 적어야 한다

role을 붙인다고 동작이 따라오지는 않습니다. role="button"은 '버튼이라고 읽어 달라'는 말일 뿐, Enter·Space 처리는 여전히 직접 짜야 합니다. 그래서 ARIA 의 첫 규칙이 "ARIA 를 쓰지 않는 것"입니다 — <button>을 쓰면 역할과 동작이 함께 옵니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 상태가 바뀌는 것 — 켜짐·펼침·골라짐·비활성
  • 직접 만든 부품 — 탭·콤보박스·스위치에는 role과 상태가 필요합니다
  • 장식 아이콘에 aria-hidden="true"

이럴 때는 안 쓴다

  • 맞는 태그가 있는데 role로 흉내 내는 것
  • 상태를 처음 한 번만 적고 안 바꾸는 것 — 거짓말이 됩니다
  • aria-hidden을 포커스 받는 것에 거는 것 — 갈 수는 있는데 안 읽히는 유령이 됩니다
  • 색·위치로만 상태를 표현하는 것

대신 이걸 — 이름만 다루려면 이름 붙이기, 태그 고르기는 시맨틱 태그, 저절로 바뀌는 것은 라이브 리전.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 규칙역할·이름·상태 세 줄

태그가 줄 수 있으면 태그로, 못 줄 때만 role과 aria-*로 메웁니다.

<!-- 태그가 역할을 준다 — 가장 좋다 -->
<button>저장</button>
<input type="checkbox" id="n"><label for="n">알림</label>

<!-- 태그가 없을 때만 role 로 메운다 -->
<span role="switch" tabindex="0"
      aria-checked="false">이메일 알림</span>

// 상태가 바뀌면 속성도 같이 바꾼다 — 안 바꾸면 거짓말이 된다
el.setAttribute('aria-checked', String(on));

<!-- 장식은 아예 빼 둔다 -->
<svg aria-hidden="true">…</svg>
규칙지켜야 하는 것
태그를 먼저<button>·<input>이 역할·동작을 함께 준다
role은 땜질역할만 바뀌고 키 처리는 안 따라온다
상태를 같이 바꾼다눈에 보이는 변화마다 aria-*도 바꾼다
장식은 숨긴다aria-hidden="true". 단 포커스 받는 것에는 걸지 않는다
에러는 말로빨간 테두리 + aria-invalid + aria-describedby
트리를 본다개발자 도구 Accessibility 패널에서 실제로 뭐라고 읽힐지 확인한다

9 서버 쪽으로 치면백엔드 감각으로 번역

상태는 서버가 아는 것과 다르다서버의 status는 데이터이고, aria-expanded는 지금 화면의 모습입니다. 둘을 혼동하면 접힌 패널이 '펼침'으로 읽힙니다.
목록 개수<ul>을 쓰면 '목록, 항목 12개'가 자동으로 읽힙니다. 무한 스크롤로 늘어날 때는 aria-setsize 로 전체 수를 알려 주기도 합니다.
실제로 들어 본다맥은 Cmd+F5로 VoiceOver 가 켜집니다. 10분만 써 봐도 코드로 아는 것보다 많이 배웁니다.
자동 검사의 한계도구는 '이름 없음'은 잡지만 '이름이 틀림'은 못 잡습니다. 사람이 한 번은 들어 봐야 합니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

세 플랫폼 모두 역할·이름·상태 구조가 같습니다.

웹role + aria-*
이메일 알림"스위치, 켜짐"
태그가 역할을 주고, 모자라면 role·aria-*로 메웁니다.
iOSVoiceOver
.accessibilityTraits
.accessibilityValue
역할을 trait, 상태를 value 라 부릅니다. 표준 부품은 다 들어 있습니다.
안드로이드TalkBack
semantics {
 role = Role.Switch
}
semantics 블록에 역할·상태를 적습니다. 구조가 웹과 거의 같습니다.

자주 생기는 사고 — 구조가 같아서 "이 스위치가 켜졌다고 읽히나요"가 세 쪽에 그대로 통합니다. 다만 읽는 순서와 말투는 스크린 리더마다 다릅니다 — 한 기기에서 자연스러운 문장이 다른 기기에서는 어색할 수 있으니, 이름은 짧고 사실만 적는 편이 안전합니다.
