에러 상태

Error state

에러 상태는 사용자가 하려던 일이 실패했다는 것과 이제 무엇을 하면 되는지를 알리는 화면입니다. 에러를 어디에 붙이느냐에 따라 네 단계로 나뉩니다.

① 실물② 이름③ 상태④ 해부도⑤ 쓸 때⑥ 사례⑦ 마크업⑧ 백엔드 메모⑨ 플랫폼

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

네 단계를 번갈아 눌러 보세요. 같은 실패라도 단계마다 에러가 붙는 자리가 다릅니다. 단계가 올라갈수록 사용자가 할 수 있는 일은 줄어듭니다. 예를 들어 칸 하나에 붙은 에러는 그 칸을 고쳐서 바로 다시 보내면 되지만, 화면 전체에 띄운 에러 앞에서는 '다시 불러오기'밖에 할 수 없습니다. 그래서 꼭 필요하지 않으면 에러의 단계를 올리지 않습니다.

2 이름같은 것을 부르는 여러 이름

한국어에러 상태, 오류 상태, 오류 화면
영어error state, error message, inline error, error page
같이 쓰는 말입력 칸 아래 붙는 에러는 인라인 에러, 폼 위에 뜨는 상자는 얼럿이나 배너, 화면 전체를 덮는 에러는 에러 페이지(404·500)라고 부릅니다.
자주 잘못 부르는 이름얼럿 — 웹에서 얼럿은 alert() 창을 가리키기도 하고 인라인 경고 상자를 가리키기도 해서, 모달과 혼동하기 쉽습니다.
토스트 — 에러를 토스트로만 알리면 토스트가 금방 사라져서 사용자가 다 읽지 못합니다. 사용자가 고쳐야 하는 에러는 화면에 남아 있어야 합니다.
빈 상태 — 비어 있다고 해서 무언가 잘못된 것은 아니므로 빈 상태는 빨갛게 칠하지 않습니다.

  1. 경고 상자 alert · callout빨강은 진행이 정말 막혔을 때만 씁니다. 빨강을 아무 데나 쓰면 정작 중요한 에러가 눈에 들어오지 않습니다
  2. 아이콘 icon색만으로 에러를 알리지 않으려고 둡니다. 색각 이상인 사람은 색 대신 아이콘을 보고 에러임을 알아챕니다
  3. 실패한 일 title사용자가 쓰는 말로 적습니다. '요청 실패'가 아니라 '등록하지 못했습니다'처럼 씁니다
  4. 원인과 다음에 할 일 description원인과 다음에 할 일을 함께 적습니다. 둘 중 하나만 있으면 사용자가 상황을 이해하거나 해결하기 어렵습니다
  5. 다시 시도 버튼 retry · action에러 화면에서 특히 중요한 요소입니다. 다시 할 방법이 없으면 사용자는 그 화면에서 더 할 수 있는 일이 없습니다
  6. 오류 번호 error code고객센터에 문의할 때 씁니다. 사용자에게는 의미 없는 글자지만 고객센터는 이 번호로 어떤 요청이 실패했는지 찾습니다

에러 화면에 적지 말아야 할 것도 있습니다. 스택 트레이스와 내부 주소, SQL은 사용자에게는 쓸모가 없지만 공격자에게는 시스템 구조를 알려 주는 정보가 됩니다. 자세한 내용은 서버 로그에 남기고, 화면에는 그 로그를 찾을 수 있는 오류 번호만 적습니다.

5 쓸 때 / 안 쓸 때

에러 상태를 쓰는 경우

  • 사용자가 고칠 수 있는 가장 가까운 자리에 붙일 때
  • 다시 시도, 돌아가기, 문의하기처럼 다시 할 방법을 함께 줄 때
  • '은행 점검 시간입니다'처럼 원인을 사용자가 쓰는 말로 적을 때

에러 상태를 쓰지 않는 경우

  • 에러를 토스트로만 알릴 때. 토스트가 금방 사라져서 다 읽지 못합니다
  • 폼 전송이 실패했는데 입력값을 지울 때. 사용자가 처음부터 다시 입력해야 해서 가장 불만이 많은 처리입니다
  • "오류가 발생했습니다"만 적을 때. 사용자가 무엇을 해야 하는지 알 수 없습니다
  • 스택 트레이스나 내부 주소를 보여 줄 때. 사용자에게는 쓸모가 없고 보안상 위험합니다
  • 빨강을 아무 데나 쓸 때. 정작 중요한 에러의 빨강이 눈에 띄지 않게 됩니다

에러 상태 대신 다른 것을 써야 하는 경우 — 사용자에게 알려 주기만 하면 되는 일이면 토스트를 쓰고, 답을 꼭 받아야 하면 모달을 씁니다. 아직 불러오는 중이라면 스피너를, 실패가 아니라 원래 내용이 없는 것이라면 빈 상태를 보여 줍니다.

7 최소 마크업과 키보드구현할 때 지킬 최소 규칙

구현에서 중요한 것은 에러 설명을 해당 입력 칸과 연결해 두는 것입니다. 색만으로 에러를 알리면 스크린 리더 사용자와 색각 이상인 사람은 에러가 났다는 것을 알 수 없습니다.

<!-- 칸과 설명을 이어 둔다. 색만으로는 안 된다 -->
<input id="acct" aria-invalid="true" aria-describedby="e1">
<p id="e1" class="field-err">자릿수가 모자랍니다. 11~12자리입니다.</p>

<!-- 폼 전체 실패는 읽던 말을 끊고 알린다 -->
<div role="alert">등록하지 못했습니다…</div>

// 다시 보낼 때까지 기다리지 말고 고쳐지는 즉시 풀어 준다
input.addEventListener('input', () => {
  if (valid(input.value)) clearError(input);
});

// 사용자에게는 번호만, 자세한 것은 로그로

폼을 보낼 때첫 번째 틀린 칸으로 포커스를 옮깁니다. 그래야 사용자가 어디가 틀렸는지 찾아 헤매지 않습니다
aria-invalid틀린 칸에 true로 겁니다. 에러 설명은 aria-describedby로 칸과 연결합니다
role="alert"폼 전체 실패처럼 지금 바로 알려야 하는 것에만 씁니다. 칸 하나의 에러에는 쓰지 않습니다
사용자가 값을 고쳤을 때다시 보낼 때까지 기다리지 말고 입력하는 도중에 풀어 줍니다
색으로 알릴 때빨강만으로 알리지 않고 아이콘과 글자를 함께 둡니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

실패한 층에 따라 정해지는 단계검증 실패(400)는 칸에, 일시적 실패(503)는 폼 위에, 렌더 실패(500)는 화면 전체에, 연결 실패는 꼭대기 띠에 표시합니다. 서버 응답의 종류에 따라 에러를 보여 줄 단계가 정해지는 셈입니다.
필드 단위로 에러 내려 주기에러를 { field: 'account', message: '…' } 형태로 내려 주면 화면에서 해당 칸에 붙일 수 있습니다. 에러 문장 하나만 내려 주면 어느 칸의 문제인지 알 수 없어 폼 위에 띄울 수밖에 없습니다.
다시 시도하려면 멱등성이 필요함'다시 시도'를 누르면 같은 요청이 한 번 더 서버로 가는데, 멱등 키가 없으면 같은 내용이 두 번 등록될 수 있습니다. 그래서 다시 시도 버튼을 두려면 서버도 같은 요청을 한 번만 처리하도록 설계해야 합니다.
오류 번호를 상관관계 ID로 쓰기요청마다 ID를 붙여 응답과 로그에 함께 남깁니다. 그러면 사용자가 'a4f21c'라는 번호만 알려 줘도 로그에서 그 요청을 찾아낼 수 있습니다.
바깥에 보여 줄 정보의 범위스택 트레이스와 내부 주소를 보여 주면 공격자가 시스템 구조를 파악할 수 있습니다. 바깥으로는 오류 번호만 내보내고, 자세한 내용은 모두 내부 로그에 남깁니다.
