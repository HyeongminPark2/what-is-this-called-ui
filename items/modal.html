모달

Modal · modal dialog

화면 위에 떠서 뒤쪽을 못 만지게 막는 창. 여기에 답하지 않으면 다른 일을 할 수 없게 만드는 것이 핵심이다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

포커스 갇힘은 위 틀 안에서 확인할 수 없습니다. <dialog>가 가두는 범위는 자기 문서 안이고, 위 예시는 iframe에 들어 있습니다. 그래서 모달의 마지막 버튼에서 Tab을 누르면 포커스가 이 도감 페이지로 넘어갑니다. 제대로 보려면 새 탭에서 열어 Tab을 돌려 보세요. 덧붙여 — iframe은 포커스 순서를 잇는 문이지 벽이 아니다라는 것도 알아 둘 만합니다.

폭을 390으로 바꿔 보세요. 같은 모달이 가운데 창에서 아래에서 올라오는 바텀시트로 바뀝니다. 좁은 화면에서 가운데 뜨는 창은 손가락이 닿기 어렵고 키보드가 올라오면 가려지기 때문입니다. 부품이 달라진 게 아니라 같은 부품의 좁은 폭 모습입니다.

지금 보는 기기에는 호버가 없습니다. 손가락은 '올려놓기'를 할 수 없어서, 눌러 보기 전에 무엇이 눌리는지 알 수 있어야 합니다. 아래 ④ 상태 띠의 호버 칸은 마우스가 있는 화면에서만 볼 수 있는 모습입니다.

2 이름부르는 말이 여러 개다

한국어모달, 모달 창, 모달 팝업
영어modal, modal dialog
같이 쓰는 말뒤에 깔리는 어두운 면을 스크림(scrim) · 백드롭(backdrop) · 오버레이라 부른다
자주 잘못 부름 팝업 — 원래는 브라우저가 새로 띄우는 창을 뜻한다. 모달을 팝업이라 부르면 광고창과 섞인다.
레이어 — 한국 실무에서 '레이어 띄워 주세요'라고 많이 쓰지만 표준 용어는 아니다. 디자이너와는 통하고 문서에는 모달로 쓰는 게 안전하다.
얼럿 — iOS에서는 맞는 말이지만 웹에서는 alert()나 인라인 경고와 헷갈린다.

한 줄로 — 모달인지 아닌지는 생김새가 아니라 뒤쪽을 막느냐로 정해집니다. 가운데 예쁘게 떠 있어도 뒤를 만질 수 있으면 모달이 아니고, 구석에 조그맣게 떠 있어도 뒤를 막으면 모달입니다.

4 상태그림 한 장으로는 못 배운다

5 해부도부분 이름이 제일 안 알려진 지식

프로젝트를 삭제할까요? ×
결제 서버 마이그레이션과 그 안의 기록이 모두 지워집니다. 되돌릴 수 없습니다.
취소 삭제
  1. 스크림 scrim · 백드롭 · 오버레이뒤를 가리고 클릭을 막는 면. '뒤를 막는다'를 눈에 보이게 하는 장치
  2. 서피스 surface · 컨테이너 · 패널모달의 몸통. 그림자 세기로 '얼마나 떠 있나'(고도)를 나타낸다
  3. 타이틀 title스크린 리더가 모달을 열 때 읽는 이름. 질문형으로 쓰면 버튼 문구가 쉬워진다
  4. 닫기 어포던스 close affordanceX 버튼. '여기를 누르면 닫힌다'는 것을 보여주는 생김새를 어포던스라 한다
  5. 본문 body · content길어지면 여기만 스크롤시키고 머리와 발은 고정한다
  6. 액션 영역 footer · action bar버튼을 모아 두는 띠. 폰 폭에서는 위아래로 쌓인다
  7. 세컨더리 액션 secondary action취소. 왼쪽에 두는 게 서양 관행, 한국 앱은 섞여 있다
  8. 프라이머리 액션 primary action이 모달이 존재하는 이유. 하나만 둔다
  9. 포커스 링 focus ring지금 키보드가 어디를 가리키나. 지우지 말 것

서피스의 그림자 세기를 고도(elevation)라 부릅니다 — 가리킬 테두리가 없어 번호를 안 붙였습니다. 2부 고도와 z-index에서 따로 다룹니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 되돌릴 수 없는 일을 하기 직전에 한 번 묻을 때
  • 짧은 입력 하나를 받고 원래 자리로 돌아와야 할 때 (이름 바꾸기, 멤버 초대)
  • 진행을 막아야 할 때 (약관 동의, 결제 비밀번호)

이럴 때는 안 쓴다

  • 단계가 여러 개이거나 입력이 많을 때 → 페이지로 보낸다
  • 알려 주기만 할 때 → 토스트나 인라인 얼럿
  • 이미 한 일을 알릴 때 → 되돌리기 붙인 토스트. 확인 모달보다 낫다
  • 모달 위에 모달 → 거의 항상 설계가 잘못된 신호

대신 이걸 — 알려 주기만 하면 토스트, 누른 것 옆에 붙어야 하면 팝오버, 손가락으로 쓰는 긴 선택이면 바텀시트, 보조 내비게이션이면 드로어. (아직 안 쓴 항목들)

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 키보드이 부품의 계약서

브라우저가 주는 <dialog>를 쓰면 포커스 갇힘, Esc, 뒤쪽 비활성이 공짜로 따라옵니다. 직접 만든 <div> 모달이 접근성 지적을 받는 이유가 이것들을 다시 구현해야 해서입니다.

<!-- 뼈대 -->
<button id="opener">삭제</button>

<dialog id="dlg" aria-labelledby="t">
  <h2 id="t">프로젝트를 삭제할까요?</h2>
  <p>되돌릴 수 없습니다.</p>
  <button value="cancel">취소</button>
  <button value="ok">삭제</button>
</dialog>

// 열기 — show()가 아니라 showModal(). 이 한 글자가 모달과 비모달을 가른다
dlg.showModal();

// 닫힌 뒤 포커스를 부른 버튼으로 돌려준다 (브라우저가 해 주지 않는 부분)
dlg.addEventListener('close', () => opener.focus());
키일어나야 하는 일
Esc닫힌다. 입력 중이던 내용이 날아갈 때는 한 번 더 묻는다
Tab모달 안에서만 돈다. 마지막에서 누르면 첫 요소로 (포커스 갇힘)
Shift+Tab거꾸로 돈다. 뒤쪽 화면으로 새지 않는다
Enter프라이머리 액션. 파괴적 동작에서는 연결하지 않는다
열릴 때포커스가 모달 안으로 들어간다. 파괴적 동작이면 '취소'에 둔다
닫힐 때포커스가 열었던 버튼으로 돌아간다

9 서버 쪽으로 치면백엔드 감각으로 번역

모달 = 블로킹 호출뒤쪽 화면을 멈추고 답을 기다립니다. UI의 동기 호출입니다. 그래서 남발하면 화면이 '스레드 하나로 돌아가는' 느낌이 됩니다.
확인 모달 = 2단계 커밋 앞의 prepare진짜 실행 전에 의사를 한 번 확정받는 단계. 그런데 되돌리기(undo)가 가능하면 이 단계는 없어도 됩니다 — 롤백이 되면 확인은 군더더기라는 점이 UI에서도 같습니다.
포커스 갇힘 = 스코프 격리키보드 포커스라는 전역 상태를 모달 범위로 묶어 두는 것. 안 하면 뒤쪽 폼에 글자가 들어갑니다.
스크림 = 뮤텍스가 걸렸다는 표시잠금이 걸렸다는 사실을 눈에 보이게 하는 장치. 잠궜는데 표시를 안 하면 사용자는 앱이 멈춤 줄 압니다.
'처리 중' 상태 = 멱등성 문제버튼을 두 번 누르면 요청이 두 번 갑니다. 비활성 처리는 UI 쪽 멱등 키입니다.
