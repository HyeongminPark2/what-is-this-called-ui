지속 시간

Duration

지속 시간은 움직임이 얼마나 걸릴지를 정합니다. 처음 볼 때는 멋있던 길이도 백 번째 볼 때는 답답하게 느껴집니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

막대를 끌어 길이만 바꿔 보세요. 같은 움직임인데도 길이에 따라 전혀 다르게 느껴집니다.
0ms에서는 요소가 순간이동하듯 바로 바뀌어 무엇이 어디서 왔는지 알 수 없고, 100ms 아래에서는 깜빡인 것처럼 보이며, 400ms를 넘으면 움직임이 끝나기를 기다리게 됩니다. 아래 표에서는 지금 길이에 맞는 쓰임이 밝게 표시됩니다.

2 이름같은 것을 부르는 여러 이름

한국어지속 시간, 길이, 재생 시간
영어duration, transition duration
같이 쓰는 말CSS에서는 transition-duration과 animation-duration 속성으로 정합니다. 시작을 늦추는 값은 딜레이(delay)라고 하고, 길이 값들을 --duration-fast처럼 이름 붙여 두면 모션 토큰이라고 부릅니다.
자주 잘못 부르는 이름이징 — 이징은 움직임이 '어떻게' 진행되는지, 지속 시간은 '얼마나' 걸리는지를 정합니다.
딜레이 — 늦게 시작하는 것과 오래 걸리는 것은 다릅니다. 딜레이는 차례로 들어오게 할 때 씁니다.
FPS — 초당 프레임 수는 움직임이 얼마나 매끄러운지의 문제라서 무엇을 움직이나에서 다룹니다.

3 길이에 따라 달라지는 느낌같은 움직임을 길이만 바꿔 본 모습

4 해부도부분마다 붙은 이름

툴팁과 색 바뀜은 100ms
드롭다운과 토글은 150ms
모달과 시트를 열 때 250ms
화면 전체 전환은 350ms
400ms를 넘으면 기다리게 됨
100ms 아래는 깜빡인 것처럼 보임
  1. 아주 짧게 100ms색, 테두리, 툴팁처럼 자리가 거의 변하지 않는 것에 씁니다
  2. 짧게 150ms토글이나 드롭다운처럼 손가락 하나 거리만큼 움직이는 것에 씁니다
  3. 보통 250ms모달과 시트에 씁니다. 요소가 어디서 왔는지 보여 줄 시간이 필요하기 때문입니다
  4. 길게 350ms화면 전체를 전환할 때 씁니다. 이보다 길면 대부분 과합니다
  5. 상한 400ms이 값을 넘으면 사용자가 애니메이션이 끝나기를 기다리느라 조작을 멈추게 됩니다
  6. 하한 100ms이보다 짧으면 움직임이 눈에 들어오지 않습니다. 그럴 바에는 0으로 두는 편이 낫습니다

기준표의 숫자보다 중요한 것은 사용자가 그 움직임을 몇 번 보느냐입니다. 온보딩처럼 한 번만 보는 화면은 400ms도 괜찮지만, 목록에서 하루에 백 번 여는 메뉴가 300ms라면 사용자는 하루에 30초를 기다리는 셈입니다. 그래서 자주 쓰는 것일수록 짧게 한다는 규칙을 거리나 크기보다 먼저 따집니다.

5 쓸 때 / 안 쓸 때

지속 시간을 정할 때 지킬 것

  • fast · base · slow처럼 토큰 서너 개를 정해 두고 그것만 쓸 때
  • 거리가 멀거나 요소가 클 때. 이때는 조금 더 길게 줍니다
  • 자주 보는 것을 짧게 줄 때. 하루에 백 번 보는 것이면 100ms도 깁니다

지속 시간을 정할 때 피할 것

  • 화면마다 숫자를 손으로 적을 때. 400, 350, 420처럼 값이 뒤섞입니다
  • 멋있어 보인다고 길게 줄 때. 두 번째 볼 때부터 답답합니다
  • 100ms 아래로 줄 때. 움직임이 보이지 않을 바에는 0이 낫습니다
  • 데이터를 기다리는 시간을 애니메이션으로 채울 때. 이럴 때는 스켈레톤을 씁니다

지속 시간과 헷갈리기 쉬운 다른 항목 — 속도를 나눠 쓰는 방식은 이징에서, 줄마다 조금씩 늦게 들어오게 하는 방법은 차례로 들어오기 항목에서 다룹니다. 기다리는 동안 작업이 진행 중임을 보여 주려면 스피너를 씁니다.

6 자주 보는 모습구조만 따라 그린 재현 그림

7 최소 코드와 규칙구현할 때 지킬 최소 규칙

길이도 토큰으로 정의해 두고, 모션 줄이기 설정에서는 거의 0으로 내립니다.

:root {
  --dur-fast: 120ms;   /* 색 · 툴팁 */
  --dur-base: 220ms;   /* 토글 · 드롭다운 */
  --dur-slow: 340ms;   /* 모달 · 화면 전환 */
}

.menu { transition: opacity var(--dur-base) var(--ease-out); }

@media (prefers-reduced-motion: reduce) {
  :root { --dur-fast: 1ms; --dur-base: 1ms; --dur-slow: 1ms; }
}
알아 둘 규칙자세한 내용
단위를 빠뜨리지 않기transition: transform 200처럼 단위를 빼면 선언이 통째로 무시됩니다. 200ms나 .2s로 적습니다
0s와 0.01ms길이가 완전히 0이면 transitionend와 animationend가 오지 않아서, 그 이벤트를 기다리는 코드가 멈춥니다
속성마다 길이를 다르게 주기transition: transform 240ms, opacity 140ms처럼 속성마다 길이를 다르게 줄 수 있고, 투명도는 더 짧아도 됩니다
prefers-reduced-motion길이를 1ms로 내리는 것이 가장 안전한 대응입니다
초점이 옮겨 갈 때애니메이션이 끝나기를 기다렸다가 초점을 옮기면 그동안 키보드 사용자는 아무것도 할 수 없습니다. 초점은 먼저 옮깁니다
<dialog>를 닫을 때close()를 부르면 바로 사라집니다. 나가는 연출을 보여 주려면 연출이 끝난 뒤에 호출합니다

8 서버 쪽으로 치면백엔드 개념과 짝지어 보기

응답보다 애니메이션이 길면데이터가 50ms 만에 와도 전환이 400ms 걸리면 사용자는 400ms를 기다립니다. 화면이 느릴 때 원인이 서버가 아닐 수도 있습니다.
요청을 연출보다 먼저 보내기'애니메이션이 끝나면 요청 보내기'로 짜면 애니메이션 길이만큼 응답이 늦어집니다. 요청과 연출은 같이 시작합니다.
성능 지표에 들어가는 연출 시간LCP나 INP 같은 지표에는 연출 시간이 들어갑니다. 그래서 히어로 영역이 느리게 나타나면 점수가 깎입니다.
최소 표시 시간스피너가 50ms만 보였다가 사라지면 깜빡인 것처럼 보입니다. 한번 띄웠으면 300ms는 유지하는 편이 덜 어지럽습니다.

9 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

세 플랫폼의 권장값은 100~400ms로 거의 같습니다.

웹팀이 정한 토큰
220ms
표준 권장값이 없어서 팀이 정합니다. 그래서 미리 정해 두지 않으면 화면마다 길이가 달라집니다.
iOS0.2~0.35s
0.3s
시스템 전환은 약 0.35초입니다. 요즘은 길이를 직접 정하는 대신 스프링의 뻣뻣함으로 정합니다.
안드로이드Material 3
200ms
short · medium · long 구간으로 나눠 50~600ms 사이의 값을 정해 두었습니다. 기본값은 200ms 안팎입니다.

플랫폼 차이 때문에 자주 생기는 문제 — 사용자는 "애니메이션이 느려요"와 "화면이 느려요"를 같은 말로 신고하지만 둘은 다른 문제입니다. 길이를 토큰으로 묶어 두면 한 줄만 고쳐 전체 애니메이션을 빠르게 만들어 볼 수 있어서, 원인이 어느 쪽인지 금방 가릴 수 있습니다.
