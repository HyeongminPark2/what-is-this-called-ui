가상 스크롤

Virtual scrolling

가상 스크롤은 목록이 수만 줄이어도 화면에 보이는 줄만 그려서 브라우저가 느려지지 않게 하는 기법입니다. 대신 안 그린 줄은 찾기·인쇄·스크린 리더에서 빠지므로 잃는 것도 분명합니다.

가상 스크롤을 끄고 2만 줄을 그려 보세요. 그리는 데 걸린 시간과 실제로 만들어진 DOM 노드 수가 아래에 나옵니다.
가상 스크롤을 켜면 노드 수가 열몇 개로 줄어듭니다. 그런데도 스크롤 막대 길이가 그대로인 것은 빈 받침대 하나가 전체 목록의 높이만 차지하고 있기 때문입니다.

2 이름같은 것을 부르는 여러 이름

한국어가상 스크롤, 가상화, 창 띄우기
영어virtual scrolling, virtualization, windowing
같이 쓰는 말보이는 구간만 그리는 것은 윈도잉(windowing), 전체 목록의 높이만 차지하는 빈 상자는 스페이서·사이저(sizer), 보이는 구간 위아래로 조금 더 그려 두는 여유분은 오버스캔(overscan)이라고 합니다. 리액트 쪽 라이브러리 이름(react-window, TanStack Virtual)을 기법 이름처럼 쓰기도 합니다.
자주 잘못 부르는 이름무한 스크롤 — 무한 스크롤은 데이터를 더 받아오는 기법이고, 가상 스크롤은 받은 데이터를 덜 그리는 기법입니다. 둘을 함께 쓰기도 합니다.
페이지네이션 — 페이지네이션은 목록을 쪽으로 끊어 보여 주고, 가상 스크롤은 목록 전체를 하나로 이어 둡니다.
레이지 로딩 — 레이지 로딩은 이미지를 필요할 때 늦게 받는 기법이라 가상 스크롤과는 다릅니다.

줄 높이가 제각각이면 이 계산이 전부 어긋남
  1. 굴리는 상자 height 고정상자 높이가 정해져 있어야 몇 줄이 보이는지 계산할 수 있습니다
  2. 받침대 sizer높이를 전체 줄 수 × 줄 높이로 잡아 스크롤 막대 길이만 만듭니다
  3. 보이는 창 windowscrollTop / 줄높이로 화면에 보이는 첫 줄 번호를 구합니다
  4. 그린 줄 12개 남짓보이는 줄 위아래로 두세 줄 더(overscan) 그려 두면 스크롤할 때 덜 깜빡입니다
  5. 자리 옮기기 translateYtop을 바꾸는 것보다 transform으로 옮기는 편이 브라우저 부담이 적습니다
  6. 고정 줄 높이 전제 조건줄 높이가 제각각이면 줄마다 높이를 재야 해서 구현이 훨씬 어려워집니다

가상 스크롤을 넣기 전에 잃는 것부터 따져 보세요. 그리지 않은 줄은 Ctrl+F로 찾을 수 없고, 스크린 리더도 읽지 못합니다. 인쇄하면 화면에 보이던 열몇 줄만 나오고, 검색 엔진도 그 줄을 보지 못합니다. Ctrl+A로 전체를 복사해도 보이는 줄만 복사됩니다. 그래서 공개 페이지에는 거의 쓰지 않고 로그인한 뒤에 쓰는 관리 도구에만 씁니다.

6 쓸 때 / 안 쓸 때

가상 스크롤을 쓰는 경우

  • 로그, 시세, 채팅처럼 줄이 수천 개를 넘고 쪽으로 끊어 보여 줄 수 없을 때
  • 줄 높이가 모두 같을 때
  • 검색이나 인쇄를 쓰지 않아도 되는, 로그인 뒤의 관리 도구일 때

가상 스크롤을 쓰지 않는 경우

  • 줄이 몇백 개일 때. 요즘 브라우저는 이 정도는 무리 없이 그리므로 전부 그립니다
  • 공개 페이지일 때. 그리지 않은 줄은 검색 엔진이 보지 못합니다
  • 줄 높이가 제각각인데 직접 만들려고 할 때. 이 경우에는 라이브러리를 씁니다
  • 쪽을 나눌 수 있을 때. 페이지네이션이 만들기 쉽고 사용자도 쓰기 편합니다

가상 스크롤 대신 다른 것을 써야 하는 경우 — 목록을 쪽으로 끊어 보여 줘도 되면 페이지네이션을 쓰고, 스크롤하는 대로 데이터를 이어서 받아야 하면 무한 스크롤이 맞습니다. 줄이 몇백 개 정도라면 평범한 데이터 테이블로 전부 그려도 됩니다.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 최소 마크업과 키보드가상 스크롤을 만들 때 꼭 갖출 것

받침대로 전체 길이를 만들고, 보이는 구간만 그린 뒤 transform으로 그 자리까지 내려 둡니다.

<div class="scroller" role="list"
     aria-label="정산 20,000건">
  <div class="sizer">             <!-- 막대 길이만 만든다 -->
    <div class="window">…12줄…</div>
  </div>
</div>

const H = 36, N = 20000;
sizer.style.height = N * H + 'px';

scroller.onscroll = () => {
  const first = Math.floor(scroller.scrollTop / H);
  const count = Math.ceil(scroller.clientHeight / H) + 2;  // 여유분
  win.style.transform = `translateY(${first * H}px)`;
  render(first, count);
};
키와 마크업그때 일어나야 하는 일
PageDown·Home·End브라우저 기본 스크롤이 그대로 동작해야 합니다. 키 입력을 직접 가로채지 않습니다
Tab그리지 않은 줄로는 포커스가 갈 수 없습니다. 포커스가 있던 줄을 지우면 포커스가 <body>로 넘어갑니다
role="list"에 전체 건수 적기'20,000건'처럼 전체 건수를 레이블에 적습니다. 그러지 않으면 스크린 리더가 그려진 12줄만 읽어서 사용자는 열두 건뿐이라고 생각합니다
aria-setsize·aria-posinset줄마다 '20,000개 중 9,981번째'처럼 전체에서 몇 번째인지 알립니다
Ctrl+F로 찾지 못하는 문제브라우저 찾기 기능은 그리지 않은 줄을 찾지 못하므로 검색 칸을 따로 둡니다
인쇄할 때화면에 보이는 열몇 줄만 인쇄됩니다. 인쇄가 필요하면 별도 내보내기를 만듭니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

2만 건을 한 번에 보내지 않기그리는 줄은 줄었어도 서버에서 받는 데이터 양은 그대로입니다. 응답이 5MB라면 받는 동안 느린 것은 여전합니다.
커서 페이징OFFSET 19000을 쓰면 데이터베이스가 앞의 19,000줄을 읽어 세고 버립니다. 그래서 받은 마지막 줄의 키를 기준으로 다음 묶음을 받는 편이 빠릅니다.
목록 중간으로 건너뛸 때스크롤 막대를 끌어 목록 한가운데로 가면 그 구간을 따로 요청해야 합니다. 이런 요청은 커서 방식과 잘 맞지 않아서, 중간으로 뛰는 것을 허용할지에 따라 설계가 달라집니다.
받침대 높이에 필요한 전체 건수받침대 높이를 정하려면 전체 줄 수가 필요합니다. COUNT(*)가 오래 걸리면 어림수로 높이를 잡고, 목록 끝에 다다랐을 때 실제 줄 수로 고칩니다.
보이지 않는 줄의 데이터가 바뀔 때보이지 않는 줄의 데이터가 서버에서 바뀌어도 화면은 알 수 없습니다. 그래서 언제 다시 받을지 정해 둡니다.

플랫폼 차이 때문에 자주 생기는 문제 — "목록이 느려요"라는 말을 듣자마자 가상 스크롤을 꺼내지 마세요. 줄이 몇백 개라면 느린 원인은 보통 줄 수가 아니라 줄마다 들어간 그림자·이미지·계산입니다. 가상 스크롤은 줄이 수천 개인 것이 확실하고 줄 높이가 같을 때만 쓰고, 쓰기로 했다면 찾기·인쇄·스크린 리더 대응을 따로 만들어야 한다는 것까지 일정에 넣으세요.
