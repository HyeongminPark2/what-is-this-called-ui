2 이름부르는 말이 여러 개다

한국어가상 스크롤, 가상화, 창 띄우기
영어virtual scrolling, virtualization, windowing
같이 쓰는 말보이는 구간만 그리는 것을 윈도잉(windowing), 길이를 흉내 내는 빈 상자를 스페이서·사이저(sizer), 위아래로 조금 더 그려 두는 여유분을 오버스캔(overscan)이라 합니다. 리액트 쪽 라이브러리 이름이 그대로 쓰이기도 합니다(react-window, TanStack Virtual).
자주 잘못 부름무한 스크롤 — 무한 스크롤은 더 받아오는 것, 가상 스크롤은 덜 그리는 것입니다. 둘은 같이 쓰기도 합니다.
페이지네이션 — 페이지네이션은 화면을 끊고, 가상 스크롤은 한 줄로 이어 둡니다.
레이지 로딩 — 이미지를 늦게 받는 것과는 다른 얘기입니다.

3 가르는 기준형제들과 비교하는 네 축

데이터를 다루는 화면은 '건수가 늘면 어떻게 되나'가 설계의 전부입니다. 이 네 가지만 물어보면 갈립니다.

무엇을 다루나건수가 늘면주소에 담나서버가 할 일

검색질의어결과가 늘어난다담는다색인 · 순위
폼 설계입력 묶음단계를 나눈다안 담는다저장 · 임시 저장

한 줄로 — 가상 스크롤은 마지막 수단입니다. 줄을 줄이거나 쪽을 나눠서 되면 그쪽이 늘 낫습니다.

실제로 그린 것은 12줄뿐
transform: translateY(첫 줄 번호 × 36px)
줄 높이가 제각각이면 이 계산이 전부 무너진다
  1. 굴리는 상자 height 고정높이가 안 정해지면 몇 줄이 보이는지를 모른다
  2. 받침대 sizer전체 줄 수 × 줄 높이. 막대 길이만 만든다
  3. 보이는 창 windowscrollTop / 줄높이로 첫 줄을 구한다
  4. 그린 줄 12개 남짓위아래로 두세 줄 더(overscan) 그려 두면 덜 깜빡인다
  5. 자리 옮기기 translateYtop보다 transform이 싸다
  6. 고정 줄 높이 전제 조건제각각이면 다 재야 하고 난이도가 뛴다

잃는 것을 먼저 세어 보세요. 안 그린 줄은 Ctrl+F 로 못 찾고, 스크린 리더가 못 읽고, 인쇄하면 열몇 줄만 나오고, 검색 엔진도 못 봅니다. Ctrl+A 로 전체 복사하면 보이는 것만 복사됩니다. 그래서 공개 페이지에는 거의 쓰지 않고 로그인 뒤 관리 도구에만 씁니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 줄이 수천을 넘고 끊어 보여 줄 수 없을 때 — 로그, 시세, 채팅
  • 줄 높이가 모두 같을 때
  • 로그인 뒤 관리 도구 — 검색·인쇄를 안 써도 되는 화면

이럴 때는 안 쓴다

  • 줄이 몇백일 때 — 그냥 다 그린다. 요즘 브라우저는 버틴다
  • 공개 페이지 — 검색 엔진이 못 본다
  • 줄 높이가 제각각인데 직접 만들기 — 라이브러리를 쓴다
  • 쪽을 나눌 수 있는데 굳이 — 페이지네이션이 더 쉽고 더 친절하다

대신 이걸 — 끊어도 되면 페이지네이션, 이어 받으면 무한 스크롤, 줄이 적으면 그냥 데이터 테이블.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 최소 마크업과 키보드이 기법의 계약서

받침대로 길이를 만들고, 보이는 구간만 그려 transform으로 밀어 둡니다.

<div class="scroller" role="list"
     aria-label="정산 20,000건">
  <div class="sizer">             <!-- 막대 길이만 만든다 -->
    <div class="window">…12줄…</div>
  </div>
</div>

const H = 36, N = 20000;
sizer.style.height = N * H + 'px';

scroller.onscroll = () => {
  const first = Math.floor(scroller.scrollTop / H);
  const count = Math.ceil(scroller.clientHeight / H) + 2;  // 여유분
  win.style.transform = `translateY(${first * H}px)`;
  render(first, count);
};
키일어나야 하는 일
PageDown·Home·End브라우저 기본 스크롤이 그대로 돌아야 한다. 직접 가로채지 않는다
Tab안 그린 줄에는 못 간다. 초점이 있던 줄을 지우면 초점이 <body>로 튄다
role="list" + 건수'20,000건'을 레이블에 적는다. 12줄만 읽히면 열두 건인 줄 안다
aria-setsize·aria-posinset줄마다 '20,000개 중 9,981번째'를 알린다
Ctrl+F 는 안 된다브라우저 찾기가 안 그린 줄을 못 본다. 검색 칸을 따로 둔다
인쇄보이는 열몇 줄만 나온다. 인쇄가 필요하면 별도 내보내기를 만든다

9 서버 쪽으로 치면백엔드 감각으로 번역

2만 건을 한 번에 보내지 않는다그릴 줄은 줄었어도 받는 양은 그대로입니다. 응답이 5MB 면 느린 건 여전합니다.
커서 페이징OFFSET 19000은 앞의 19,000줄을 세고 버립니다. 마지막 줄의 키를 기준으로 다음을 받는 편이 빠릅니다.
중간으로 뛰면막대를 끌어 한가운데로 가면 그 구간을 따로 요청해야 합니다. 커서 방식과는 잘 안 맞아 설계가 갈립니다.
전체 건수받침대 높이를 만들려면 총 줄 수가 필요합니다. COUNT(*)가 비싸면 어림수를 쓰고 끝에서 보정합니다.
줄이 바뀌면안 보이는 줄이 서버에서 바뀌어도 화면은 모릅니다. 언제 다시 받을지를 정해 둡니다.
