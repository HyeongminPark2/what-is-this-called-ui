입력 검증

Validation

입력 검증은 사용자가 넣은 값이 틀렸을 때 알려 주는 일입니다. '무엇이 틀렸나'를 판단하는 것보다 언제 알려 줄지 정하는 것이 더 까다롭습니다.

검사 시점을 바꿔 가며 칸에 글자를 쳐 보세요.
칠 때마다 검사하면 두 글자만 쳐도 칸이 빨개져서 사용자가 재촉받는 느낌을 받습니다. 떠날 때 검사하면 입력하는 동안에는 아무 표시가 없다가 칸을 벗어나는 즉시 알려 줍니다. 제출할 때만 검사하면 폼을 다 채운 뒤에야 오류를 한꺼번에 보게 됩니다.
제출을 눌러 보면 첫 번째 오류 칸으로 포커스가 옮겨 가는 것도 볼 수 있습니다.

2 이름같은 것을 부르는 여러 이름

한국어검증, 유효성 검사, 입력 확인
영어validation, form validation, constraint validation
같이 쓰는 말글자를 칠 때마다 검사하는 것은 실시간 검증(live·inline validation), 제출할 때 한꺼번에 검사하는 것은 제출 검증이라고 합니다. 브라우저가 required·pattern 같은 속성을 보고 대신 검사해 주는 기능은 제약 검증 API(Constraint Validation API)라고 부릅니다.
자주 잘못 부르는 이름오류 메시지 — 오류 메시지는 검사 결과를 보여 주는 부분이고, 검증은 값이 맞는지 판단하는 과정입니다.
인증(authentication) — 인증은 사용자가 본인이 맞는지 확인하는 일이라 입력 검증과는 전혀 다른 일이고, 영어로도 다른 단어를 씁니다.
폼 — 입력 검증은 폼 설계를 이루는 한 부분입니다.

한번 틀린 칸은 고치는 즉시 다시 검사한다
제출하면 첫 오류 칸으로 초점을 옮긴다
  1. 치는 중엔 조용히 on input: 안 함두 글자만 쳤는데 칸이 빨개지면 사용자는 재촉받는다고 느낍니다
  2. 떠날 때 검사 on blur칸을 벗어나는 때를 입력을 마친 시점으로 보고, 이때 검사하는 것을 기본으로 삼습니다
  3. 메시지는 칸 밑 같은 자리메시지가 칸에서 멀리 떨어져 있으면 어느 칸에 대한 말인지 알기 어렵습니다
  4. 기계에게 알리기 aria-invalid / describedby빨간 테두리는 눈으로만 알 수 있으므로 스크린 리더에도 틀렸음을 알립니다
  5. 고치면 즉시 풀기 re-validate on input한번 틀린 칸에만 적용합니다. 이미 틀린 칸은 칠 때마다 검사해도 사용자가 거슬려 하지 않습니다
  6. 제출하면 초점 이동 focus first error오류 칸이 화면 밖에 있으면 제출을 눌러도 아무 일도 일어나지 않은 것처럼 보이므로 첫 오류 칸으로 포커스를 옮깁니다

검사 시점은 틀리기 전과 뒤가 다릅니다. 처음에는 떠날 때 검사하고, 한번 틀린 칸은 그때부터 칠 때마다 검사합니다. 처음부터 칠 때마다 검사하면 다 치기 전에 칸이 빨개져서 사용자가 재촉받는 느낌을 받습니다. 반대로 고친 뒤에도 칸을 떠날 때까지 빨간 채로 두면 고쳤는데도 아직 틀렸다고 하는 것처럼 보입니다. 대부분의 폼 라이브러리가 이 두 단계 방식을 기본값으로 둡니다.

6 쓸 때 / 안 쓸 때

입력 검증을 쓰는 경우

  • 번호 자릿수, 날짜, 전자우편처럼 형식이 정해진 값을 받을 때
  • 중복, 잔액, 권한처럼 서버만 알 수 있는 조건을 확인할 때
  • 되돌리기 어려운 동작을 실행하기 직전

입력 검증을 쓰지 않는 경우

  • 입력하는 도중에 칸을 빨갛게 표시할 때. 다 치기 전에는 틀렸다고 하지 않습니다
  • '올바른 값을 입력하세요'처럼 막연하게 알릴 때. 무엇이 어떻게 틀렸는지 적습니다
  • 색만으로 알릴 때. 빨간 테두리만으로는 색을 구별하지 못하는 사람이 오류를 알아챌 수 없습니다
  • 브라우저 검사만 믿을 때. 서버가 다시 검사해야 합니다

입력 검증 대신 다른 것을 써야 하는 경우 — 오류를 보여 주는 방법은 오류 메시지, 확인만 받으려면 다이얼로그, 처리 결과를 알리려면 토스트를 봅니다.

8 최소 마크업과 키보드검증이 꼭 갖출 것

칸에 aria-invalid를 달아 값이 틀렸음을 알리고, aria-describedby로 무엇이 틀렸는지 적은 메시지를 연결합니다.

<label for="no">사업자번호</label>
<input id="no" inputmode="numeric"
       aria-invalid="true" aria-describedby="no-err">
<p id="no-err">10자리를 채워 주세요</p>

// 떠날 때 한 번, 그 뒤로는 칠 때마다
input.addEventListener('blur', () => { touched = true; check(); });
input.addEventListener('input', () => { if (touched) check(); });

// 제출하면 첫 오류 칸으로
form.querySelector('[aria-invalid="true"]')?.focus();
키와 동작그때 일어나야 하는 일
aria-invalid="true"스크린 리더가 '잘못된 값'이라고 읽습니다. 값을 고치면 속성을 지웁니다
aria-describedby메시지를 칸에 연결합니다. 칸에 포커스가 가면 메시지까지 함께 읽습니다
제출 뒤 Tab 없이제출하면 첫 오류 칸으로 포커스를 옮깁니다. 옮기지 않으면 사용자가 어느 칸이 문제인지 직접 찾아야 합니다
색 + 글자빨간 테두리에 ✕ 표시와 문장을 함께 붙입니다. 색만으로는 알리지 않습니다
required·pattern브라우저가 알아서 제출을 막아 주지만, 메시지가 영어로 나올 수 있습니다
novalidate메시지를 직접 그리려면 이 속성으로 브라우저 기본 말풍선을 끕니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

서버가 최종 판단브라우저 검사는 사용자를 돕는 안내입니다. curl 명령 한 줄로 요청을 보내면 브라우저 검사를 모두 건너뛸 수 있으므로 서버가 최종 판단을 내립니다.
같은 규칙을 두 곳에 쓰지 않는다화면과 서버가 규칙을 따로 가지고 있으면 '화면은 통과했는데 서버가 거절'하는 일이 생깁니다. 규칙을 한 곳에 적고 화면과 서버가 함께 쓰게 합니다.
오류는 칸 이름과 함께{"field":"no","message":"10자리여야 합니다"}처럼 보냅니다. 문장만 보내면 화면이 그 메시지를 어느 칸에 붙여야 할지 알 수 없습니다.
중복 확인은 경합한다'쓸 수 있는 번호'라고 확인한 뒤 저장하기 전까지 다른 사람이 그 번호를 먼저 등록할 수 있습니다. 그래서 저장할 때 다시 확인하고, DB에도 유일 제약을 겁니다.
확인 요청을 아낀다글자를 칠 때마다 서버에 물으면 요청이 한꺼번에 많이 몰립니다. 검색에서처럼 디바운스를 겁니다.
