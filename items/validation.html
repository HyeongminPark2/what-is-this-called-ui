2 이름부르는 말이 여러 개다

한국어검증, 유효성 검사, 입력 확인
영어validation, form validation, constraint validation
같이 쓰는 말칠 때마다 검사하는 것이 실시간 검증(live·inline validation), 보낼 때 한꺼번에 하는 것이 제출 검증입니다. 브라우저가 required·pattern으로 해 주는 것을 제약 검증 API(Constraint Validation API)라 합니다.
자주 잘못 부름오류 메시지 — 오류 메시지는 결과를 보여 주는 쪽, 검증은 판단하는 쪽입니다.
인증(authentication) — 사람이 맞는지 확인하는 일과 완전히 다릅니다. 영어로도 다른 단어입니다.
폼 — 폼 설계의 한 부분이지 폼 자체가 아닙니다.

한번 틀린 칸은 고치는 즉시 다시 검사한다
제출하면 첫 오류 칸으로 초점을 옮긴다
  1. 치는 중엔 조용히 on input: 안 함두 글자 쳤는데 빨개지면 재촉으로 느낀다
  2. 떠날 때 검사 on blur다 쳤다고 볼 수 있는 시점. 기본으로 삼는다
  3. 메시지는 칸 밑 같은 자리칸에서 멀면 어느 칸 얘기인지 모른다
  4. 기계에게 알리기 aria-invalid / describedby빨간 테두리는 눈으로만 보인다
  5. 고치면 즉시 풀기 re-validate on input한번 틀린 칸만. 이때는 칠 때마다 검사해도 안 거슬린다
  6. 제출하면 초점 이동 focus first error오류가 화면 밖에 있으면 아무 일도 안 일어난 것처럼 보인다

규칙은 비대칭입니다 — 처음에는 떠날 때 검사하고, 한번 틀린 칸은 칠 때마다 검사합니다. 처음부터 칠 때마다 검사하면 다 치기 전에 빨개져 재촉당하는 느낌이 들고, 고친 뒤에도 떠날 때까지 빨간 채로 두면 고쳤는데도 틀렸다고 하는 것처럼 보입니다. 대부분의 폼 라이브러리가 이 두 단계를 기본값으로 둡니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 형식이 정해진 값 — 번호 자릿수, 날짜, 전자우편
  • 서버만 아는 조건 — 중복, 잔액, 권한
  • 되돌리기 어려운 동작 직전

이럴 때는 안 쓴다

  • 치는 도중에 빨갛게 — 다 치기 전에 틀렸다고 하지 않는다
  • '올바른 값을 입력하세요' — 무엇이 어떻게 틀렸는지 적는다
  • 색만으로 알리기 — 테두리 빨강만으로는 못 보는 사람이 있다
  • 브라우저 검사만 믿기 — 서버가 다시 검사해야 한다

대신 이걸 — 보여 주기만 하면 오류 메시지, 확인만 받으면 다이얼로그, 결과를 알리면 토스트.

8 최소 마크업과 키보드이 검증의 계약서

aria-invalid로 틀렸음을, aria-describedby로 무엇이 틀렸는지를 칸에 붙입니다.

<label for="no">사업자번호</label>
<input id="no" inputmode="numeric"
       aria-invalid="true" aria-describedby="no-err">
<p id="no-err">10자리를 채워 주세요</p>

// 떠날 때 한 번, 그 뒤로는 칠 때마다
input.addEventListener('blur', () => { touched = true; check(); });
input.addEventListener('input', () => { if (touched) check(); });

// 제출하면 첫 오류 칸으로
form.querySelector('[aria-invalid="true"]')?.focus();
키일어나야 하는 일
aria-invalid="true"'잘못된 값'으로 읽힌다. 고쳐지면 지운다
aria-describedby메시지를 칸에 묶는다. 칸에 초점이 가면 메시지까지 읽힌다
제출 뒤 Tab 없이첫 오류 칸에 초점을 옮긴다. 안 그러면 어디가 문제인지 찾아 헤맨다
색 + 글자빨간 테두리에 ✕ 와 문장을 함께. 색만으로는 안 된다
required·pattern브라우저가 알아서 막아 준다. 다만 메시지가 영어일 수 있다
novalidate직접 메시지를 그리려면 브라우저 기본 말풍선을 끈다
