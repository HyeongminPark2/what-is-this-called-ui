키보드 조작

Keyboard operability

키보드 조작은 화면의 모든 기능을 마우스 없이 키보드만으로도 쓸 수 있어야 한다는 요구입니다. 손을 자유롭게 쓰지 못하는 사람뿐 아니라 마우스가 고장 난 사람에게도 해당합니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

세 버튼은 똑같아 보이지만 키보드로 다뤄 보면 전혀 다르게 동작합니다. 마우스는 쓰지 말고 Tab·Enter·Space로만 눌러 보세요.
<div>로 만든 버튼은 Tab을 눌러도 포커스가 건너뛰고, tabindex를 더하면 포커스는 가지만 Enter나 Space를 눌러도 반응하지 않습니다. 이때 기록에 '아무 일도 안 일어남'이 찍힙니다.

2 이름같은 것을 부르는 여러 이름

한국어키보드 조작, 키보드 접근성, 키보드만으로
영어keyboard operability, keyboard accessibility, keyboard trap
같이 쓰는 말포커스가 어딘가에 갇혀 빠져나올 수 없게 된 상태는 키보드 트랩(keyboard trap)이라고 부르는데, 일부러 가두는 포커스 트랩과 달리 사고를 가리키는 말입니다. 부품마다 정해 둔 키 동작 규칙은 키보드 인터랙션 패턴(ARIA Authoring Practices)이라고 합니다.
자주 잘못 부르는 이름단축키 — 단축키는 기능을 더 빠르게 쓰는 방법이고, 키보드 조작은 키보드로 그 기능을 쓸 수 있기는 한가를 따집니다.
포커스 — 포커스는 '지금 어디에 있는가'를 말하고, 키보드 조작은 '거기서 무엇을 할 수 있는가'를 말합니다.
키보드 트랩 — 포커스가 빠져나오지 못하는 사고를 말합니다. 모달이 일부러 거는 포커스 트랩과 헷갈리지 않아야 합니다.

키보드 조작을 한 줄로 정리하면 — 누르는 것은 <button>으로, 다른 곳으로 이동하는 것은 <a href>로 만듭니다. 같은 동작을 div로 만들면 브라우저가 해 주던 다섯 가지를 직접 짜야 합니다.

4 태그에 따라 달라지는 키보드 동작모양이 같은 버튼이 태그마다 다르게 동작하는 모습

5 해부도부분마다 붙은 이름

저장하기
<button> — 포커스·Enter·Space를 기본 제공
<div onclick> — 키보드로는 갈 수 없음
tabindex="0" + role="button" — 포커스는 갈 수 있음
keydown: Enter · Space — 직접 짜야 함
화살표 · Esc · Home/End — 부품마다 정해진 키가 있음
  1. 누를 것 button원래 태그를 쓰면 아래 다섯 줄에 적힌 동작을 브라우저가 모두 처리합니다
  2. 태그가 주는 것 <button>포커스 순서, Enter, Space, 역할, 비활성 처리를 기본으로 제공합니다
  3. div로 만든 버튼 <div onclick>Tab으로 포커스가 아예 가지 않아서 마우스로만 쓸 수 있습니다
  4. 순서에 넣기 tabindex="0" + role포커스가 갈 수는 있게 되지만, 키로 누를 수는 아직 없습니다
  5. 키 처리 keydownEnter와 Space 입력을 직접 받아서 click 이벤트를 일으켜야 합니다
  6. 부품별 키 동작 화살표 · Esc · Home/End탭, 라디오, 메뉴처럼 부품마다 정해진 키 동작이 있습니다

<div>로 버튼을 만들면 tabindex, role, Enter, Space, 비활성 처리까지 다섯 가지를 직접 챙겨야 합니다. 게다가 Space는 기본으로 화면을 스크롤하기 때문에 preventDefault()로 스크롤도 막아야 합니다. 이 다섯 가지를 전부 맞춰도 <button> 태그를 쓴 것보다 나은 점은 없습니다. 그래서 이 항목의 결론은 언제나 "원래 태그를 쓰세요"입니다.

6 쓸 때 / 안 쓸 때

키보드 조작을 확인해야 하는 경우

  • 모든 화면을 만들 때. 마우스를 치우고 화면을 처음부터 끝까지 한 번 써 봅니다
  • 부품을 새로 만들 때. 같은 일을 하는 원래 태그가 있는지 먼저 찾습니다
  • 탭, 메뉴, 라디오처럼 화살표 키로 항목 사이를 옮겨 다니는 부품을 만들 때

키보드 조작을 망가뜨리는 실수

  • <div>나 <span>에 onclick만 걸 때
  • 포커스가 빠져나올 수 없게 만들 때(키보드 트랩). 키보드 사고 가운데 가장 심각합니다
  • 호버로만 열리는 메뉴나 드래그로만 되는 정렬처럼 마우스로만 할 수 있는 동작만 둘 때
  • tabindex에 1 이상의 값을 줄 때

키보드 조작과 이어지는 주제는 다른 항목에서 다룹니다 — 포커스가 어디 있는지 보이게 하는 방법은 포커스에서, 모달 안에 포커스를 가두는 방법은 포커스 트랩에서 다룹니다. 어떤 태그를 골라야 하는지는 시맨틱 태그를 보세요.

8 최소 마크업과 키보드원래 태그를 쓰면 저절로 지켜지는 규칙

가장 간단한 해결책은 태그를 button으로 바꾸는 것입니다. 그래도 div로 만들어야 한다면 필요한 코드를 아래에 적어 두었습니다.

<!-- 이 한 줄이면 된다 -->
<button type="button">저장하기</button>

<!-- 굳이 div 로 만든다면 이만큼이 필요하다 -->
<div role="button" tabindex="0"
     aria-disabled="false">저장하기</div>

el.addEventListener('keydown', (e) => {
  if (e.key === 'Enter' || e.key === ' ') {
    e.preventDefault();      // Space 는 기본이 '화면 스크롤'이다
    el.click();
  }
});
키와 마크업그때 일어나야 하는 일
Tab다음 요소로 포커스가 옮겨 갑니다. 옮겨 가는 순서는 화면에 보이는 순서와 같아야 합니다
Enter버튼이나 링크를 누릅니다
Space버튼이나 체크박스를 누릅니다. Space의 기본 동작은 화면 스크롤이라 직접 만든 버튼에서는 막아야 합니다
Esc모달, 메뉴, 콤보박스를 닫습니다
←→↑↓탭, 라디오, 메뉴 안에서 항목 사이를 옮겨 다닙니다
HomeEnd목록의 처음이나 끝으로 갑니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

가장 확인하기 쉬운 접근성 항목접근성 항목 가운데 직접 확인하기가 가장 쉽습니다. 마우스를 치우고 화면을 끝까지 써 보면 되므로 따로 도구나 지식이 필요 없습니다.
Tab이 가지 않는 요소 자동 검사Playwright로 Tab을 눌러 가며 activeElement를 기록하면, 누를 수는 있는데 Tab으로 포커스가 가지 않는 요소를 CI에서 찾아낼 수 있습니다.
키 동작이 구현된 라이브러리 쓰기부품을 직접 만들기 전에 키 동작이 이미 구현된 라이브러리를 찾는 편이 대개 낫습니다. 콤보박스 하나에만 키 처리 코드가 열 줄 넘게 들어가기 때문입니다.
드래그로만 되는 순서 바꾸기순서 바꾸기를 드래그로만 만들면 키보드로는 순서를 아예 바꿀 수 없으므로, '위로/아래로' 버튼을 함께 둡니다.

플랫폼 차이 때문에 자주 생기는 문제 — 앱에서는 키보드보다 스크린 리더 제스처와 스위치 제어를 더 많이 따집니다. 그래서 같은 요구가 웹에서는 "Tab으로 되나요", 앱에서는 "VoiceOver로 되나요"라는 질문으로 나오지만 묻는 내용은 같습니다.
