핸드오프

Handoff

핸드오프는 시안을 개발 쪽에 넘기는 일입니다. 이때 넘겨야 하는 것은 그림 파일만이 아니라, 개발자가 화면을 실제로 만들 수 있을 만큼의 정보입니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

체크를 끄면 그림만 받은 상태가 됩니다. ✕가 붙은 항목은 개발하는 동안 하나씩 물어보게 되는 것들이고, 이렇게 묻고 답하는 데 일정의 상당 부분이 들어갑니다.
그림에서 재서 알 수 있는 것은 두 가지뿐이고, 나머지 여덟 가지는 글로 적어 넘겨야 합니다.

2 이름같은 것을 부르는 여러 이름

한국어핸드오프, 전달, 개발 전달, 스펙
영어handoff, design handoff, spec, redline
같이 쓰는 말치수를 적어 넣은 그림을 레드라인(redline) 또는 스펙이라고 하고, 시안 도구가 값을 자동으로 보여 주는 화면을 인스펙트(inspect) 화면이라고 합니다. 그림 속 부품과 코드 부품을 짝지어 두는 것을 코드 커넥트라고 부르기도 합니다. 한 번 넘기고 끝나지 않고 디자인과 개발 사이를 계속 오간다는 뜻으로 지속적 핸드오프라는 말도 씁니다.
자주 잘못 부르는 이름스펙 — 기능 명세서를 뜻하기도 하지만, 핸드오프에서 말하는 스펙은 화면의 치수와 규칙입니다.
QA — 다 만든 뒤에 확인하는 일이고, 핸드오프는 만들기 전에 하는 일입니다.
리뷰 — 의견을 주고받는 일이고, 핸드오프는 만들 정보를 넘기는 일입니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

15부에서 다루는 현장 용어는 화면 부품의 이름 대신 디자인과 개발이 함께 일하는 단계를 가리킵니다. 아래 네 가지를 물어보면 이 용어들을 서로 구별할 수 있습니다.

무엇을 가리키는가어느 작업 단계에서 나오는가개발 쪽에서 대응하는 것잘못 알아들으면 생기는 일
와이어프레임과 목업과 시안그림이 얼마나 진짜 같은지기획 ~ 디자인마크업 구조 ~ 완성 화면묻는 것과 어긋난 리뷰가 돌아옴
디자인 시스템규칙과 부품과 문서프로젝트 내내토큰과 컴포넌트 라이브러리스타일 가이드와 섞어 부름
컴포넌트와 인스턴스원본과 복제본시안 작업컴포넌트 정의와 사용원본을 고쳐 전체가 바뀜
배리언트와 프롭같은 부품의 정해진 변형시안 작업props상태와 섞어 부름
오토 레이아웃자동 배치시안 작업flexbox‘여백이 자동’이라는 말을 못 알아들음
프로토타입눌리는 시안리뷰 · 사용자 시험아직 대응하는 코드가 없음다 만든 것으로 오해함
핸드오프넘기는 일개발 시작 전스펙 읽기그림만 받고 규칙은 못 받음
에셋 내보내기그림 파일 넘기기개발 중srcset · SVG1배 파일만 받아 그림이 뭉개짐
디자인 리뷰고칠 거리를 만드는 말단계마다코드 리뷰의견이 너무 이르거나 늦음
버전 관리어느 것이 지금 것인지 가리기프로젝트 내내커밋 메시지final 사슬이 생김

핸드오프를 한 줄로 정리하면 — 그림에서 재서 알 수 있는 것은 간격·크기와 색·글꼴 두 가지뿐입니다. 나머지 여덟 가지는 적어 주지 않으면 개발자가 하나씩 물어보게 됩니다.

4 그림과 함께 넘어오는 정보그림에서 재는 것과 물어야 하는 것

5 해부도부분마다 붙은 이름

그림에서 잴 수 있는 것은 간격 · 색 · 크기
토큰 이름이 accent인지 brand인지
상태는 호버 · 누름 · 비활성 · 로딩
글이 길거나 폰이거나 비어 있을 때
문구는 버튼 글자와 오류 문장
그림만 받으면 여덟 가지를 물어보게 됨
  1. 잴 수 있는 것 간격 · 색 · 크기시안 도구가 자동으로 보여 줍니다
  2. 토큰 이름 값이 아니라 이름#2f6df6이 어떤 토큰인지를 적어 줍니다
  3. 상태 호버 · 누름 · 비활성시안에는 기본 상태 하나만 그려져 있습니다
  4. 경계 길어질 때 · 좁아질 때글이 길어지거나 화면이 좁아질 때 어떻게 보일지 정합니다
  5. 없는 화면 빈 · 로딩 · 오류데이터가 가득 찬 시안에는 빈 화면, 로딩, 오류 화면이 보이지 않습니다
  6. 문구 · 에셋 글자와 파일버튼에 들어갈 글자와 아이콘 파일 형식을 정합니다

스펙은 짧아도 됩니다. 예를 들어 '이 파랑은 --accent', '글이 길면 두 줄까지', '560px 아래에서 한 단', '목록이 비면 가맹점 등록 버튼'처럼 시안 옆에 메모 열 줄 정도만 적어 두어도 대개 충분합니다. 분량보다 중요한 것은 그림에서 알 수 없는 것만 골라 적는 것입니다. 적어야 할 항목은 화면이 달라도 거의 매번 같기 때문에, 한 번 만들어 둔 점검표를 화면마다 다시 쓰면 됩니다.

6 쓸 때 / 안 쓸 때

핸드오프할 때 지킬 것

  • 그림에서 알 수 없는 것만 골라 적습니다
  • 같은 점검표를 매번 다시 씁니다
  • 색과 간격은 값 대신 토큰 이름으로 적습니다

핸드오프할 때 피할 것

  • 그림만 넘기고 '보면 알죠'라고 할 때. 개발자가 여덟 번 물어보게 됩니다
  • 값을 그대로 적을 때. #2f6df6 대신 토큰 이름을 적어야 합니다
  • 상태와 빈 화면을 그리지 않을 때. 그 화면들이 개발하는 도중에 즉흥으로 정해집니다
  • 한 번 넘기고 끝났다고 여길 때. 개발하는 동안에도 질문과 수정이 계속 오갑니다

관련 주제는 다른 항목에서 다룹니다 — 그림의 단계 구분은 와이어프레임과 목업과 시안에서, 부품 규칙은 디자인 시스템에서, 그림 파일을 넘기는 방법은 에셋 내보내기에서 다룹니다.

8 핸드오프 점검표그림에서 알 수 없는 열 가지

화면이 달라도 매번 같은 열 가지 항목을 채워 넘깁니다.

# 핸드오프 점검표 — 그림에서 알 수 없는 것만

1. 토큰 이름  : 이 파랑은 --accent, 간격은 --space-3
2. 상태       : 기본 / 호버 / 누름 / 비활성 / 로딩
3. 글이 길면  : 두 줄까지, 넘으면 말줄임
4. 좁아지면   : 560px 아래에서 한 단, 메뉴는 접기
5. 비어 있으면: "아직 등록한 가맹점이 없어요" + [가맹점 등록]
6. 불러오는 중: 스켈레톤 세 줄
7. 실패하면   : "불러오지 못했습니다" + [다시 시도]
8. 문구       : 버튼은 "내보내기" (확인 아님)
9. 움직임     : 240ms ease-out, 모션 줄이기에서는 0
10. 에셋      : 아이콘 SVG, 사진 WebP 2x
지킬 규칙그렇게 하는 이유
상태에 초점도 넣기호버만 그려 두면 키보드 초점 상태가 빠지기 쉽습니다
대비비 적기흐린 회색 글씨는 시안에서는 보기 좋아도 대비비 기준을 통과하지 못하는 경우가 많습니다
아이콘의 이름 적기아이콘만 있는 버튼은 스크린 리더가 뭐라고 읽을지를 적어 줍니다
눌리는 넓이 적기눌리는 넓이는 보이는 크기와 따로 정하는 값이라 시안에는 드러나지 않습니다
모션 줄이기에서의 동작 적기움직임을 적을 때 모션 줄이기 설정에서 어떻게 되는지도 함께 적습니다
읽는 순서 적기눈에 보이는 차례와 Tab 순서가 달라야 하면 적어 둡니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

필요한 데이터 함께 정하기핸드오프 때 화면에 필요한 값을 함께 정해 두면 API 설계를 그만큼 일찍 시작할 수 있습니다.
빠진 화면 때문에 늘어나는 일정화면마다 빈 화면, 로딩, 오류를 더하면 만들 화면 수가 세 배가 됩니다. 이 화면들이 핸드오프 때 드러나야 일정에 반영할 수 있습니다.
문구를 표 하나로 받기버튼 글자와 오류 문장을 표로 받으면 그 표를 그대로 문구 파일로 쓸 수 있습니다. 문구를 정하는 기준은 말투와 높임 항목에 있습니다.
토큰을 코드로 내보내기시안 도구에 정의한 변수를 CSS 변수로 뽑아 그대로 쓰면, 값을 손으로 옮겨 적다가 틀리는 일이 없습니다.

10 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

플랫폼마다 시안 도구가 보여 주는 단위는 다르지만, 도구가 도와주는 범위는 모두 그림에서 잴 수 있는 것까지입니다.

웹인스펙트 화면과 메모
padding: 12px
color: --accent
시안 도구가 CSS 값을 보여 주지만, 토큰 이름과 상태, 경계는 사람이 적어야 합니다.
iOS웹과 같은 문제
spacing: 12pt
color: Accent
값을 pt 단위로 보여 줍니다. 사용자가 글자 크기를 키우는 다이내믹 타입에서 화면이 어떻게 되는지는 따로 물어야 합니다.
안드로이드웹과 같은 문제
padding: 12dp
color: colorPrimary
값을 dp 단위로 보여 줍니다. 기기마다 화면 폭이 다양해서 경계에 관한 질문이 더 많이 생깁니다.

플랫폼 차이 때문에 자주 생기는 문제 — "시안 다 나왔으니 개발만 하면 됩니다"라는 말이 자주 틀리는 것도 그림에 없는 정보 때문입니다. 시안에 그려진 것은 기본 상태 한 장이지만, 실제로 만들어야 하는 것은 상태 다섯 가지와 경계 세 가지입니다. 핸드오프 점검표를 한 번 만들어 두면 일정을 잡을 때 이 차이가 드러나고, 개발하면서 묻고 답하는 일도 크게 줄어듭니다.
