HIG와 Material의 차이

HIG vs Material

같은 화면을 세 곳에서 그리면 자리가 달라집니다. 어느 쪽이 옳은 게 아니라 이미 배운 자리가 다릅니다.

1 실물 — 직접 만져 보기

보고 싶은 것을 골라 보세요 — 뒤로 가는 길 · 주 동작의 자리 · 켜고 끄는 부품 · 알림의 버튼 차례 · 아래 탭이 세 곳에서 어떻게 다른지 나란히 나옵니다.

2 이름부르는 말이 여러 개다

한국어애플 휴먼 인터페이스 가이드라인, 머티리얼 디자인, 플랫폼 관례
영어Apple HIG (Human Interface Guidelines), Material Design 3
같이 쓰는 말애플 쪽이 HIG, 구글 쪽이 머티리얼(현재 M3)입니다. OS 가 정해 둔 모양을 그대로 쓰는 것을 네이티브 느낌이라 하고, 한 벌로 양쪽에 올리는 것을 크로스 플랫폼이라 합니다. 어느 쪽도 아닌 자기 모양을 쓰는 것은 브랜드 UI입니다.
자주 잘못 부름디자인 시스템 — HIG·M3 는 OS 의 관례 모음이고, 디자인 시스템은 한 조직의 부품 모음입니다.
머티리얼 — 구글 제품의 모양이지 '안드로이드의 유일한 답'은 아닙니다.
네이티브 — 기술(스위프트·코틀린)을 가리키기도 하고 모양을 가리키기도 해 말이 자주 엇갈립니다.

3 가르는 기준형제들과 비교하는 네 축

PC와 폰은 다른 기계가 아니라 다른 전제입니다. 이 네 가지만 물어보면 갈립니다.

무엇이 다른가폰에서는PC에서는안 챙기면
브레이크포인트폭에 따른 배치한 단여러 단중간 폭에서 깨진다
터치 타깃누를 수 있는 넓이44px 이상24px도 된다옆 것이 눌린다
호버가 없는 세계올려놓기가 되나없다있다영영 못 보는 정보가 생긴다
시스템 백뒤로 가는 길OS가 준다브라우저 버튼모달 대신 앱이 나간다
화면 밀도1px 의 실제 화소 수2~3배1~2배그림이 뭉갠다
뷰포트 단위100vh 가 가리키는 높이주소창 때문에 흔들린다고정바닥 버튼이 잘린다
폰 키보드올라오는 자리화면 절반없다입력칸이 가려진다
HIG와 Material의 차이OS 의 말투각자 다르다웹 관례어느 쪽에서도 어색하다

한 줄로 — 웹은 제3의 자리입니다. 세 곳을 다 흉내 내려다 셋 모두에서 어색해지느니, 웹의 관례를 지키는 편이 낫습니다.

4 같은 화면, 다른 자리무엇이 어디로 가나

5 해부도부분 이름이 제일 안 알려진 지식

뒤로 — iOS 는 ‹ 와 이전 화면 이름, 안드로이드는 ← 만
주 동작 — iOS 는 오른쪽 위, 안드로이드는 오른쪽 아래 FAB
확인·취소 — iOS 는 반반, 안드로이드는 둘 다 오른쪽
탭 — iOS 는 색만, M3 는 알약 바탕까지
웹은 제3의 자리 — 흉내보다 웹 관례
한쪽 규격을 그대로 옮기면 둘 다에서 어색하다
  1. 뒤로 ‹ 이름 / ← / 브라우저iOS 만 이전 화면 이름을 함께 적는다
  2. 주 동작 오른쪽 위 / FAB / 폼 아래안드로이드만 떠 있는 동그란 버튼을 쓴다
  3. 확인·취소 반반 / 오른쪽 / 오른쪽iOS 만 반으로 나눠 놓는다
  4. 탭 색 / 알약 / 위쪽M3 는 색만으로 안 가른다
  5. 웹 제3의 자리흉내 내기보다 웹 관례를 따른다
  6. 섞으면 둘 다 어색아이폰의 FAB, 안드로이드의 ‹ 는 둘 다 틀린 모양

실무에서 자주 나오는 결론은 '하나로 통일한다'입니다. OS 마다 확인·취소 차례를 바꾸면 코드가 갈리고 시험할 화면이 두 배가 되는데, 얻는 것은 미묘한 익숙함뿐입니다. 다만 뒤로가기만은 예외입니다 — 그건 취향이 아니라 OS 가 쥐고 있는 동작이라, 따르지 않으면 앱이 꺼지는 쪽으로 바로 드러납니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 뒤로가기는 OS 를 따른다 — 선택이 아니다
  • 셋 다 올리는 앱이라면 한 가지로 통일하고 그렇게 적어 둔다
  • OS 부품을 쓸 때는 그 OS 의 자리에

이럴 때는 안 쓴다

  • iOS 화면에 FAB — 그 자리에 아무것도 없는 OS 다
  • 안드로이드에서 ‹ 이전 화면 이름 — 거기선 ← 만 쓴다
  • 웹에 아래 탭을 PC 폭에서도 — 아래쪽은 웹의 자리가 아니다
  • OS 마다 확인·취소를 바꾸기 — 얻는 것보다 비싸다

대신 이걸 — 웹의 자리는 앱바·탭·다이얼로그 항목에 정리돼 있다. 뒤로가기는 시스템 백.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 따를 것과 정할 것이 관례의 계약서

따라야 하는 것과 정하면 되는 것을 갈라 적어 둡니다.

// 반드시 OS 를 따른다 — 안 따르면 바로 사고가 난다
- 뒤로가기 (시스템 백 · 가장자리 제스처)
- 세이프 에어리어 · 노치 · 홈 인디케이터
- 글자 크기 설정 · 모션 줄이기 · 다크 모드

// 팀이 정하면 되는 것 — 하나로 통일하는 편이 싸다
- 확인 · 취소의 차례
- 주 동작의 자리
- 스위치냐 체크박스냐
- 탭을 위에 둘지 아래에 둘지

/* 웹에서 폰 폭일 때만 아래 탭을 쓰고 싶다면 */
@media (max-width: 560px) {
  .tabs { position: fixed; bottom: 0; padding-bottom: env(safe-area-inset-bottom); }
}
키일어나야 하는 일
OS 부품을 쓰면 접근성이 딸려 온다시스템 스위치·날짜 선택기는 스크린 리더 대응이 이미 들어 있다
직접 만들면 직접 챙긴다모양만 흉내 내고 role·키보드를 빼면 껍데기가 된다
글자 크기 설정두 OS 모두 사용자가 키울 수 있다. px 로 못 박으면 안 커진다
모션 줄이기·다크 모드OS 설정이라 어느 쪽에서든 따라야 한다
세이프 에어리어노치·홈 인디케이터는 협상 대상이 아니다
뒤로가기따르지 않으면 앱이 꺼진다. 가장 먼저 확인할 것

9 서버 쪽으로 치면백엔드 감각으로 번역

화면이 둘이면 API 도 둘이 된다OS 마다 흐름을 다르게 만들면 단계와 응답도 갈립니다. 통일하면 서버가 한 벌로 끝납니다.
기기별 통계같은 기능이 한쪽 OS 에서만 안 쓰인다면 자리가 달라서일 수 있습니다.
푸시 알림두 OS 의 체계가 완전히 달라 서버 쪽 작업이 두 벌입니다. 일정에 따로 잡습니다.
