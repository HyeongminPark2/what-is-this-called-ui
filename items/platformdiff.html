HIG와 Material의 차이

HIG vs Material

같은 화면이라도 iOS와 안드로이드, 웹에서 그리면 버튼이 놓이는 자리가 달라집니다. 어느 쪽이 옳다기보다, 각 플랫폼 사용자가 이미 익숙해진 자리가 서로 다릅니다.

2 이름같은 것을 부르는 여러 이름

한국어애플 휴먼 인터페이스 가이드라인, 머티리얼 디자인, 플랫폼 관례
영어Apple HIG (Human Interface Guidelines), Material Design 3
같이 쓰는 말애플이 낸 지침이 HIG이고, 구글이 낸 지침이 머티리얼(현재 M3)입니다. OS가 정해 둔 모양을 그대로 쓰는 것을 네이티브 느낌이라고 하고, 코드 한 벌로 두 OS에 앱을 올리는 것을 크로스 플랫폼이라고 합니다. 어느 OS의 모양도 따르지 않고 자기 회사만의 모양을 쓰면 브랜드 UI라고 부릅니다.
자주 잘못 부르는 이름디자인 시스템 — HIG와 M3는 OS가 정한 관례 모음이고, 디자인 시스템은 한 조직이 만들어 쓰는 부품 모음입니다.
머티리얼 — 머티리얼은 구글 제품의 모양일 뿐, 안드로이드 앱이 꼭 따라야 하는 유일한 모양은 아닙니다.
네이티브 — 스위프트나 코틀린 같은 개발 기술을 가리킬 때도 있고 OS 고유의 모양을 가리킬 때도 있어서, 대화에서 뜻이 자주 엇갈립니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

PC와 폰의 차이는 기계 자체보다 화면을 쓰는 전제에 있습니다. 아래 네 가지를 물어보면 두 환경이 어디서 갈리는지 알 수 있습니다.

무엇이 다른가폰에서는PC에서는안 챙기면
브레이크포인트폭에 따른 배치한 단여러 단중간 폭에서 깨진다
터치 타깃누를 수 있는 넓이44px 이상24px도 된다옆 것이 눌린다
호버가 없는 세계올려놓기가 되나없다있다영영 못 보는 정보가 생긴다
시스템 백뒤로 가는 길OS가 준다브라우저 버튼모달 대신 앱이 나간다
화면 밀도1px의 실제 화소 수2~3배1~2배그림이 뭉개진다
뷰포트 단위100vh가 가리키는 높이주소창 때문에 흔들린다고정바닥 버튼이 잘린다
폰 키보드올라오는 자리화면 절반없다입력칸이 가려진다
HIG와 Material의 차이OS의 말투각자 다르다웹 관례어느 쪽에서도 어색하다

HIG와 Material의 차이를 한 줄로 정리하면 — 웹에는 iOS나 안드로이드와 다른 웹만의 관례가 있습니다. 두 OS의 모양을 다 흉내 내다 보면 어느 쪽에서도 어색해지므로, 웹에서는 웹의 관례를 지키는 편이 낫습니다.

4 같은 화면, 다른 자리무엇이 어디로 가나

5 해부도부분마다 붙은 이름

뒤로 — iOS 는 ‹ 와 이전 화면 이름, 안드로이드는 ← 만
주 동작 — iOS 는 오른쪽 위, 안드로이드는 오른쪽 아래 FAB
확인·취소 — iOS 는 반반, 안드로이드는 둘 다 오른쪽
탭 — iOS 는 색만, M3 는 알약 바탕까지
웹은 제3의 자리 — 흉내보다 웹 관례
한쪽 규격을 그대로 옮기면 둘 다에서 어색하다
  1. 뒤로 ‹ 이름 / ← / 브라우저iOS만 뒤로 버튼에 이전 화면 이름을 함께 적습니다
  2. 주 동작 오른쪽 위 / FAB / 폼 아래안드로이드만 화면 위에 떠 있는 동그란 버튼을 씁니다
  3. 확인·취소 반반 / 오른쪽 / 오른쪽iOS만 확인과 취소를 반씩 나눠 놓습니다
  4. 탭 색 / 알약 / 위쪽M3는 고른 탭을 색만으로 구분하지 않고 바탕까지 깝니다
  5. 웹 제3의 자리두 OS를 흉내 내기보다 웹 관례를 따릅니다
  6. 섞으면 둘 다 어색아이폰 앱의 FAB와 안드로이드 앱의 ‹는 둘 다 그 OS의 관례에 맞지 않는 모양입니다

실무에서는 '하나로 통일한다'는 결론이 자주 나옵니다. OS마다 확인·취소 차례를 바꾸면 코드가 둘로 갈리고 시험할 화면이 두 배가 되지만, 그 대가로 얻는 것은 사용자가 조금 더 익숙하게 느끼는 정도입니다. 다만 뒤로가기는 예외입니다. 뒤로가기는 취향의 문제가 아니라 OS가 처리하는 동작이기 때문에, 따르지 않으면 뒤로가기를 눌렀을 때 앱이 꺼지는 식으로 문제가 바로 드러납니다.

6 쓸 때 / 안 쓸 때

HIG와 Material의 차이를 쓰는 경우

  • 뒤로가기를 다룰 때. 고를 수 있는 문제가 아니므로 OS를 따릅니다
  • 세 플랫폼에 모두 올리는 앱을 만들 때. 한 가지로 통일하고 그 결정을 문서로 적어 둡니다
  • OS가 제공하는 부품을 쓸 때. 부품을 그 OS의 자리에 둡니다

HIG와 Material의 차이를 쓰지 않는 경우

  • iOS 화면에 FAB를 둘 때. iOS에는 화면 오른쪽 아래에 버튼을 띄우는 관례가 없습니다
  • 안드로이드 화면에 ‹ 이전 화면 이름을 적을 때. 안드로이드에서는 ←만 씁니다
  • 웹에서 PC 폭일 때도 아래 탭을 둘 때. 웹에서는 탭을 아래에 두는 관례가 없습니다
  • OS마다 확인·취소 차례를 바꿀 때. 들이는 비용에 비해 얻는 것이 적습니다

HIG와 Material의 차이 대신 다른 것을 써야 하는 경우 — 웹에서 부품을 놓는 자리는 앱바·탭·다이얼로그 항목에 정리해 두었고, 뒤로가기는 시스템 백 항목에서 다룹니다.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 따를 것과 정할 것팀 문서에 적어 둘 목록

OS를 반드시 따라야 하는 것과 팀이 정하면 되는 것을 나눠 적어 둡니다.

// 반드시 OS를 따른다. 따르지 않으면 바로 문제가 생긴다
- 뒤로가기 (시스템 백 · 가장자리 제스처)
- 세이프 에어리어 · 노치 · 홈 인디케이터
- 글자 크기 설정 · 모션 줄이기 · 다크 모드

// 팀이 정하면 되는 것. 하나로 통일하는 편이 비용이 적게 든다
- 확인 · 취소의 차례
- 주 동작의 자리
- 스위치냐 체크박스냐
- 탭을 위에 둘지 아래에 둘지

/* 웹에서 폰 폭일 때만 아래 탭을 쓰고 싶다면 */
@media (max-width: 560px) {
  .tabs { position: fixed; bottom: 0; padding-bottom: env(safe-area-inset-bottom); }
}
키와 동작그때 일어나야 하는 일
OS 부품을 쓰면 접근성이 딸려 온다시스템이 제공하는 스위치나 날짜 선택기에는 스크린 리더 대응이 이미 들어 있습니다
직접 만들면 직접 챙긴다모양만 흉내 내고 role과 키보드 조작을 빼면 보기에만 같고 스크린 리더나 키보드로는 쓸 수 없는 부품이 됩니다
글자 크기 설정두 OS 모두 사용자가 글자 크기를 키울 수 있습니다. 글자 크기를 px로 고정하면 설정을 바꿔도 커지지 않습니다
모션 줄이기·다크 모드사용자가 OS에서 고른 설정이므로 어느 플랫폼에서든 따라야 합니다
세이프 에어리어노치와 홈 인디케이터가 차지하는 자리는 팀이 정할 수 있는 것이 아니므로 반드시 비워 둡니다
뒤로가기따르지 않으면 뒤로가기 한 번에 앱이 꺼집니다. 가장 먼저 확인해야 합니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

화면이 둘이면 API 도 둘이 된다OS마다 화면 흐름을 다르게 만들면 API의 단계와 응답도 OS별로 갈립니다. 흐름을 통일하면 서버 쪽도 한 벌로 끝납니다.
기기별 통계같은 기능이 한쪽 OS에서만 거의 쓰이지 않는다면, 그 OS에서 버튼이 다른 자리에 있어서일 수 있습니다.
푸시 알림두 OS의 푸시 알림 체계가 완전히 달라서 서버 쪽 작업을 두 번 해야 합니다. 그래서 일정을 따로 잡습니다.

플랫폼 차이 때문에 자주 생기는 문제 — "아이폰처럼 만들어 주세요"와 "안드로이드도 되게"가 한 요청에 같이 들어오면, 버튼을 어느 OS의 자리에 둘지 정해야 할 일이 생깁니다. 이때 비용이 가장 적게 드는 답은 "뒤로가기와 세이프 에어리어는 OS를 따르고, 나머지는 한 가지로 통일합니다"입니다. 따르지 않았을 때 실제로 문제가 생기는 것은 앞의 두 가지뿐이고, 나머지는 통일해도 사용자가 불편을 거의 느끼지 않기 때문입니다.
