배리언트와 프롭

Variants & props

배리언트는 같은 부품에 미리 정해 둔 변형입니다. 크기나 강조 같은 변형의 축을 하나 늘릴 때마다 만들어야 할 칸이 곱으로 늘어납니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

축을 켜고 끄면서 칸 수가 어떻게 바뀌는지 보세요. 축이 늘 때마다 9 → 18 → 54로 늘어납니다.
시안에서는 54칸을 손으로 만들어야 하고, 고칠 때마다 54칸을 모두 손대야 합니다. 배리언트를 미리 설계해야 하는 이유가 이 작업량입니다. 같은 변형이 코드에서는 props 세 개로 끝납니다.

2 이름같은 것을 부르는 여러 이름

한국어배리언트, 변형, 프롭, 속성
영어variant, variant property, props, component set
같이 쓰는 말변형의 축을 프로퍼티(property), 그 축의 값을 배리언트라고 부릅니다. 같은 부품의 변형을 모아 둔 것은 컴포넌트 세트입니다. 코드 쪽에서는 같은 개념을 props라고 부르고, 클래스 이름으로 적으면 btn--primary 같은 모디파이어(BEM)가 됩니다.
자주 잘못 부르는 이름상태 — 호버나 누름은 사용자의 조작으로 생기는 것이고, 배리언트는 화면을 만드는 쪽이 골라서 정하는 것입니다.
컴포넌트 — 컴포넌트는 부품 자체를 가리키고, 배리언트는 그 부품 안의 변형을 가리킵니다.
스타일 — 색이나 글꼴만 바뀌는 변형뿐 아니라 구조가 바뀌는 변형도 배리언트입니다.

3 가르는 기준헷갈리는 형제 부품과 견주는 네 가지 기준

15부에서 다루는 현장 용어는 화면 부품의 이름 대신 디자인과 개발이 함께 일하는 단계를 가리킵니다. 아래 네 가지를 물어보면 이 용어들을 서로 구별할 수 있습니다.

무엇을 가리키나언제 나오나개발 쪽 대응물잘못 알아들으면
와이어프레임과 목업과 시안얼마나 진짜 같은 그림인가기획 ~ 디자인마크업 구조 ~ 완성 화면엉뚱한 리뷰가 돌아온다
디자인 시스템규칙 + 부품 + 문서프로젝트 내내토큰 + 컴포넌트 라이브러리스타일 가이드와 섞인다
컴포넌트와 인스턴스원본과 복제본시안 작업컴포넌트 정의와 사용원본을 고쳐 전체가 바뀐다
배리언트와 프롭같은 부품의 정해진 변형시안 작업props상태와 섞인다
오토 레이아웃자동 배치시안 작업flexbox‘여백이 자동’을 못 알아듣는다
프로토타입눌리는 시안리뷰 · 사용자 시험아직 코드가 아니다다 된 줄 안다
핸드오프넘기는 일개발 시작 전스펙 읽기그림만 받고 규칙은 못 받는다
에셋 내보내기그림 파일 넘기기개발 중srcset · SVG1배만 받아 뭉갠다
디자인 리뷰고칠 거리를 만드는 말단계마다코드 리뷰너무 이르거나 너무 늦다
버전 관리어느 것이 지금 것인가프로젝트 내내커밋 메시지final 사슬이 생긴다

배리언트와 프롭을 한 줄로 정리하면 — 축을 늘리기 전에 칸 수를 곱해 보세요. 3×3×2는 18칸이지만, 값이 세 개인 축을 하나만 더해도 54칸이 됩니다.

4 축을 늘리면칸이 몇 개가 되나

5 해부도부분마다 붙은 이름

축 — 크기 · 강조 · 상태. 각각 값이 몇 개인가
저장저장저장
칸 수 = 축의 값을 모두 곱한 것
축을 하나 늘리면 칸이 몇 배가 된다
코드로는 props — 같은 축, 같은 값
상태(호버·누름)는 배리언트로 안 만들기도 한다
  1. 축 크기 · 강조 · 상태축마다 값이 몇 개인지 셉니다
  2. 칸 축의 곱칸 수는 축마다 값 개수를 곱한 수입니다. 3 × 3 × 2 = 18
  3. 곱의 무서움 +1 축 = ×N축을 하나 더하면 칸 수가 그 축의 값 개수만큼 몇 배로 늘어납니다
  4. 코드로는 props시안의 축은 코드의 props에 해당합니다
  5. 상태는 빼기 :hover · :active사용자의 조작으로 생기는 상태는 CSS에 맡깁니다
  6. 쪼개기 다른 부품으로모양이 많이 다르면 다른 부품으로 따로 만듭니다

축을 줄이는 방법은 두 가지입니다. 첫째는 상태를 빼는 것입니다. 호버와 누름, 초점은 사용자의 조작으로 생기기 때문에 시안에 칸으로 둘 필요가 없고, 코드에서는 CSS가 처리합니다. 둘째는 부품을 쪼개는 것입니다. 아이콘만 있는 버튼은 크기와 여백, 접근성 규칙이 모두 달라서 같은 부품의 변형으로 두면 예외 조건이 계속 늘어납니다. '이게 정말 같은 부품인가'를 한 번 물어보는 것만으로 축 하나를 없앨 수 있는 경우가 흔합니다.

6 쓸 때 / 안 쓸 때

배리언트와 프롭을 쓰는 경우

  • 축을 늘리기 전에 칸 수를 곱해 볼 때
  • 상태를 축에서 빼고 CSS에 맡길 때
  • 모양이 많이 달라서 부품을 쪼갤 때

배리언트와 프롭을 쓰지 않는 경우

  • 축을 다섯 개나 둘 때. 칸이 백 칸을 넘습니다
  • 호버와 누름을 칸으로 만들 때. 상태 축이 하나 늘어 칸이 두 배가 됩니다
  • 모양이 많이 다른 것까지 한 부품에 모두 넣을 때. 예외 조건이 계속 늘어납니다
  • 쓰지 않을 칸을 만들 때. '혹시 몰라서' 만든 칸이 절반을 차지하기도 합니다

배리언트와 프롭 대신 다른 것을 써야 하는 경우 — 부품 자체는 컴포넌트와 인스턴스, 값 묶음은 디자인 시스템, 배치는 오토 레이아웃.

7 자주 보는 모습구조만 따라 그린 재현 그림

8 코드와 맞춰 보기시안의 축과 코드의 props

시안의 축은 코드의 props가 되고, 호버나 누름 같은 상태는 CSS가 처리합니다.

// 축 = props. 세 개면 코드로는 세 줄이다
<Button size="md" tone="primary" disabled={false} />

/* 상태는 축이 아니다 — CSS 가 만든다 */
.btn:hover        { background: color-mix(in srgb, var(--accent) 86%, #000); }
.btn:active       { transform: translateY(1px); }
.btn:focus-visible{ outline: 3px solid var(--accent); }
.btn[disabled]    { opacity: .45; cursor: not-allowed; }

// 모양이 많이 다르면 쪼갠다 — 조건이 안 붙는다
<IconButton icon="trash" label="삭제" />
키와 동작그때 일어나야 하는 일
상태는 CSS로호버, 누름, 초점, 비활성은 CSS로 처리합니다. 이것들을 축으로 만들면 칸만 늘어납니다
:focus-visible포커스 표시는 키보드로 옮겼을 때만 보여야 해서 배리언트로는 만들 수 없습니다
disabled는 축일 수도모양이 아주 다르면 칸으로 두기도 합니다. 그래도 누를 수 없게 하는 동작은 CSS와 속성이 맡습니다
이름을 쓰임으로tone="danger"가 color="red"보다 낫습니다. 다크 모드에서는 위험 색이 빨강이 아닐 수도 있기 때문입니다
쪼갠 부품에도 접근성IconButton에는 글자가 없으니 aria-label이 꼭 필요합니다(이름 붙이기 참고)
안 쓰는 칸 찾기코드에서는 검색으로 실제로 쓰인 조합을 셀 수 있습니다

9 서버 쪽으로 치면백엔드 개념과 짝지어 보기

축 이름을 맞춘다시안의 강조와 코드의 tone처럼 축 이름이 다르면, 이야기할 때마다 두 이름을 옮겨 가며 맞춰야 합니다.
값도 맞춘다시안의 값이 주/약하게/위험이고 코드의 값이 primary/secondary/danger면, 둘을 짝지은 대응표를 하나 더 관리해야 합니다.
안 쓰는 조합 지우기실제로 쓰인 조합을 세어 보면 만들어 둔 조합의 절반이 쓰이지 않는 경우가 많으니, 쓰지 않는 조합은 지웁니다.

10 플랫폼마다 다른 이름웹 · iOS · 안드로이드에서 부르는 이름

플랫폼마다 이름은 달라도 정해 둔 변형을 props처럼 골라 쓰는 방식은 같습니다.

웹props · modifier
저장저장
props나 btn--ghost 같은 클래스로 변형을 고르고, 상태는 CSS가 처리합니다.
iOSButtonStyle
저장취소
.buttonStyle(.borderedProminent)처럼 이름이 붙은 스타일을 골라 씁니다.
안드로이드Material 버튼
저장취소
Filled · Outlined · Text처럼 버튼의 변형이 규격에 정해져 있습니다.

플랫폼 차이 때문에 자주 생기는 문제 — 시안에서 칸이 50개 넘는 컴포넌트 세트를 받으면 대개 축을 줄일 여지가 있습니다. 상태를 뺄 수 있는지, 부품을 쪼갤 수 있는지 두 가지만 물어봐도 칸 수가 절반으로 줄어듭니다. 코드 쪽에서도 마찬가지로, props가 다섯 개 넘는 컴포넌트는 대개 둘로 나눠야 할 부품을 하나로 합쳐 둔 것입니다.
