배리언트와 프롭

Variants & props

같은 부품의 정해진 변형. 축을 하나 늘릴 때마다 칸이 곱으로 늘어납니다.

1 실물 — 직접 만져 보기

새 탭에서 열기 ↗

축을 켜고 끄며 칸 수를 보세요 — 9 → 18 → 54 가 됩니다.
시안에서 54칸을 손으로 만들고 고칠 때마다 54번 손대는 것이 어떤 일인지가 배리언트 설계가 중요한 이유입니다. 코드에서는 props 세 개일 뿐입니다.

2 이름부르는 말이 여러 개다

한국어배리언트, 변형, 프롭, 속성
영어variant, variant property, props, component set
같이 쓰는 말변형의 축을 프로퍼티(property), 그 축의 값을 배리언트라 부릅니다. 같은 부품의 변형들을 모아 둔 것이 컴포넌트 세트입니다. 코드 쪽에서는 그대로 props이고, 클래스 이름으로 적으면 btn--primary 같은 모디파이어(BEM)입니다.
자주 잘못 부름상태 — 호버·누름은 사용자가 만드는 것이고, 배리언트는 우리가 고르는 것입니다.
컴포넌트 — 컴포넌트는 부품 자체, 배리언트는 그 안의 변형입니다.
스타일 — 색·글꼴만이 아니라 구조가 바뀌는 변형도 배리언트입니다.

3 가르는 기준형제들과 비교하는 네 축

현장 용어는 말이 아니라 일하는 단계를 가리킵니다. 이 네 가지만 물어보면 갈립니다.

무엇을 가리키나언제 나오나개발 쪽 대응물잘못 알아들으면
와이어프레임과 목업과 시안얼마나 진짜 같은 그림인가기획 ~ 디자인마크업 구조 ~ 완성 화면엉뚱한 리뷰가 돌아온다
디자인 시스템규칙 + 부품 + 문서프로젝트 내내토큰 + 컴포넌트 라이브러리스타일 가이드와 섞인다
컴포넌트와 인스턴스원본과 복제본시안 작업컴포넌트 정의와 사용원본을 고쳐 전체가 바뀐다
배리언트와 프롭같은 부품의 정해진 변형시안 작업props상태와 섞인다
오토 레이아웃자동 배치시안 작업flexbox‘여백이 자동’을 못 알아듣는다
프로토타입눌리는 시안리뷰 · 사용자 시험아직 코드가 아니다다 된 줄 안다
핸드오프넘기는 일개발 시작 전스펙 읽기그림만 받고 규칙은 못 받는다
에셋 내보내기그림 파일 넘기기개발 중srcset · SVG1배만 받아 뭉갠다

한 줄로 — 축을 늘리기 전에 곱해 보세요. 3×3×2 는 18칸이고, 거기에 하나만 더하면 54칸입니다.

4 축을 늘리면칸이 몇 개가 되나

5 해부도부분 이름이 제일 안 알려진 지식

축 — 크기 · 강조 · 상태. 각각 값이 몇 개인가
저장저장저장
칸 수 = 축의 값을 모두 곱한 것
축을 하나 늘리면 칸이 몇 배가 된다
코드로는 props — 같은 축, 같은 값
상태(호버·누름)는 배리언트로 안 만들기도 한다
  1. 축 크기 · 강조 · 상태각각 값이 몇 개인가
  2. 칸 축의 곱3 × 3 × 2 = 18
  3. 곱의 무서움 +1 축 = ×N축 하나가 칸을 몇 배로 만든다
  4. 코드로는 props시안의 축 = 코드의 props
  5. 상태는 빼기 :hover · :active사용자가 만드는 것은 CSS 에 맡긴다
  6. 쪼개기 다른 부품으로모양이 많이 다르면 따로 만든다

축을 줄이는 두 가지 방법이 있습니다. 하나는 상태를 빼는 것 — 호버·누름·초점은 사용자가 만드는 것이라 시안에 칸으로 둘 필요가 없고, CSS 가 알아서 합니다. 다른 하나는 부품을 쪼개는 것 — 아이콘만 있는 버튼은 크기·여백·접근성 규칙이 다 달라서, 같은 부품의 변형으로 두면 조건이 덕지덕지 붙습니다. '이게 정말 같은 부품인가'를 한 번 물어보면 축 하나가 사라지는 일이 흔합니다.

6 쓸 때 / 안 쓸 때

이럴 때 쓴다

  • 축을 늘리기 전에 곱해 보기
  • 상태는 축에서 빼고 CSS 에 맡기기
  • 모양이 많이 다르면 부품을 쪼개기

이럴 때는 안 쓴다

  • 축을 다섯 개 — 백 칸이 넘는다
  • 호버·누름을 칸으로 만들기 — 칸이 두 배가 된다
  • 한 부품에 다 넣기 — 조건이 덕지덕지 붙는다
  • 안 쓰는 칸 만들기 — '혹시 몰라서'가 절반을 차지한다

대신 이걸 — 부품 자체는 컴포넌트와 인스턴스, 값 묶음은 디자인 시스템, 배치는 오토 레이아웃.

7 자주 보는 모습구조만 흉내 낸 재현 그림

8 코드와 맞춰 보기이 변형의 계약서

시안의 축은 코드의 props이고, 상태는 CSS가 맡습니다.

// 축 = props. 세 개면 코드로는 세 줄이다
<Button size="md" tone="primary" disabled={false} />

/* 상태는 축이 아니다 — CSS 가 만든다 */
.btn:hover        { background: color-mix(in srgb, var(--accent) 86%, #000); }
.btn:active       { transform: translateY(1px); }
.btn:focus-visible{ outline: 3px solid var(--accent); }
.btn[disabled]    { opacity: .45; cursor: not-allowed; }

// 모양이 많이 다르면 쪼갠다 — 조건이 안 붙는다
<IconButton icon="trash" label="삭제" />
키일어나야 하는 일
상태는 CSS로호버·누름·초점·비활성. 축으로 만들면 칸만 는다
:focus-visible배리언트로는 못 만든다. 키보드일 때만 보여야 한다
disabled는 축일 수도모양이 아주 다르면 칸으로 두기도 한다. 다만 동작은 CSS·속성이 맡는다
이름을 쓰임으로tone="danger"가 color="red"보다 낫다 — 다크 모드에서 빨강이 아닐 수 있다
쪼갠 부품에도 접근성IconButton은 aria-label이 필수다 — 이름 붙이기
안 쓰는 칸 찾기코드에서는 검색으로 쓰인 조합을 셀 수 있다

9 서버 쪽으로 치면백엔드 감각으로 번역

축 이름을 맞춘다시안의 강조와 코드의 tone이 다르면 매번 통역해야 합니다.
값도 맞춘다시안이 주/약하게/위험이고 코드가 primary/secondary/danger면 표를 하나 더 들고 다니게 됩니다.
안 쓰는 조합 지우기쓰인 조합을 세어 보면 절반이 안 쓰이는 경우가 많습니다.

10 플랫폼마다 다른 이름같은 부품, 다른 말

이름은 달라도 props라는 생각은 같습니다.

웹props · modifier
저장저장
props나 btn--ghost 같은 클래스. 상태는 CSS 가 맡습니다.
iOSButtonStyle
저장취소
.buttonStyle(.borderedProminent)처럼 이름 붙은 스타일을 고릅니다.
안드로이드Material 버튼
저장취소
Filled · Outlined · Text 처럼 변형이 규격에 정해져 있습니다.

자주 생기는 사고 — 시안에서 칸이 50개 넘는 컴포넌트 세트를 받으면 대개 축을 줄일 여지가 있습니다. 상태를 뺄 수 있는지, 쪼갤 수 있는지 두 가지만 물어봐도 절반이 됩니다. 코드 쪽에서도 같은 이익이 있습니다 — props 가 다섯 개 넘는 컴포넌트는 대개 둘로 나눠야 할 것이 하나로 붙어 있는 것입니다.
