# 이름표 (what-is-this-called-ui)

화면 속 그게 뭔지 알려주는 프론트엔드 UI/UX 도감입니다.

백엔드를 하던 사람이 프론트엔드 화면을 볼 때 막히는 지점은 개념보다 **이름**인 경우가 많습니다. 부품 이름을 모르면 디자이너와 이야기할 때 말이 엇갈리고, 무엇을 검색해야 할지도 떠올리기 어렵습니다. 그래서 이 도감은 이름순 색인을 맨 뒤로 보내고, 입구에 **화면 지도**를 두었습니다. 지도에서 눈에 보이는 자리를 누르면 그 부품을 무엇이라고 부르는지 나옵니다.

👉 **<https://hyeongminpark2.github.io/what-is-this-called-ui/>**

## 항목 카드의 열 칸

모든 항목을 같은 열 칸 틀로 씁니다. 틀이 같아야 백 번째 항목을 읽을 때도 무엇이 어디에 있는지 바로 찾을 수 있기 때문입니다.

| 칸 | 내용 |
|---|---|
| ① 실물 | 실제로 눌러 볼 수 있는 예시입니다. **폭 토글**로 390 / 768 / 넓게를 바꿔 봅니다. |
| ② 이름 | 한국어 이름, 영어 이름, 같이 쓰는 말, 자주 잘못 부르는 이름 |
| ③ 가르는 기준 | 형제 부품들과 비교하는 축 |
| ④ 상태 | 기본, 진입, 열림, 처리 중, 에러, 닫힌 뒤를 나란히 보여 줍니다. 2부는 '단', '층', '쓰임'처럼 칸 이름이 다릅니다. |
| ⑤ 해부도 | 부분마다 번호와 이름 |
| ⑥ 쓸 때 / 안 쓸 때 | 쓰는 조건과 '대신 이걸' |
| ⑦ 자주 보는 모습 | 구조만 따라 그린 재현 그림 |
| ⑧ 마크업과 키보드 | 기본 마크업과 키마다 일어나야 하는 일입니다. 2부는 최소 코드와 지켜야 하는 규칙을 적습니다. |
| ⑨ 서버 쪽으로 치면 | 백엔드 개념과 짝지어 본 설명 |
| ⑩ 플랫폼 | 웹, iOS(HIG), 안드로이드(Material 3)에서 부르는 이름 |

## 화면 지도

이름만 적은 빈 상자를 늘어놓으면 이름은 알려 줄 수 있어도 **그 부품이 어떻게 생겼는지**는 알려 주지 못합니다. 그래서 진짜 앱처럼 내용을 채운 화면을 그리고 부분마다 번호를 붙였습니다.

서비스 종류가 다르면 쓰는 부품도 달라집니다. 모든 화면이 관리 대시보드처럼 생기지는 않기 때문에 지도 여덟 장을 나란히 두었고, 장끼리 겹치는 이름이 거의 없도록 골랐습니다.

| 화면 | 여기서만 보는 것 |
|---|---|
| PC · 관리 도구 | 사이드바, 데이터 테이블, 필터 칩, 스탯 타일, 페이지네이션 |
| PC · 쇼핑몰 | 메가 메뉴, 히어로, 상품 카드, 별점, 리본, 쿠키 배너 |
| PC · OTT | 빌보드, 로우, 포스터 타일, 스크러버, 자막 버튼, 호버 프리뷰 카드 |
| PC · 기업 소개 | 스크롤 진행 표시줄, 패럴랙스, 스크롤 등장, 스티키 섹션, 아코디언 |
| PC · 설정 | 텍스트 필드, 라벨, 헬퍼 텍스트, 에러 상태, 스위치, 라디오, 슬라이더, 위험 구역 |
| PC · 메신저 | 말풍선과 꼬리, 읽음 표시, 타이핑 인디케이터, 반응 이모지, 답장 인용, 스레드, 멘션 자동완성 |
| PC · 글쓰기 도구 | 트리뷰, 툴바, 선택 영역, 플로팅 툴바, 댓글 핀, 상태 표시줄 |
| 폰 | 세이프 에어리어, FAB, 바텀시트, 바텀 탭바, 홈 인디케이터 |

OTT 화면만 어둡게 그렸기 때문에, 같은 부품이 다크 UI에서는 어떻게 보이는지도 함께 볼 수 있습니다.

지도를 그리고 다루는 방식은 다음과 같습니다.

- **지시선은 늘 그어 두지 않습니다.** 이름 열다섯 개에서 선이 한꺼번에 뻗어 나오면 그림을 알아보기 어렵습니다. 평소에는 작은 번호 배지와 아래 목록만 보여 주고, 사용자가 짚은 것 하나에만 지시선을 긋습니다.
- **목록과 화면 어느 쪽에서 찾아도 됩니다.** 목록의 이름에 마우스를 올리면 화면에서 그 부품이 밝아지고, 화면의 부품에 올리면 목록에서 그 이름이 밝아집니다. 부품이 겹쳐 있으면 안쪽 부품을 고릅니다.
- 지시선 좌표는 JS가 매번 계산합니다. 좌표를 손으로 적어 두면 화면 폭이 바뀔 때마다 선이 어긋나기 때문입니다.
- 번호 배지가 가리키는 부품을 덮으면 안 됩니다. 그래서 높이가 낮은 부품은 왼쪽 바깥으로, 오른쪽 끝에 붙은 작은 부품은 오른쪽 바깥으로 배지를 뺍니다. 검사 스크립트가 배지가 부품을 덮는 넓이를 재서 이를 확인합니다.
- 좁은 화면에서는 지시선을 쓰지 않고 번호로만 목록과 잇습니다. PC 화면 지도는 옆으로 밀어서 봅니다.

항목을 부 단위로 묶어 한꺼번에 쓴 데에는 이유가 있습니다. 입문자가 실제로 막히는 질문은 "모달이 뭐냐"보다 "모달과 저건 뭐가 다르냐"이기 때문입니다. 그래서 같은 부의 항목들은 서로를 가리키고, 각 항목의 ③ 칸에는 부 전체가 같이 쓰는 비교표가 나오며 그 항목의 줄만 굵게 표시됩니다. 부마다 비교하는 축은 다음과 같습니다.

- 1부: 무엇을 정하나 · 방향 · 넘치면 · 누가 값을 정하나
- 2부: 무엇을 정하나 · 몇 단이 좋나 · 바꾸면 어디가 바뀌나 · 틀렸을 때 증상
- 3부: 무엇을 바꾸나 · 한글에서 다른 점 · 안 지키면 · 고르는 단위
- 4부: 고르는 개수 · 선택지가 보이나 · 바로 적용되나 · 타이핑
- 5부: 무엇을 담나 · 전체가 눌리나 · 어떻게 모이나 · 내용이 길어지면
- 6부: 뒤쪽 화면을 막는가 · 포커스를 안에 가두는가 · 뒤쪽 화면의 스크롤은 · 화면 어디에서 뜨는가
- 7부: 자리 · 데려가는 곳 · 지금 위치 · 감당하는 개수
- 8부: 끝나는 때를 아나 · 들어올 자리를 잡나 · 사용자가 기다리나 · 화면이 덜컥거리나
- 12부: 무엇을 돕나 · 눈으로 보이나 · 안 하면 누가 막히나 · 어떻게 확인하나

## 구조

```
index.html          입구: 화면 지도, 혼동 쌍, 목차
items/*.html        항목 카드 181장 (tools/gen 으로 찍는다)
demos/*.html        각 항목 ① 칸에 들어가는 실물 예시 181장
appendix.html       부록 색인 (tools/appendix.js 로 항목 카드에서 다시 만든다)
tools/gen/          항목 카드 생성기 (tools/README.md 참고)
tools/check.js      브라우저 검사 (tools/README.md 참고)
assets/base.css     디자인 토큰과 도감 바깥 틀
assets/card.css     항목 카드 열 칸 틀
assets/demo.css     예시 안에서 쓰는 UI 부품
assets/map.css      화면 지도 속 가짜 앱 화면과 번호

```

빌드 도구가 없어서 `index.html`을 브라우저로 그냥 열면 됩니다.

## 원칙

- **상태까지 보여 줍니다.** 버튼 그림 한 장으로는 눌렀을 때, 비활성일 때, 처리 중일 때의 모습을 알 수 없기 때문에 상태마다 그림을 따로 둡니다.
- **캡처한 그림 대신 실제로 돌아가는 HTML로 보여 줍니다.** 호버, 포커스, 애니메이션은 캡처한 그림으로는 전달되지 않습니다.
- **PC와 폰을 같은 항목 안에서 비교합니다.** 폭 토글을 움직여 같은 부품이 좁은 화면에서 어떻게 바뀌는지 직접 확인할 수 있습니다.
- **다른 제품의 화면 캡처를 쓰지 않습니다.** 모든 그림은 색과 로고를 뺀 재현이고, 설명에 필요 없는 요소가 없어서 오히려 구조가 잘 보입니다.
