# 검사

```sh
node tools/check.js                                                    # 레포의 파일
node tools/check.js https://hyeongminpark2.github.io/what-is-this-called-ui/   # 배포본
```

Playwright와 node 20 이상이 필요합니다. 이 머신에서는 다음처럼 돌립니다.

```sh
NODE_PATH=/data/work/verbatim/node_modules /data/tools/node20/bin/node tools/check.js
```

배포본을 검사할 때는 주소 끝에 빗금(`/`)을 꼭 붙입니다. 빗금이 없으면 `index.html`이 계정 루트 주소로 풀려서, 지도가 없는 페이지를 열고 시간 초과로 실패합니다.

## 무엇을 보나

모달이 열리고 닫히는지 같은 기능만 보는 것이 아니라 **레이아웃이 무너졌는지**도 봅니다. 기능 검사만 돌리면 해부도 글자가 세로로 한 글자씩 쌓여 칸 높이가 10,000px가 되어도 통과하기 때문입니다.

- 글이 세로로 쌓였는지 (폭이 46px 미만인데 높이가 170px를 넘는 글 상자)
- 그림이 칸 밖으로 잘렸는지
- 390px 폭에서 가로로 넘치는지
- 페이지 전체 높이가 터무니없이 길어졌는지
- 폭 토글이 실제로 390 / 768 폭을 만드는지
- 좁은 폭에서 모달이 바텀시트로 바뀌는지
- 포커스가 **배경의 누를 수 있는 요소에 닿지 않는지**, 배경이 정말 비활성인지, 닫은 뒤 포커스가 모달을 연 버튼으로 돌아오는지

항목 카드는 **181장 모두** 같은 틀인지 봅니다. 칸이 9개인지, 해부도 번호가 목록과 1대1로 맞고 1부터 이어지는지, `<hr>` 같은 빈 태그에 번호를 붙여 번호가 그려지지 않는 곳은 없는지, 형제 링크가 같은 부에서 자기만 뺀 목록인지, 해부도 번호가 잘리거나 서로 겹치거나 찌그러지지 않았는지를 확인합니다.

**번호가 한 칸 밀려 있지 않은지**도 봅니다. 번호끼리 겹치면 자동으로 비키는데, 예전에는 아래로 비켰습니다. 그러면 겹치지도 잘리지도 않은 채 **옆 줄을 가리키는** 번호가 생겨서, 눈으로 봐도 기존 검사로도 잡히지 않았습니다. 지금은 `card.js`가 번호를 같은 줄에 둔 채 바깥으로만 밀고, 검사는 번호의 세로 중심이 자기 부품 상자 안에 있는지를 확인합니다. 이 검사를 넣자마자 6부 카드 네 장에서 번호 여덟 개가 걸렸습니다. 이 문제를 처음부터 막으려면 해부도를 한 겹의 세로 줄로 그리고 **번호를 중첩해 넣지 않는** 것이 좋습니다.

데모 181장도 실제로 눌러 봅니다. 토스트가 쌓이고 되돌려지고 저절로 사라지는지, 시트가 화면 아래에 붙는지, 드로어가 높이를 다 쓰는지, 팝오버가 화면 가장자리에서 반대쪽으로 뒤집히는지, 툴팁이 지연 뒤에 뜨고 마우스 이벤트를 받지 않는지, `show()`와 `showModal()`이 정말 다르게 동작하는지를 확인합니다.

### 부마다 데모가 재는 것

2부 토큰 데모는 **보여 주려는 실패가 아직 실패하는지**도 봅니다. 색을 직접 적어 둔 카드가 다크 모드를 따라오지 않는지, 비율을 끄면 단 사이 비가 정말 들쭉날쭉해지는지, z-index에 9999를 쓰면 모달이 가림막에 덮이는지를 확인합니다. 이 실패가 고쳐져 버리면 데모가 보여 줄 것이 없어지기 때문입니다.

2부의 나머지 데모는 **값을 재서 판정합니다.** 안쪽 모서리가 `바깥 − 여백`과 같은지, 자르지 않으면 네모난 그림이 둥근 모서리 자리를 정말 덮는지(그 점을 찍어 봅니다), 맞닿은 테두리가 1 + 1 = **2px**가 되는지, `opacity: .5`가 대비비를 4.5:1 아래로 떨어뜨리는지, 그리고 **부모의 opacity가 자식의 z-index를 그 안에 가두는지**(겹치는 자리를 찍어 어느 쪽이 위인지 봅니다)를 확인합니다. 아이콘은 24px로 그린 선이 12px에서 0.75px로 얇아지는지 계산하고, 상태 색은 적록 색각 흉내를 거친 뒤 성공 색과 오류 색의 **색 거리**를 잽니다. 토큰 이름은 규칙 세 가지로 판정합니다.

1부 데모는 **뼈대를 숫자로** 잽니다. `absolute`로 바꾸면 자리를 정말 차지하지 않는지(빠진 자리를 점선으로 보여 줍니다), 폭을 세 가지로 바꿔도 비가 같은지, 스냅과 부드러운 스크롤, 튐 막기가 computed style에 실제로 걸리는지, `max-content`가 넉넉한 폭에서도 넘치는지, 맞닿은 24px와 16px 여백이 40이 아니라 **24**로 나오는지를 확인합니다. 마지막으로 눈으로는 볼 수 없는 문제도 잡습니다. `row-reverse`로 순서를 뒤집은 뒤 **Tab을 실제로 눌러** 포커스가 간 차례를 적고, 그 차례가 눈에 보이는 차례(그려진 x 좌표)와 다른지를 봅니다.

5부 데모는 **생김새가 비슷한 것들을 숫자로 가릅니다.** 글자 없이도 뜻이 통하는 아이콘이 몇 개인지 세고(일곱 개 중 세 개), 썸네일은 cover가 잘라내는 넓이와 fill이 일그러뜨리는 비율을 백분율로 잽니다. 테이블 행은 밀도를 바꿔 가며 480px에 몇 줄이 들어가는지 세고, **행 전체를 링크로 두었을 때 안쪽 버튼을 누르면 행 링크까지 눌리는 횟수**를 셉니다. 키-값 목록은 담긴 폭과 보이는 폭을 비교해 잘린 줄을 세고, 미디어 오브젝트는 **글이 그림 밑으로 흘러 들어갔는지**를 글줄 좌표로 보고, 접히는 글은 찾는 말이 **접힌 글 속에 몇 건** 있는지를 따로 셉니다.

6부 데모는 **겹쳐 뜬 것이 화면을 얼마나 가리는지**를 잽니다. 액션 시트가 화면의 몇 %를 덮는지, 배너를 네 개 쌓으면 알림이 내용보다 커지는지, 오류 메시지가 틀린 칸에서 몇 px 떨어져 있는지, 띄엄띄엄 입력했을 때 찾는 개수가 이어진 글자로만 찾을 때보다 많은지, 라이트박스를 닫은 뒤 **포커스가 눌렀던 칸으로 돌아가는지**를 확인합니다. 메뉴가 화면 밖으로 몇 px 나가는지, ⋯ 버튼을 빼면 **같은 일을 하는 경로가 하나로 줄어드는지**, 코치마크를 네 개 띄우면 한꺼번에 읽어야 하는 말풍선이 몇 개가 되는지, 좁은 폭에서 모달이 전체 화면 레이어보다 **내용 칸을 더 좁히는지**도 봅니다.

7부 데모는 **탐색 경로가 끊기는 자리**를 잽니다. 단계 이름이 좁은 폭에서 잘리는지 칸마다 담긴 폭과 보이는 폭을 비교하고, 트리를 깊이 펼치면 이름이 들어갈 자리가 정말 줄어드는지 px로 셉니다. 고정 헤더가 있는 문서에서 앵커로 이동한 뒤 제목이 헤더 밑에 가려지는지 좌표로 보고, 링크로 바로 들어오면 뒤로가기로 갈 곳이 없는지 방문 기록을 가지고 확인합니다. 메가 메뉴는 **대각선으로 움직이는 마우스 경로를 흉내 내** 가는 동안 메뉴가 몇 번 바뀌는지 셉니다. 열기를 100ms 늦추면 그 횟수가 0이 되는 것까지 확인해야 검사 한 쌍이 끝납니다.

8부 데모는 **잘못 만들었을 때 치르는 비용을 셉니다.** 확인 창이 지울 때마다 사용자를 몇 번 멈춰 세우는지, 화면 전체를 다시 그리면 **포커스와 입력하던 글이 실제로 사라지는지**(입력칸을 진짜로 새로 만들어 봅니다)를 확인합니다. 성공을 알리지 않으면 사용자가 같은 요청을 몇 번 더 보내는지, 백오프 없이 재시도하면 같은 시간에 요청을 몇 배 더 보내는지, 연결이 끊긴 동안 쌓인 작업과 잃은 작업이 몇 건인지, 데이터를 다시 받는 동안 **숫자가 화면에서 사라져 있던 시간(ms)**이 얼마인지도 잽니다.

9부 데모는 **움직임 자체**를 잽니다. 같은 시간 동안 움직이는 네 곡선이 정말 같은 시간에 끝나는지, `left`로 움직이는 쪽이 `transform`보다 실제로 프레임 시간을 더 쓰는지(한 프레임을 만들고 재서 숫자로 비교합니다), 시차 간격을 키우면 마지막 줄이 3초를 넘겨 나타나는지, 모션 줄이기를 켜면 큰 이동은 멈추고 **투명도 변화는 남는지**를 확인합니다. 마지막 검사는 모션 줄이기를 '애니메이션 전부 끄기'로 처리한 코드를 잡기 위한 것입니다.

10부 데모도 같은 방식입니다. 디바운스를 끄면 글자를 칠 때마다 요청이 나가는지, 일부만 고른 상태에서 머리글 체크박스가 중간 상태가 되는지, 가상 스크롤을 끄면 천 개가 정말 모두 만들어지는지, 제출했을 때 처음 틀린 칸으로 포커스가 가는지, 질문을 바꾸면 알맞은 차트도 바뀌는지를 확인합니다.

11부 데모는 **PC에서는 보이지 않는 문제**를 흉내 내서 잽니다. 기기 폭으로 브레이크포인트를 나누면 390px에서 가게 이름이 정말 두 줄로 접히는지(접힌 칸을 셉니다), 보이는 크기 24px와 눌리는 넓이 44px가 따로 움직이는지, 모달을 방문 기록에 넣지 않으면 뒤로가기가 엉뚱한 화면을 닫는지, 키보드가 올라오면 바닥의 버튼이 가려지는지를 확인합니다. 모두 실제 폰이 없어도 잡히도록 만든 검사입니다.

13부 데모는 **화면이 아니라 흐름**을 잽니다. 오류 문구를 자세히 쓰면 계정이 있는지가 드러나는지, 단계를 넷에서 여섯으로 늘리면 끝까지 마치는 사람이 절반 아래로 떨어지는지, 결과에서 상세로 들어갔다 돌아오면 검색어와 스크롤 위치가 되살아나는지, 결제를 두 번 눌렀을 때 주문이 두 개 생기는지, 권한을 묻기 전 설명에서 '나중에'를 고르면 OS 권한 창을 띄울 기회를 아낄 수 있는지를 확인합니다.

13부의 나머지 데모는 **보이면 안 되는 정보가 보이는지**를 셉니다. 프로필은 보는 사람을 바꿔 가며 지금 보이는 칸과 그중 볼 자격이 없는 칸을 세고, 대시보드는 맨 위 칸이 전체 높이에서 차지하는 비율을 재서 가장 중요한 지표가 묻혔는지 봅니다. 공유는 범위마다 볼 수 있는 사람 수를 어림해 회사 밖까지 열리는지 확인합니다. 파일 올리기는 **헛되이 올린 양(MB)**을 잽니다. 미리 거르면 0이고, 거르지 않으면 14.8MB를 보낸 뒤 거절당합니다. 여러 파일을 한 묶음으로 처리하면 멀쩡한 세 장까지 함께 실패하는 것도 확인합니다.

14부 데모는 **문구를 규칙으로 판정합니다.** 동사가 있는지, 두세 어절인지, '확인'이나 '제출'처럼 뜻이 없는 말인지를 봅니다. 사람이 읽고 판단하는 대신 규칙을 돌리기 때문에 검사도 같은 기준으로 확인할 수 있습니다. 받침을 보고 조사를 고르는 데모도 마찬가지로, '모란상회'는 '를', '대림유통'은 '을'을 고르고, 'Starbucks'는 **모른다고 답해야** 통과합니다.

15부 데모는 **시안 도구의 동작을 흉내 내서** 잽니다. 토큰 하나를 바꾸면 부품이 따라 바뀌는지, 연결을 끊은(디태치) 인스턴스 하나만 옛 모습에 머무는지, 축을 하나 더하면 칸이 18개에서 54개가 되는지, 오토 레이아웃 조작기와 그 아래 CSS가 함께 움직이는지를 확인합니다. 마지막 데모는 두 개념이 같은 것임을 보여 주려고 만들었기 때문에 **상자의 computed style과 화면에 적힌 CSS를 둘 다** 확인합니다.

### 그 밖에

**부록 색인은 손으로 적지 않습니다.** `tools/appendix.js`가 항목 카드에서 이름, 영어 이름, 부, 설명을 뽑아 `appendix.html`을 다시 만듭니다. 항목이 늘거나 카드 설명을 고치면 이 스크립트를 다시 돌려야 하고, 돌리지 않으면 검사가 **색인에 빠진 항목**을 이름까지 짚어 알려 줍니다. 항목 카드가 원본이고 색인은 거기서 만든 사본입니다.

포커스 갇힘은 iframe 안에서는 검사할 수 없어서 `demos/modal.html`을 직접 열어 검사합니다.

**단정문이 모두 통과해도 스크린샷을 눈으로 확인합니다.**

# 카드 생성기

`items/*.html` 항목 카드는 `tools/gen/`의 생성기로 찍습니다. 찍힌 HTML이 레포에 올라가는 실제 파일이고, 생성기는 아홉 칸 틀이 어긋나지 않게 다시 찍기 위해 둡니다.

```sh
python3 tools/gen/build.py tooltip popover    # d_tooltip.py, d_popover.py → items/
```

- `tmpl.py`: 아홉 칸 카드의 틀과 칸마다 쓰는 조각 함수입니다. `parts.py`는 여러 카드가 같이 쓰는 그림 조각입니다.
- `d_<이름>.py`: 항목 하나의 데이터입니다. `items/modal.html`만 데이터 파일 없이 손으로 쓴 첫 카드입니다.
- `_t14.py`, `_t15.py`, `_tx.py`: 몇몇 부의 카드가 같이 쓰는 작은 조각입니다.

카드의 문장을 고칠 때는 `items/*.html`이 아니라 `d_<이름>.py`를 고친 뒤 다시 찍습니다. 카드 HTML을 손으로 고쳤다면 데이터 파일도 같이 고쳐서, 다시 찍었을 때 `git diff`가 비어 있어야 합니다. 카드 설명(`desc`)을 바꿨다면 `node tools/appendix.js`로 색인도 다시 만듭니다.
